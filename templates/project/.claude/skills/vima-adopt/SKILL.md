# vima-adopt：接管陌生代码库

接管的全部风险浓缩成一句话：**反推容易把既有缺陷追认成规格**。
代码里有个字段叫 `status` 存了五种值，你反推出「status 有五种状态」——
这句话作为「代码现在是这样」是真的，作为「系统应当这样」是假的，
而它可能只是三年前一次没做完的重构留下的。

所以这个规程的骨架就是一条区分，第三节是全篇的重点。

## 零、先看现状（展开时实测）

!`vima status 2>/dev/null || echo '（拿不到 vima status：vima 不在 PATH。先把它装好——接管的第一步就是看清现状，看不清就别动手。）'`

三种情况分开处理：**不在 vima 项目里** → 先 `vima init`；**已 init 但三档全 0**
→ 这才是真正的从零接管；**已经有命题** → 别重新反推一遍，先看它已经覆盖到哪，
只补空档。反推第二遍产出的是重名不同义的命题，比没覆盖更难收拾。

## 一、先划边界，别一口吞

`vima init` 之后，不要立刻全库扫描。先跟用户确认接管范围：
哪些目录是活的业务代码、哪些是 vendor/生成物/已废弃模块。
把范围写进 `.vima/project.json` 的 `apps`。

范围之外的代码**一条命题都不要生成**。上一代吃过的亏是把整棵树扫进来，
产出几百条谁也不看的命题，然后覆盖率永远 30%，看的人第二周就放弃了。

## 二、用 extract 拿代码事实，不要自己写扫描器

`core/extract.mjs` 是全系统唯一从代码提取事实的地方（正则、扫描方式、
注释处理、行号换算都在那一处）。你要的是路由表、调用图、标注——
通过 `vima` 命令拿它的结果，**不要自己 grep 一套并行的事实**。
两套扫描器必然漂移，而漂移的那天没人知道该信哪一份。

同时读一下它自陈的 `CAPABILITY`：当前是 file 级归属、看不见 import 图。
接管报告里要如实写出这个边界，别让人以为覆盖表是全知的。

## 三、两个轴分开填 —— 本规程的核心

反推出来的每条命题，两个轴**分别**判定：

**来源可信度 S：可以标最高档 `fact`。**
理由正当：这条命题的来源是正在运行的代码本身，比任何一份人写的文档都硬。
「系统当前暴露 `GET /api/orders`」——这是事实，标 `fact` 没有问题。

**验证强度 E：一律从 `claimed` 起步，不得自动继承。**
代码存在 ≠ 代码正确 ≠ 代码是有意为之。「来源是事实」和「行为被验证过」
是两件完全不同的事，正交两轴的整个设计就是为了让它们分开记。

如果这里图省事，把反推命题直接标成 `observed`，后果是确定的：
**接管当天覆盖表就全绿，既有缺陷被追认成规格，此后任何人想改都要先跟一条
「已达标」的命题打架。** 接管的价值瞬间归零——你没有获得一份规格，
你只是给现状盖了个章。

具体怎么落：

- `impl` 层命题：来源 `fact`，证据 `derived`（extract 推出来的，可重放）。
- `contract` 层命题：来源 `fact`（签名是事实），`need` 至少 `executed`，
  证据先留空——接口能被调通要单独取证。
- `spec` 层命题：这一层最危险。从代码倒推「系统应当…」时，来源标 `fact`
  但正文必须写明「**由现状反推，未经人确认**」，证据 `claimed`。
- `intent` 层：**不要反推**。代码里没有意图。留空，等人来写，
  或在 intake 里问出来。凭空生成的 intent 是纯粹的污染。

## 四、把「反推」这件事本身记成 ruling

接管过程里你必然会做一批判断：这个模块算不算活的、这三个近似接口算一个还是三个、
这个 magic number 是规格还是意外。每个都记 ruling，`confidence` 老实写。
批量反推时 confidence 普遍偏低是正常的，不要为了台账好看往上抬。

## 五、交付一份诚实的接管报告

跑 `vima audit`，然后给用户三张清单：

1. **反推出了什么**：按层计数，注明全部证据强度为 `claimed`/`derived`。
2. **看不见什么**：extract 的能力边界、被排除的目录、没有 intent 层。
3. **最该先人工确认的 N 条**：blastRadius 大且 confidence 低的排前面。

明确告诉用户：**现在覆盖表上的绿不代表系统是对的，只代表代码是这样的。**
把 `claimed` 抬到 `executed` 需要真去跑一遍，那是接管之后的事，不是接管的一部分。
