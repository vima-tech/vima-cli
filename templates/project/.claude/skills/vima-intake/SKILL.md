# vima-intake：从物料到命题

物料进来时是散的：三份文档说法不一、有口头补充、有截图里的字段、还有一句「按上次那个项目来」。
这个规程把它整理成 `docs/` 下的规格 markdown，再由 `vima compile` 编译成命题。

**先明确两件事**：`docs/` 里的 markdown 是唯一真源，命题是它的投影；
你写 markdown，不要试图直接写事件或命题。

## 项目现在有什么（展开时实测，不是印象）

!`vima status 2>/dev/null || echo '（拿不到 vima status：vima 不在 PATH。先把它装好——下面每一步都要照着真实状态做，不要凭印象编。）'`

已经立过的题不要再立一遍：同一件事出两条命题，覆盖表会同时变长和变虚。
上面显示「不在 vima 项目里」的话，`vima init` 是这个规程的前置条件而不是它的一步——
先把项目立起来再回来，别直接往 `docs/` 里写。

## 一、清点物料，先建来源台账

在 `docs/raw/` 下逐份归档，每份开头写一段来源说明：**谁给的 · 什么时候 · 是什么性质**。
性质决定这份材料能撑起多高的来源可信度（S 轴）：

| 材料 | S 轴 | 说明 |
|---|---|---|
| 现网行为、可运行的代码、真实数据样本 | `fact` | 能被复核的客观事实 |
| 明确作废/被新版取代但仍在引用的旧文档 | `superseded` | 不能直接删，下游可能还挂着它 |
| 人写的需求、口头描述、会议纪要 | `stated` | 绝大多数物料在这一档 |
| 你自己补的空缺 | `ruled` | 见第四节 |

来源不明的材料标 `stated` 并在正文里注明「来源不明」——不要为了好看往上抬档。

## 二、切成命题，而不是切成章节

命题就写在 `docs/` 的 markdown 里，**一份文件一层**，文件头声明层与缺省值：

```
---
layer: spec
upstream: [intent-login]
trust: stated
need: derived
---

背景写成正文段落，它不参与编译。

- `spec-login-remember` 登录页提供「记住我」勾选框
- `spec-login-captcha` 连续失败 3 次后出验证码
  - need: executed
```

一条命题 = 一个列表项，反引号包住 id，其后是陈述。常见情形到此为止——
层、可信度、门槛、上游都从文件头继承，只有例外才缩进两格补属性。
可写的属性只有 `trust` / `need` / `from` / `source` / `impl` / `ruling.*`，
写错当场报错。完整说明在 `docs/intent.md` 的「格式说明」一节。

**顶层（intent）不写 `from`，写 `source`**：它上面没有命题了，出处只能是物料
（`docs/raw/` 下那份纪要、聊天记录、旧文档）。说不出物料出处的意图，
就是你自己想出来的需求——compile 会当场拒掉它，这是刻意的。

一条命题 = 一句**可以被判定真假**的话，落在某一层：

- `intent` 为什么做，成功长什么样
- `spec` 系统对外应当表现成什么样（用户看得见的行为）
- `contract` 接口、数据形状、错误码
- `impl` 落在哪些符号/文件上
- `behavior` 运行起来实际是什么样

判据：一句话如果无法回答「怎么验证它做到了」，它就还不是命题，是背景。
背景写在章节正文，命题写成条目。每条命题声明它需要多强的证据（`need`）——
`intent` 多半停在 `derived`，`contract` 至少 `executed`，别一律拉满，
门槛虚高会让整张覆盖表永远飘红，然后所有人开始无视它。

## 三、连编译边

每条下游命题写清它来自哪些上游（`from`）。这条边是失效传播的轨道：
上游改了，下游的证据自动过期。**边连错比不连更糟**——不连只是缺覆盖，
连错会让无关的东西集体失效，人很快就学会忽略失效清单。

只连真实的派生关系：contract 来自 spec，spec 来自 intent。
不要为了图好看把所有 impl 都挂到同一条 intent 上。

## 四、多来源矛盾：定夺 → 记 ruling → 继续

发现两份材料冲突时，**不要停下来问人**（约束 C4：不阻塞）。按以下顺序做：

1. **先按 S 轴比一次**。`fact` 压 `stated`，新版压 `superseded`。
   能靠可信度分出胜负的，不算矛盾，直接采用高档那份，在正文注明另一份被取代。
2. **同档冲突才需要裁定**。选一个，写一条 ruling，记全五件事：
   - `question` 冲突的到底是什么（写具体，别写「文档不一致」）
   - `options` candidate 各自出自哪份材料
   - `chosen` 选了哪个
   - `rationale` 为什么——依据是什么，不是「感觉更合理」
   - `confidence` + `blastRadius` 这两项**必填**。没有优先级的裁定台账
     会走向和「永远消不掉的告警」同一个结局：人不看了。
     confidence 低、blastRadius 大的排最前面，那是最该被人复核的。
3. **被裁定的命题 trust 标 `ruled`**，不要标成 `stated` 混进人写的需求里。
   人复核时要一眼认出哪些是 AI 替他定的。
4. 继续往下做。人推翻裁定时走既有的失效传播链路，不需要你为它预留回滚。

## 五、收尾

- 跑 `vima compile`（不带参数就是编整棵 `docs/`），看它报出来的逐条拒绝理由。
  层序由系统按 intent → spec → contract → impl → behavior 排，你不用管文件名。
- 跑 `vima audit` 看覆盖：哪些层完全没有命题、哪些命题一条证据都没有。
- 把「已知没搞清楚的」单列一节写进 `docs/`，标 `ruled` + 低 confidence。
  **写下来的未知 > 装作没有的未知。**
