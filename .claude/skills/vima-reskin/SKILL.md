# vima-reskin：换皮

vima 的资产分皮骨两层：

- **骨**：版面词表、交互范式、信息架构词表。它们决定「这是什么」——
  一个列表页有工具条、有搜索、有表格、有分页。
- **皮**：令牌阶梯。它们决定「长什么样」——颜色、间距刻度、圆角、字阶、阴影。

换皮 = 只换后者。骨不动，所以换皮是安全的、可回退的、不需要重新验收行为的。

## 一、先确认这确实是换皮

用户说「换个风格」时，实际想要的可能是三种：

1. **换皮**：同样的页面，另一种视觉调性。→ 本规程。
2. **换骨**：列表改成卡片流、侧栏改成顶栏、表单分步。→ 这是改 spec，
   走 intake 记需求、重新编译命题，**不要**用换皮硬凑。
3. **两者都要**。→ 分两步做，先换骨再换皮。合在一起做，出问题时分不清是谁引起的。

问清楚再动手。把判断结果记成一条 ruling（confidence 通常不低，写清依据）。

## 二、看清当前 theme 覆盖了什么

换之前先把基线拍下来（展开时实测）：

!`vima status 2>/dev/null || echo '（拿不到 vima status：vima 不在 PATH。装好再换——没有换前基线，第四节的「失效清单为空」就无从对比。）'`

这份基线有两个用处：一是它给出当前 `主题`，二是**换皮前失效清单里已经有的那几条，
换完之后仍在里面不算你造成的**。不先记下来，第四节会把旧账算到换皮头上。

`.vima/project.json` 的 `theme` 指向资产仓 `assets/style/tokens/<theme>.json`。
先读它，列出：这个阶梯定义了哪些令牌、项目在它之上又局部覆盖了哪些。

**局部覆盖是换皮的主要障碍。** 项目里每一处硬编码的颜色/间距都是换皮换不掉的钉子。
换皮前先跑一遍机检，把硬编码列出来交给用户看——
「这次能换掉 90%，剩下这 12 处是硬编码的」比事后发现半绿半旧诚实得多。

## 三、换

1. 选或写新的令牌阶梯。**阶梯的键必须与旧的完全一致**——
   换皮换的是值不是结构。少一个键，用到它的块就会静默退化。
2. 改 `.vima/project.json` 的 `theme`，跑 `vima compile`。
3. 把上一节列出的硬编码逐个改成引用令牌。这是换皮里唯一真正的工作量，
   也是换皮的副产品价值：**它把项目从「这次能换」推进到「以后都能换」。**

## 四、验形

换皮不改行为，所以：

- `spec` / `contract` / `impl` 层的命题**不应该有任何一条失效**。
  如果失效了，说明你动到了骨——回去看是哪一步越界了。
- 视觉是 `behavior` 层的事。换皮后这一层的证据需要重新取。

跑 `vima audit`，把「失效清单为空」这件事明确报给用户——
这正是皮骨分离的收益，值得说出来。

## 五、什么时候该说「这不该用换皮做」

- 新皮需要**新增令牌键** → 阶梯结构变了，这是资产仓的改动，走 harvest 提名。
- 换完之后**某些页面明显不能看** → 那些页面依赖了旧皮的具体值（比如指望某个色阶
  足够浅来当背景）。这是既有实现的耦合缺陷，如实报出来，不要靠调新皮的值去迁就它。
- 用户其实想要**多套皮同时存在** → 那是 apps 多端的事，不是 theme 的事。
