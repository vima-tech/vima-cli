## A1 代码级追溯：`@vima <taskId>` 标注 + `vima trace`

### 动机（PACT 对应机制与其解决的问题）

PACT 要求每段业务代码带 `@pact R###` 注释，由 `pact-trace.sh`
（`/home/renmk/projects/PACT/pact/scripts/pact-trace.sh`）做三方交叉比对：
规格 P5 声称要做的 R-ID ↔ 代码里实际标注的 R-ID ↔ 执行图谱声称完成的 R-ID。
它抓两类靠人眼永远抓不到的问题：

- **虚报**：状态说「完成」，代码里却反查不到任何实现痕迹；
- **野生**：代码实现了任何规格都没有的功能（未经授权的复杂度）。

v2.0 的完成度信号只有任务 frontmatter `status` 与构建结果——`status: done`
完全靠主 Agent 自觉回写，没有任何机制验证「done 的任务在代码里真的存在」。
这正是 PACT 用一条 grep 管线就堵死的洞，移植成本极低、收益直接。

### 规格（vima-cli 中的确切行为）

新增命令 `vima trace`（C3 所有，`lib/commands/trace.mjs`），规则见契约 §10：

1. **标注语法**：代码注释内 `@vima <taskId>`，正则 `/@vima\s+([a-z0-9][a-z0-9-]*)/g`。
   taskId 即任务 frontmatter 的 `taskId`（不另造 ID 体系——vima 的追溯单元是任务，
   不是需求条目，这是与 PACT `R###` 的刻意差异：vima 的需求→任务映射已由
   coverage-matrix 承担）。
2. **扫描范围**：template.json `codeDirs`（无 manifest 时默认 `["src","backend/src"]`），
   扩展名 `.ts .tsx .vue .js .mjs .cjs .java`，排除 `node_modules/dist/target/.vima`。
3. **野生标注**（error，exit 2）：标注的 taskId 不存在于 `docs/tasks/` 任务清单。
4. **虚报嫌疑**（warn；`--strict` 时 exit 2）：`status=done` 且
   `layer ∈ {shared, business}` 的任务在代码里没有任何标注
   （pipeline 任务是流程性任务，天然可无代码落点，不检）。
5. 报告按契约 §6.6 写 `.vima/reports/trace.json`（`stableStringify`，
   markers/wild/unmarked/summary 四段），stdout 输出中文摘要。
6. **Builder 角色模板必须要求写标注**：`templates/admin/workspace/agents/vima-builder.md`
   （init 安装为 `.claude/agents/vima-builder.md`）中写明「每个实现文件头部
   （或核心实现处）必须带 `// @vima <本任务 taskId>` 注释」，
   使标注在生产端强制、在 trace 端验证，闭环成立。

### 验收判据（可跑命令 / 可检条件）

```bash
# 黄金夹具（tests/fixtures/golden/，含 2 个标注文件 + 1 个制造出的虚报 warn）：
node bin/vima.mjs trace                  # exit 0，stdout 报 1 个虚报嫌疑（shared-base）
node bin/vima.mjs trace --strict         # exit 2（虚报在 strict 下阻断）
# 向夹具代码写入 // @vima not-a-task 后：
node bin/vima.mjs trace                  # exit 2，报告 wild 数组含该条
cat .vima/reports/trace.json             # 符合契约 §6.6 schema，字节稳定
```

### 落点

| 类型 | 路径 |
|---|---|
| 命令实现 | `lib/commands/trace.mjs`（C3） |
| 报告格式 | `.vima/reports/trace.json`（契约 §6.6） |
| 单测 | `tests/unit/c3.trace.test.mjs`（C3） |
| 角色模板（标注生产端） | `templates/admin/workspace/agents/vima-builder.md`（安装为 `.claude/agents/vima-builder.md`，D2） |
| 夹具标注样例 | `tests/fixtures/golden/src/api/device.ts` 等（D1） |

## A2 单一真源裁定：任务 `page: PAGE-xx` 引用，不手写组件树

### 动机

PACT 的「分工铁律」（`PACT/pact/SKILL.md` 物料结构一节）：执行态只有
`action-graph.json` 一份真源，「不另设覆盖表，两份执行态必然漂移」；
`pact-book/` 生成物一个字不许手写，`--check` 抓漂移。核心洞察是：
**同一信息存两份，漂移不是风险而是必然**。

v2.0 的任务文件正文里保留了「页面结构 / 组件树」段（设计文档 §9.1），
而页面结构同时又存在于 spec 的 `vima:page` 数据块（§13.2/13.3 的唯一渲染源）——
这正是 PACT 明令禁止的双真源结构：Builder 改哪份？Verifier 对账信哪份？

### 规格

1. 前端页面任务的 frontmatter 增加可选字段 `page: PAGE-xx`（契约 §6.1），
   值必须存在于 spec 的 pages 集合（V-TASK-06，error）。
2. **带 `page` 字段的任务 body 不得含「组件树」或「## 页面结构」手写段**
   （V-TASK-05，error）——页面结构以 spec 的 `vima:page` 数据块 + 渲染出的原型为准，
   任务文件只写业务逻辑、验收清单与维护须知。
3. Builder 开发页面任务时按 `page` 字段回 spec 加载对应 YAML 块（只载当前页，
   契合设计文档 §13.3 的 token 控制），不从任务文件读结构。
4. 前端任务模板 `_template-fe.md` 相应改写：预置 `page:` 字段占位，
   删除组件树章节，加一行指针「页面结构见 docs/spec.md 对应 PAGE 块与
   docs/review/prototype.html」。

### 验收判据

```bash
node bin/vima.mjs validate               # 黄金夹具 exit 0（device-list-fe 带 page: PAGE-01）
# 向 device-list-fe.md body 加入「## 页面结构」段后：
node bin/vima.mjs validate               # exit 2，报 V-TASK-05
# 把 page 改为 PAGE-99 后：
node bin/vima.mjs validate               # exit 2，报 V-TASK-06
grep -L "## 页面结构" templates/admin/planning/_template-fe.md   # 模板本身不含该段
```

### 落点

| 类型 | 路径 |
|---|---|
| frontmatter 字段 | 契约 §6.1 `page`；`lib/model/tasks.mjs` 透传（F） |
| 校验规则 | `lib/commands/validate.mjs` V-TASK-05 / V-TASK-06（C3） |
| 任务模板 | `templates/admin/planning/_template-fe.md`（D1） |
| checklist 镜像 | `templates/admin/planning/validate.checklist.md` 对应条目（D1） |

## A3 轻量冷读门：/go 第二道闸门的可选深模式

### 动机

PACT 的定义性检验是**零知识冷读门**（`PACT/pact/templates/cold-read.md`）：
另起一个全新 agent，只给 `PACT.md`，要求它输出实现计划 + **必须追问的问题清单**——
「每问一个问题就是一处规格漏洞」，跑到追问清单为空为止。
这是唯一能验证「规格自足」的手段：作者自查天然盲于自己的假设，
只有零知识读者暴露得出「懂行的人自然知道、文档里却没写」的缺口。

v2.0 的第二道闸门（设计文档 §7.5 / §13.1 语义抽查）只做「对照 raw/ 原文核对失真」，
查的是**写错了**，查不出**没写**——遗漏的约束在 raw/ 里往往也没有。

### 规格

1. `templates/admin/workspace/commands/go.md`（安装为 `.claude/commands/go.md`）的第二道闸门（语义抽查）
   增加**可选深模式**：用户说「深度校验」或 spec 首次进评审时，主 Agent 追加派发
   一个**零知识 Verifier 子代理**——提示词明确：只读 `docs/spec.md` 与
   `docs/contracts/*.md`，不读 raw/、不读对话历史、不读代码，输出
   「动工前必须得到答复、否则只能靠猜」的问题清单，逐条注明不问的后果。
2. 问题清单由主 Agent 呈给用户逐条裁定：属规格遗漏 → 回 PLANNING 补 spec/契约后
   重跑 `vima validate`；属可推断项 → 在对应 YAML 条目标 `pendingConfirm: true`
   （复用 13.1 信息源分级机制，approve 时统一裁定）。
3. **轻量化边界**（与 PACT 的刻意差异）：不落独立的 cold-read.md 台账、不设
   「追问清单为空才准冻结」的硬门——深模式是 go.md 流程文字里的**可选步骤**，
   默认路径不变，CLI 不为它新增任何命令或状态字段。理由：vima 的规格粒度
   （单 spec + 契约，页级 YAML 块）远小于 PACT 单文件完备规格，硬门的边际收益
   撑不起一道新工序的重量。

### 验收判据

深模式是 Agent 侧流程资产，验收为可检文本条件（e2e 不跑子代理）：

```bash
# go.md 含深模式段落，且明确了零知识约束三要素（只读 spec+契约 / 不读 raw 与代码 / 输出必问清单）：
grep -q "深度校验" templates/admin/workspace/commands/go.md
grep -q "只读 docs/spec.md 与 docs/contracts" templates/admin/workspace/commands/go.md
grep -q "pendingConfirm" templates/admin/workspace/commands/go.md
```

### 落点

| 类型 | 路径 |
|---|---|
| 流程资产 | `templates/admin/workspace/commands/go.md` 第二道闸门段（安装为 `.claude/commands/go.md`，D2） |
| 裁定承接 | spec YAML 条目 `pendingConfirm: true`（契约 §7）+ `vima approve` 阻断（C3） |

## A4 决策留否决项：spec 第八章决策表

### 动机

PACT 把「决策必须留已否决方案」列为区别于文档模板的三机制之一
（`PACT/README.md`），并由 `pact-lint.sh` 第 7 项机检「A5 每条 D-ID 四件套
（选项/结论/理由/已否决）齐全且有实质内容」。价值在于：**理由要能被反驳，
后人看到的是路口而不只是结果**——没有否决项的决策记录，维护期的 Agent/人
会把当年被否决的方案当新点子再提一遍，或在不知情下推翻有意为之的取舍。

v2.0 的 spec 七章结构没有决策记录的位置，PLANNING 期做出的技术与业务取舍
只留在对话里——对话会被压缩，落盘的文件才可信（PACT 协议 A 的同一教训）。

### 规格

1. `docs/spec.md` 由七章扩为**八章**，新增 `## 8. 关键决策记录`
   （V-SPEC-01 的章节标题前缀表随之更新，契约 §8）。
2. 第八章为 markdown 决策表：编号 `D-01, D-02, …`，
   列 = **决策 / 理由 / 已否决方案 / 否决理由**。
3. 机检 V-DEC-01（error）：第八章含 markdown 表格且表头含「已否决方案」列
   （轻量化：不像 pact-lint 那样检查每格「实质内容」——格内空洞交给用户评审，
   机检只保证结构逼迫作者面对这一列）。
4. spec 骨架模板第八章预置表头与一行示例 + 填写提示
   （「写下你放弃了什么、为什么——否决理由与采纳理由同等重要」）。

### 验收判据

```bash
node bin/vima.mjs validate               # 黄金夹具 exit 0（第八章决策表 ≥1 行含已否决方案）
# 删掉夹具 spec 第八章后：
node bin/vima.mjs validate               # exit 2，报 V-SPEC-01
# 把表头「已否决方案」改名后：
node bin/vima.mjs validate               # exit 2，报 V-DEC-01
grep -q "已否决方案" templates/admin/planning/spec.admin.md
```

### 落点

| 类型 | 路径 |
|---|---|
| 校验规则 | `lib/commands/validate.mjs` V-SPEC-01（八章）+ V-DEC-01（C3） |
| spec 骨架 | `templates/admin/planning/spec.admin.md` 第八章（D1） |
| checklist 镜像 | `templates/admin/planning/validate.checklist.md`（D1） |
| 审计视图 | `templates/admin/planning/audit-view.mjs` 可将决策表纳入渲染（C4，可选增强） |

## A5 能力诚实分级：template.json `status` 字段

### 动机

PACT 平台的最高准则之一是完成度诚实：「低层状态不得冒充高层交付」
（`PACT/CLAUDE.md`），README 对 Vima Starter 直接写明 `partial` / `blocked`，
「平台不会把现有空壳能力描述成可稳定生成完整业务系统」。
对用户撒谎的脚手架比没有脚手架更糟：用户用 preview 模板 init 出一套
没有 planning 资产的工作环境，会在 PLANNING 中途才发现框架根本没准备好。

v2.0 已声明「其余四个模板标注 `status: preview`」（设计文档 §3.2），
但没有规定 preview 在各命令中的**行为差异**——标注若不改变行为，就只是装饰。

### 规格

1. `template.json` 必含 `status: "stable" | "preview"`（契约 §6.3）；
   `lib/model/template.mjs` 的 `listTemplates` 透出该字段。
2. `vima create --template <preview 模板>`：**允许创建但打印显著警告**
   （「该模板为 preview：仅有代码骨架，规划体系（planning 资产）尚未就绪，
   vima init 将拒绝在此项目运行」），交互式列表中带 `[preview]` 标记。
3. `vima init` 在 preview 模板项目中：**拒绝执行，exit 4**（前置条件不满足，
   `VimaError('TEMPLATE_PREVIEW', …, { exitCode: 4 })`），输出该模板缺失的
   planning 资产清单与跟进版本说明。骨架可用≠工作流可用，init 是工作流入口，
   必须诚实拒绝。
4. preview 模板的 template.json 可省略 `planning` / `workspace` 字段（契约 §6.3）。

### 验收判据

```bash
node bin/vima.mjs create demo --template cli --no-git --no-install
# exit 0，stdout 含 preview 警告字样
cd demo && node <cliRoot>/bin/vima.mjs init
# exit 4，报 TEMPLATE_PREVIEW，列出缺失资产
node bin/vima.mjs create demo2 --template admin --no-git --no-install && cd demo2 && node <cliRoot>/bin/vima.mjs init
# exit 0（stable 模板不受影响）
node -e "console.log(JSON.parse(require('fs').readFileSync('templates/cli/template.json','utf8')).status)"  # → preview
```

### 落点

| 类型 | 路径 |
|---|---|
| 字段与加载 | `templates/*/template.json`（D3）；`lib/model/template.mjs`（F） |
| create 警告 | `lib/commands/create.mjs`（C1） |
| init 拒绝 | `lib/commands/init.mjs` exit 4（C1） |
| 单测 | `tests/unit/c1.*.test.mjs`（C1） |

## 明确不吸收清单

核心口径：**避免把 PACT 的仪式重量走私回 vima-cli**——PACT 服务「大需求冻结交付」，
每道仪式都有其重量的理由；vima 服务「模板化业务系统快速落地」，
lifecycle + frontmatter + 构建信号已覆盖对应需求，重复吸收只会造出第二套平行工序。

| 不吸收项 | 一句话理由 |
|---|---|
| **30 锚点单文件规格**（`PACT.md` + `<!-- PACT:xx -->`） | vima 的规格真源是 spec 八章 + `vima:*` YAML 数据块，V-SPEC-01 的章节前缀检查已等效承担「锚点存在性」职能，再引锚点体系就是双真源。 |
| **访谈工序 S1**（interview.md 闸门记录） | PLANNING 的对话引导（终点清单 + checkpoint 断点续写）已覆盖需求澄清，落盘台账由 spec/lifecycle 承担，不需要独立访谈工序与其产物文件。 |
| **估算门 S7**（pact-estimate、费率卡、三条线） | 工期/报价承诺不在 vima-cli 的问题域内——它交付的是工作环境与调度闭环，完成度由 /check 按客观信号回答，不对外出数字。 |
| **八级完成度阶梯**（implemented→stable） | vima 的完成度已由任务状态机（pending/running/done/failed/blocked）+ 构建信号 + pipeline 任务分层表达，八级阶梯是面向对外交付承诺的语汇，引入即仪式冗余。 |
| **冻结 + changelog 协议**（S8 冻结、S10-CR 变更六步） | vima 的 spec 不冻结——维护期变更走 13.4 同步闭环（先改 YAML 块 → 重渲染 → 再改代码），漂移由 `--check`/doctor 机检兜底，无需人为冻结仪式与变更台账。 |

## A6 规范执行者阶梯：每条编码规范有唯一机器执行者

### 动机（AI-First 评估的核心结论）

编码规范写进文档 ≠ 被保证：评估时 11 条现行规范仅 3 条有机器执行者，其余靠 Agent
自觉——内置页操作列宽度一条心智规范落出 5 种写法即实证。引入**规范强度阶梯**：
L1 框架吸收（规范消失）> L2 确定性生成 > L3 机械检查 > L4 运行时量测 > L5 文档+人审；
任何规范先判层再入册，每上移一层，AI 出错概率与纠错成本各降一个量级。

### 规格（vima-cli 中的确切行为）

1. **执行者标签**：coding-standards.md 每条规范末尾标注执行者
   （〔L1·框架〕〔L3·hook〕〔L3·validate〕〔L3·trace〕〔L5·verifier〕），
   **无标签规范不允许新增**——无执行者的规范即债，一眼可盘点。
2. **post-write hook 机检扩展**（契约 §14）：幻包名 `@vima/ui` 导入；带 `data-page`
   业务页的 `.vui-page` 类、字面量色值（豁免 `--x:` 自定义属性定义片段）、
   操作列手写字面量 width；VIcon 静态图标名 ∈ vendor ai-manifest icons（含别名）。
3. **V-CODE 代码↔契约对账**（契约 §8）：V-CODE-01 前端 / V-CODE-02 后端，
   作用域自锚定为**带 `@vima` 标注的业务代码**（底座/共享层天然豁免）；
   单向对账防野生接口，实现完整性归 Verifier 逐点判定。
4. **hooks 形态**：node 直跑的 .mjs（settings.json `node .claude/hooks/<name>.mjs`），
   消除 bash 包裹单引号转义陷阱，跨平台。
5. **manifest 同源派生**：ICONS.md（图标唯一依据）与 scaffold components.d.ts
   由 `scripts/gen-from-manifest.mjs` 从 ai-manifest.json 生成（此前手工维护漂移到
   44/63），带「组件名必须存在于包类型出口」防谎言断言，字节确定。
6. **操作列宽度 L1 终态**：组件库 VTable 已内建操作列识别（title「操作」或
   key/customSlot 为 operator）并按行内按钮文案自动计算宽度；hook 拦手写
   width 回潮，规范从「怎么算」退化为「不要写」。

## A9 提问三规则：PLANNING 对话的 frontier 纪律

### 动机（mattpocock/skills 对应机制与其解决的问题）

grilling skill（`skills/productivity/grilling/SKILL.md`）把「问清楚需求」从模糊要求
变成可判定算法：决策构成**设计树**，每轮只问**前置已定、现在能问**的问题（frontier），
逐题编号并附推荐答案；**事实归 agent 自查（不许抛给用户），决策归人**；frontier 为空
才算达成共享理解。它治的是 AI 辅助开发第一失败模式——对齐失败导致的返工。

vima 现状：planning-guide.md 已有终点清单 A–G（终止判据等效）、信息源分级（禁推断）
与 §5 里程碑节奏（先复述再落盘 / 一次一主题 / 答不上记 pendingConfirm），
但**怎么问零约束**——挤牙膏式一问一答浪费轮次、把可从 raw/ 与骨架查到的事实抛给
用户、问前提未定的问题得到会随前提翻覆作废的答案，三种浪费都不违反现行任何一条。
人机对齐评审是 vima 使命句的核心环节，提问质量直接决定对齐成本。

### 规格（vima-cli 中的确切行为）

1. `templates/admin/planning/planning-guide.md` §5（对话确认节奏）新增
   「提问三规则」小节：
   - **先查后问**：能从 `docs/raw/`、骨架代码、底座与共享层能力索引查到的**事实**
     自己查，不抛给用户；提给用户的只有需要拍板的**决策**（取舍、边界、优先级）。
   - **一轮问全＋每问必附推荐答案**：同一主题内把前置已定、现在能问的问题一轮
     编号问全（`❓ Q1 …` + `➡️ 推荐：…（理由）`），不挤牙膏式一问一答。
     推荐答案是给用户裁定的候选——确认后即升级为「用户明确确认」信息源（§3 分级），
     未经确认不落盘（与信息源分级协同，不构成推断落盘的口子）。
   - **前置未定不问**：答案依赖另一个未定问题的，留到前提落定后的下一轮；
     前提被标 `pendingConfirm` 的，其下游问题一并悬置。
2. `vima-planner.md` 工作纪律镜像同一条（与信息源分级在两处镜像的既有做法同构）。
3. **轻量化边界**（与 grilling 的刻意差异）：不落设计树/frontier 台账文件、不设
   「frontier 为空才准进入下一节」的硬门——终点清单 A–G 已是终止判据，本项只约束
   提问行为；与 §0「不做问卷式提问」不冲突（问卷式=无视依赖一次性倾倒全部问题，
   三规则恰是其反面）。CLI 不为它新增任何命令或状态字段。

## A10 同构断言禁令：单测期望值必须来自独立事实源

### 动机

tdd skill（`skills/engineering/tdd/SKILL.md`）反模式清单第二条 **tautological test**：
断言用与实现同构的计算生成期望值（`expect(add(a,b)).toBe(a+b)`、照实现公式手推的
快照、常量等于自身），按构造必过、永远无法与实现分歧——期望值必须来自独立事实源
（已知字面量、手工推演、规格）。这是 AI 生成测试的高发失败模式：模型天然倾向
复述实现来生成期望。

vima 现状：`_template-be.md` 要求 Builder 写 Service 层单测（验收清单 + 开发步骤 5），
A7 又刚把 `mvn test` 从恒绿空门做成真实信号；但 coding-standards 后端节对**断言质量
零约束**——一套同构断言的测试会把 A7 的真实信号无声退化回恒绿假门，且比零测试更难
察觉（tests>0 且全绿）。

（其余两条反模式不吸收：implementation-coupled 由「测 Service 层核心业务规则」的
接口定位部分覆盖；horizontal slicing 在 vima 无对应物——任务本身即竖切单元。）

### 规格

1. `coding-standards.md` 后端节新增一条，按 A6 阶梯判层落 **〔L5·verifier〕**
   （同构判定需语义比对，L3 正则抓不住一般情形；L1/L2/L4 不适用）：
   单测期望值必须来自**独立事实源**——契约的请求/响应示例、spec 第五章业务规则、
   手工推演的已知值；禁止用与实现同构的计算生成期望值；同构断言视同无测试。
2. `_template-be.md` 开发步骤 5 同步措辞（期望值来源提示），使规范在任务模板
   生产端可见（同 A1「生产端强制、验证端对账」的闭环思路，此处验证端为 Verifier
   判定「Service 层单元测试覆盖核心业务规则」清单项时按此规范执行——A6 既有机制，
   不新增验收字段）。

## A11 红绿修复纪律：维护期 bug 先跑红再修复

### 动机

diagnosing-bugs skill（`skills/engineering/diagnosing-bugs/SKILL.md`）的内核是
Phase 1 硬门：必须先有一条**已经至少跑过一次、能对本 bug 变红**的命令（确定性、
秒级、可无人值守），才允许建立假设与改代码；修复完成的判定 = 同一命令转绿。
原文直书：「如果你发现自己在这条命令存在之前就开始读代码建理论——停下，这正是
本 skill 要防的失败。」它治的是 LLM 调试的典型失败模式：读代码空想理论、
改完宣布修好而症状仍在。

vima 现状：DEVELOPING 期的重试环已有红绿结构（Verifier 报告红 → 增量修复 →
复验绿）；但 MAINTAINING 期收到 bug 反馈时无任何纪律——CLAUDE.project.md 工作协议
只写「先定位任务文件再执行修改」。而 A7 恰好已铺齐红绿信号源（前端
runtime-errors.jsonl 与 build:check、后端真实 `mvn test`），缺的只是一条接线协议。

### 规格

1. `CLAUDE.project.md` 工作协议新增一条：维护期修 bug 先把症状固化为一条能**跑红**
   的命令（后端优先写失败测试；前端用 `npm run build:check` 或按
   `.vima/reports/runtime-errors.jsonl` 的上报复现），确认跑红后再动手修复；
   修复完成的判定 = 同一条命令**转绿**（A7 信号源）。复现不了的先向用户要复现路径，
   不凭代码推测下手。
2. **轻量化边界**（与 diagnosing-bugs 的刻意差异）：不吸收其六阶段工序
   （最小化/假设排名/插桩标签/复盘）——vima 的 bug 面主要是业务 CRUD 回归，
   单条红绿命令纪律已覆盖主要失败模式；不新增命令、报告格式或状态字段。

不可靠，对具体物的反应可靠）；**纠偏成本随时序递增**（对话期改一句话 ≈ 0，
approve 后改动走 §13.4 维护闭环）。推论：终点原型只能验收，过程原型才能催化表达。

vima 现状（全部经代码实证，见评估文档 §6.2）：产物层已强于对方（确定性渲染 +
`--check` + manifest 对账闭环 + pendingConfirm 徽标），但**原型只出现在流程终点**
（planning-guide §7 三道闸门收尾），§5 五个里程碑的确认全是文本复述——误解在
文本对齐中积累，集中到最贵的时刻才暴露。技术前提已成立：渲染只前置
V-SPEC-03/04/05、contracts 缺失返回 `[]`，增量渲染无需改渲染层；V-SPEC-03
（四要素非空）+ V-SPEC-05（nav 目标存在）把节拍推向**模块簇粒度**，恰与 §5
逐模块结构零摩擦对齐。同时暴露一个增量节拍会放大的潜伏洞：**approve 前置 2
只查 `fileExists`**（approve.mjs），用户可能对着过期原型 approve。

### 规格（vima-cli 中的确切行为）

1. **逐模块「草→渲→看→定」节拍**（planning-guide §5 里程碑 2 改造）：
   该模块页面块草入 spec 并通过 `vima validate --artifact` 后**立即**
   `vima render-prototype`，请用户在浏览器看该模块每一页并对图反应（顺手裁定页上
   的待确认徽标），反应修正回 YAML 块 → 重渲染，循环直至确认。页面对齐的完成判据
   = **用户在原型上看过并确认**，不是文本复述确认。跨模块 nav 指向尚未草拟页面时，
   把目标页面一并草入本轮（V-SPEC-05 不放宽）。备选形态用「改 YAML → 重渲染」
   时间序列迭代对比，不引入 side-by-side 变体、不引入第二真源（A2 不被触碰：
   用户反应改的是 YAML，永远不是 HTML）。§7 终点评审保留，降级为最后一次全量过目。
2. **approve 前置 2 新鲜度机检**：从「产物文件存在」升级为「产物与当前 spec 渲染
   结果逐字节一致」——render-review.mjs / render-prototype.mjs 各导出新鲜度助手
   （契约 §11：`checkReviewFresh` / `checkPrototypeFresh`，与 `--check` 分支共用
   同一比对实现，原型含 manifest；prototype:false 模板 skip），approve 前置 2
   调用之，漂移 → exit 4 并逐条指名 + 提示重渲命令。前置顺序不变

   （渲染后改 spec 不重渲也能 approve）。
3. **轻量化边界**：不新增命令、文件、状态字段或报告格式；渲染前置校验
   （V-SPEC-03/04/05）不放宽——四要素缺失的页渲出来是残图，误导反应比不渲更糟。

## A13 规格边界机检：业务规则结构化块 + 本期不做清单

### 动机（专题讨论结论，2026-08-13，用户裁定立项）

讨论起点是「快速理解并复刻一个业务系统的核心要素」与「产品经理设计产品的核心要素」。
两轮结论收敛出两条与 vima 直接相关的判断：① 角色/场景/流程覆盖**行为面**，
缺**状态面**（实体状态机）与**约束面**（不变量）——而不变量恰是唯一无法从既有系统
UI 逆推的部分；② 产品经理关注点分**问题层**（为谁解决什么、凭什么是你、成功度量）／
**范围层**（做到哪、不做什么）／**解法层**，vima 终点清单 A–G 全落在解法层，
这是**刻意且正确**的——vima 接的是「用户已决定要做这个系统」之后的活，
问题层不在脚手架问题域，硬塞进去就是约束扩面。

由此定位出的真缺口只有两处，且均满足本文吸收门槛「能落成确定性机检」：

1. **业务规则是 spec 里唯一没有结构化块的必填内容。** 终点清单 E 已要求问到
   「校验规则/状态流转/计算规则/约束条件」，V-SPEC-01 也强制第五章存在，
   但正文是自然语言散文——机器读不到，于是三条链路同时断开：进不了 validate
   （规则写没写、挂没挂到实体上无从判定）；进不了审计视图（人审要在散文里找规则）；
   **进不了 `vima context`**——契约 §6.11 打给 Builder 的包只有任务/契约/页面块/
   组件文档/编码规范五节，业务规则根本不在其中，规则写得再细，真正写代码的子代理
   也看不见。A10 又刚把「单测期望值必须来自独立事实源」指向「spec 第五章业务规则」，
   而被指向的东西没有稳定 ID，引用无处落地。

2. **spec 没有承载「本期不做」的位置。** 八章全是「要做什么」，范围边界只能靠
   「没写就不做」的隐性约定；而生成式模型最擅长的恰恰是补全没写的东西
   （顺手加个导出按钮、加个 remark 字段以后可能用得上）。CLAUDE.md 硬约束
   「防过度设计」在 vima 自身开发上有 §N/A# 反查作抓手，但在**它生成的项目里**
   没有对应物——Verifier 判定实现是否符合 spec 时，只查得了「做的对不对」，
   查不了「做了不该做的」。范围的本质是边界而非清单：只列要做的，边界就是无限的。

### 规格（vima-cli 中的确切行为）

1. **`vima:rules` 块**（spec 第五章，契约 §7）。字段口径经用户裁定为
   **entity 必填 + apis 可选**：`entity` 管语义归属与引用机检，`apis` 管消费端过滤——
   apis 是前后端任务共同的 join key（前端任务经 `page.apis`、后端任务经 `contract.apis`
   都能匹配到同一条规则，不需要两套反查链）。
   ```yaml
   rules:
     - id: RULE-01
       type: validation                                  # validation|transition|calculation|constraint
       entity: Device                                    # 必填，∈ vima:entities[].name
       apis: [POST /api/device, PUT /api/device/{id}]    # 可选；缺省 = 全局规则
       desc: 设备名称 2-50 字符且同名不可重复，违者 40001
   ```
   `type` 四值直接对应终点清单 E 的四类，使「问到了没有」从口头承诺变成可数条目。
   **无 `apis` 的规则视为全局规则**（如「任何删除均为软删除」），注入全部任务上下文。

2. **`vima:non-goals` 块 + spec 第九章**（契约 §7）。落点经用户裁定为**独立第九章
   「本期不做」**——理由是分量对等：non-goals 与第八章「关键决策记录」同为裁定类产物，
   独立成章才不会被概述文字淹没，/go 评审时也更容易定位。spec 由八章扩为九章，
   V-SPEC-01 章节表、validate 常量、骨架、checklist、黄金夹具同步。
   ```yaml
   non-goals:
     - { id: NG-01, desc: 不做移动端适配，本期仅桌面浏览器 }
     - { id: NG-02, desc: 不做数据导出，用户临时用数据库直连应对 }
   ```
   **空清单必须显式写 `non-goals: []`**——块存在且 key 存在才算声明过，
   不允许靠省略块蒙混（对抗的正是模型「没写就当没有约束」的默认行为）。

3. **消费端全链路接线**（CLAUDE.md 硬约束「立项即做透」：块定义了没人消费即半截实现）。
   四个消费端一次接齐：

   | 消费端 | 接法 |
   |---|---|
   | `vima validate` | 新增 V-SPEC-09/10/11（见契约 §8）；RULE-xx/NG-xx 并入 V-SPEC-05 全文档 ID 唯一性检查（复用既有机制，不新增规则） |
   | `vima context` | §6.11 包新增两节：「业务规则切片」（按 apis 交集过滤 + 全局规则，按 id 升序）与「本期不做」（全量注入，Builder 施工前即见红线） |
   | 审计视图 | §13.2 由四视图扩为五视图，新增「⑤ 业务规则」（按 entity 分组、type 徽标、apis 徽标复用 `apiBadge`）；「本期不做」作为范围红线区渲染在审核指引之后；审核指引由四步改五步 |
   | Verifier | 角色模板新增两条判定：带 RULE-xx 的规则逐条核对是否实现（进 §6.9 points）；实现触碰任一 NG-xx 即记 fail（越界） |

   **`vima context` 的过滤口径（确定性，无启发式）**：任务 apis 集合 =
   `task.fm.page` 对应 `page.apis` ∪ `task.fm.contract` 对应契约的全部 apis；
   规则入选 ⟺ 该规则无 `apis` 字段，或 `rule.apis ∩ 任务 apis 集合 ≠ ∅`。
   接口串归一沿用 `normalizeApiRef`（method 大写 + 单空格），与 V-SPEC-07 同构。

4. **边界（刻意不做，防后人当遗漏补上）**：
   - **不引入实体状态机块**。讨论中识别出的「状态迁移图」在 admin 后台管理域尚无第二
     实例支撑（YAGNI，且 `type: transition` 的规则条目已能表达单条迁移约束）；
     真出现需要机检迁移完整性的模板域时再立新增补项。
   - **不引入问题层要素**（成功度量、价值主张、用户画像、优先级排序）。判据是能否落成
     机检规则：non-goals 能（越界可判定），成功度量与价值主张不能，进 spec 只会是摆设。
   - **不为 non-goals 新增 CLI 命令或 lifecycle 状态字段**；越界判定走既有 Verifier
     points 机制（A6 阶梯〔L5·verifier〕，语义比对无法由 L3 正则承担）。

## A14 分栏版面：让人审产物画得出真实二维布局

> 创建日期：2026-08-13
> 来源：sustain-v3 实战——48 个业务页面中 9 个（19%）的真实版面是多列结构
> （三列工作台、`1fr/320px` sticky 汇总栏、`260px/1fr` 主从、三栏拖拽设计器、两栏会话工作台），
> 而 `layout` 是**一维词序列**，任何渲染器都画不出二维结构。评审时人只看到
> `cards → tabs → table` 三个词，看不出这是三栏，也就无法确认版面是否对。

### 问题

`vima:page` 的 `layout` 只能表达「区块的先后」，不能表达「区块的并列」。后果有三层：

1. **审计视图**只能把区块渲染成词条 chips，人读不出版面；
2. **线框原型**只能纵向平铺，多列页面全部塌成单列，与真实形态不符；
3. 评审通过后 Builder 拿到的也是一维序列，**分栏信息只能靠散文补**，机检覆盖不到。

### 决策：加可选键 `regions`，`layout` 保持不动

```yaml
layout: [toolbar, form, cards, table, pagination]   # 仍是全部区块的扁平序列，不变
regions:                                            # 纵向若干「带」
  - { blocks: [toolbar] }                           # 全宽带
  - columns:                                        # 分栏带
      - { name: 作答区,   width: 1fr,   blocks: [form] }
      - { name: 实时计分, width: 320px, blocks: [cards] }
  - { blocks: [table, pagination] }                 # 全宽带
```

四条设计约束：

- **两级：带 + 列，不做递归嵌套**。初版设计成「一行 N 列」，落 sustain-v3 时立刻被证伪——
  9 个多列页面里只有 2 个是纯三栏，其余 7 个都是「工具栏全宽 / 中间两栏 / 底部表格全宽」，
  必须有「带」这一层。两级已覆盖全部实战形态；真出现列内再分行的需求再谈，现在不建（YAGNI）。
- **`layout` 不动**。它仍是校验（V-SPEC-04）、manifest、任务点计数、`data-block` 对账的唯一口径，
  因此本增补对既有台账**零影响**。
- **完全可选、向后兼容**。不声明 `regions` 的页面**结构不变**（不产生分栏容器）、
  manifest 也不写该键；单列页面无需声明。注意渲染产物的 HTML 会因样式表新增分栏样式而
  变动一次字节——这是任何渲染器改动的固有结果，`--check` 会如实报漂移，重渲即可。
- **防两处漂移**：V-SPEC-12 强制 regions 铺开后的区块多重集等于 `layout`，
  避免「改了 layout 忘了改 regions」造成两份版面事实。

### 机检

新增 **V-SPEC-12**（error，仅在页面声明 `regions` 时触发）：
每项须为映射；`blocks` 非空且词 ∈ 布局词表；`width` 匹配 `^\d+(\.\d+)?(px|fr)$`（缺省 `1fr`）；
regions 铺开后的区块多重集 == `layout`。规则挂在 `validatePages` 里，
因此 `render-review` / `render-prototype` 渲染前同样拦截。

### 渲染

- **线框原型**：声明 regions 的页面按列渲染——`<n>px` 为固定列、`<n>fr` 为按比例弹性列，
  每列带列名与列宽标注；窄屏（≤900px）落回纵向堆叠。
- **审计视图**：原「布局区块序列」词条 chips 升级为**版面草图**——
  分栏页按列画、单列页纵向堆叠，每条区块显示中文名 + 原词；词序列降为副行保留机器口径。

### 落点

| 类型 | 路径 |
|---|---|
| 契约（改前必读） | `docs/internal-contracts.md` §6.7 manifest / §8 规则表 |
| 内核 · 校验 | `lib/commands/validate.mjs`（`REGION_WIDTH` + V-SPEC-12，挂在 `validatePages`） |
| 规范骨架 | `templates/admin/planning/spec.admin.md`（第三章填写提示补 regions） |
| 校验清单镜像 | `templates/admin/planning/validate.checklist.md` |
| 渲染器 | `templates/admin/planning/prototype.mjs` + `prototype.template.html`（按列渲染）；`audit-view.mjs` + `review.template.html`（版面草图） |
| 单测 | `c4.render`（分栏渲染 + 无 regions 时字节不变） |

### 不做

- 不扩布局词表（`steps` / `chart` / `timeline` 等仍缺，属另一件事）；
- 不引入嵌套分栏、不引入行列混排、不引入响应式断点声明——需求未出现，出现再说。

## A15 命令语义对调：`vima upgrade` 升级 CLI 自身，`vima update` 更新项目产物

> 创建日期：2026-08-13
> 来源：用户提出「upgrade 升级自身、update 更新产物」的命名直觉，经裁定立项（破坏性对调路线）。

### 问题

v2.0–v2.1 有两个缺口，一个是缺能力，一个是名字被占错了位：

1. **CLI 没有自升级能力**。全仓没有任何联网查版本或执行安装器的代码；CLI 自身版本只在
   `create.mjs:readCliVersion()` 被读出来写进 `manifest.vimaVersion`。用户想升级 vima 本体，
   只能自己记住 `npm i -g @vima-tech/cli@latest`——而恰恰是脚手架的用户最不该记这种命令，
   他的日常入口是 `vima`，不是 npm。
2. **`upgrade` 这个名字被产物更新占着**。§4.5 的 `vima upgrade` 做的是「用新模板源刷新项目里的
   vima 生成物」，语义上是 update；而读到 `upgrade` 的第一直觉是「把 vima 升到新版本」。
   名字占错位，自升级能力就没有自然的落点。

### 决策：对调，不共存

- `vima update` = 产物更新（v2.0–v2.1 `vima upgrade` 的全部行为原样承接，逻辑一行不改）；
- `vima upgrade` = 升级 CLI 自身。

**不做 `upgrade` → `update` 的自动转发**。两个命令的选项在新语义下天然兼容（见「过渡兼容」），
转发只会制造一个长期存在的歧义分支。

### 规格（`vima upgrade` 的确切行为）

**1. 查最新版本**：`fetch https://registry.npmjs.org/@vima-tech/cli/latest` 取 `.version`。
Node 20 全局 fetch，零运行时依赖不破；5 秒超时（`AbortSignal.timeout`）。
请求失败 / 超时 / 响应无 version → `REGISTRY_UNREACHABLE`（exit 2），报文含 registry URL 与
手动升级指令——**不静默降级为「已是最新」**（查不到版本与已是最新是两件事）。

> 测试逃生舱：环境变量 `VIMA_UPGRADE_LATEST` 非空时直接采信其值并跳过请求，
> 用于兑现契约 §13「单测不得依赖网络」。

**2. 识别安装方式**（只看 `ctx.cliRoot` 的路径与文件存在性，不执行外部命令探测）：

| 判据（自上而下，首个命中即定） | kind | 可自升级 |
|---|---|---|
| `<cliRoot>/.git` 存在 | `source` | 否——源码 / `npm link` 开发态，提示 `git pull` |
| 路径含 `_npx` 段 | `npx` | 否——npx 每次已取最新，提示无需自升级 |
| 路径含 `node_modules/.pnpm` 或 `pnpm` 段 | `pnpm` | 是 → `pnpm add -g @vima-tech/cli@latest` |
| 路径含 `.bun` 段 | `bun` | 是 → `bun add -g @vima-tech/cli@latest` |
| 其余 | `npm` | 是 → `npm install -g @vima-tech/cli@latest` |

**3. 默认只检查不安装**。裸 `vima upgrade` 输出「当前版本 / 最新版本 / 安装方式 / 升级指令」后
exit 0。理由：这是全仓**唯一会改 cwd 之外文件**的命令，改机器全局状态必须显式授权。

**4. `--yes` 才执行安装**：`spawnSync(<pm>, [...], { stdio: 'inherit' })`；安装器非零退出 →
`INSTALL_FAILED`（exit 2）。kind 不可自升级（`source` / `npx`）时 `--yes` →
`UPGRADE_UNSUPPORTED`（exit 4）；同一情形下**不带** `--yes` 只是报告，exit 0
（开发者在源码仓库里跑 `vima upgrade` 看版本不是错误）。

**5. 已是最新**：打印并 exit 0，带 `--yes` 也不执行安装（不做无谓的安装器往返）。

**6. 过渡兼容（一个版本周期）**：

- `--dry-run` 在新语义下 =「显式声明只检查」= 默认行为，接受但无额外行为。于是 2.x 用户的
  `vima upgrade --dry-run` 与裸 `vima upgrade` 都**不报错**，只会看到版本报告；
- cwd 存在 `.vima/manifest.json` 时，输出末尾追加一行迁移提示，指向 `vima update`——
  老用户在项目里跑旧命令，一定看得到正确去处；
- 老用法里唯一有实际动作差异的是 `vima upgrade --yes`：旧语义下无行为（实现恒非交互），
  新语义下会真装。README 与 §19.3 从未把 `--yes` 列入示例，风险面小且动作可逆（只是升 CLI）。

### 验收判据（可跑命令）

```bash
# 1. update 完全承接旧行为（在已 init 的项目中）
node bin/vima.mjs update --dry-run; echo $?                       # → 动作表，0

# 2. 自升级默认只报告；源码态（本仓库 cliRoot 有 .git）拒绝安装
node bin/vima.mjs upgrade; echo $?                                # → kind=源码/开发态，0
VIMA_UPGRADE_LATEST=99.0.0 node bin/vima.mjs upgrade --yes; echo $?   # → 4 UPGRADE_UNSUPPORTED

# 3. 已是最新时不装
VIMA_UPGRADE_LATEST=$(node -p "require('./package.json').version") \
  node bin/vima.mjs upgrade --yes; echo $?                        # → 0

# 4. 老用法不报错
node bin/vima.mjs upgrade --dry-run; echo $?                      # → 0
```

### 落点

| 类型 | 路径 |
|---|---|
| 设计真源 | `docs/design/vima-cli-design-v2.md` §4.5 标题与正文改指 `vima update`；§19.3 更名；新增 §19.13 `vima upgrade` |
| 契约（改前必读） | `docs/internal-contracts.md` §2 文件所有权、§3.1 错误码表（+3 条）、§12 增补项表、§13 e2e 链路、§14 裁定补遗 |
| 内核 · 产物更新 | `lib/commands/update.mjs`（由 `upgrade.mjs` 整体更名，逻辑不动） |
| 内核 · 自升级 | `lib/commands/upgrade.mjs`（新写） |
| 路由与帮助 | `lib/cli.mjs`（COMMANDS 表：改写 upgrade 条目 + 新增 update 条目） |
| 提示语 | `lib/commands/init.mjs`（ALREADY_INIT）、`lib/commands/doctor.mjs`（受管文件缺失修复提示） |
| 单测 | `tests/unit/c1.update.test.mjs`（更名承接）、`tests/unit/c1.upgrade.test.mjs`（新写自升级）、`tests/cli.test.mjs`、`tests/e2e.test.mjs` |
| 文档 | `README.md` 命令表与偏离表、`CHANGELOG.md` |

### 不做

- **不做自动检查更新**（跑任意命令时后台探测新版）——那要引入缓存文件、静默网络请求与关闭开关，需求没提；
- 不做版本回退（`vima upgrade --to <version>`），不做 JSON 输出；
- 不做 `upgrade` → `update` 的自动转发（见「决策」）；
- 不改 `.vima/manifest.json` 的 `vimaVersion` 语义——它仍只记录「产物由哪个 CLI 版本生成」，由 `vima update` 维护。

## A16 多端应用模型：一个后端 × 多个前端（端册 apps）

> 创建日期：2026-08-13
> 来源：多前端支持专题讨论（营养诊疗系统「院内管理后台 + 患者端小程序」场景），
> 用户裁定立项——「一个后端给多个前端提供接口」是最普遍形态，优先级高于多后端/微服务；
> 选型四项（患者端 mp-native / vendored Vant Weapp / N=1 根布局 / consumers 必填）同日拍板。

### 动机

v2.1 的模型里没有「端」维度——一个项目 = 一个模板 = 一份 spec = 一个前端目录。
立项前评估查明九处单端假设，多前端不是配置问题而是模型缺口：

1. templateId 在 manifest/lifecycle 均为单标量，`readProjectTemplateId` 返回单字符串；
2. scaffold 只有「项目根=前端、backend/=后端」两个落点，第二个前端无处安放；
   且 `create --force` 重跑会无条件重写 manifest（清空 files/templateId，端册时代即数据丢失）；
3. spec 无端维度：PAGE 无归属键，第六章权限是单一后台菜单树；
4. 布局词表 7 词 + 原型外壳均为桌面后台专用（V-SPEC-04 error 级——小程序页面**无法表达**）；
5. 任务 `side` 只分 frontend/backend，不分哪个前端；
6. V-CON-03 假设一前端（每 module 一对 fe/be 任务即闭环）；
7. V-CODE-01/02 扫描路径写死 `'src'`/`'backend/src'`（不读 codeDirs）——第二前端**静默零覆盖**，
   看起来在项目里、validate 全绿，实则野生接口一个查不出；
8. guard-shared.mjs 保护面是硬编码字面量，第二前端共享层不设防；
9. `vima context` 给任何前端任务注入的都是后台组件文档（docs/ui-framework/ 单套）。

绕行方案（双项目 + endpointAnchor / 手工塞 apps/）都以「假覆盖」或「真源两处漂移」收场，
故立项为一等公民支持。三条设计原则（本增补项全部规格的判据）：

1. **后端单数、前端复数**——`backend/` 唯一，不建模多后端；契约提供方、V-CODE-02、
   后端共享层全部不动。
2. **端册（apps roster）是唯一真源**——「有哪些端、各在哪个目录、什么形态」只在
   `.vima/manifest.json` 声明一次，全部消费方（validate/trace/guard/context/渲染器/doctor）
   经 `resolveApps` 读声明、零硬编码字面量（治共享层目录「四处口径不一」的病根：
   上次是四处抄写，这次是一处声明）。
3. **多端必显式**——端数 >1 时页面、菜单、任务、契约接口一律显式声明端归属，
   缺省即 error（A13「对抗模型没写就当没有」哲学在端维度的复用：漏标端归属的产物 =
   没想清楚给谁用的产物）。**单端项目一切端键可省略、行为与现状逐字节一致**——
   多端是同一模型的 N>1 取值，不是第二套体系。

### 规格（vima-cli 中的确切行为）

1. **端册**（契约 §6.4 manifest v2 / §6.3 template.json / §5 `resolveApps`）。
   manifest `schemaVersion` 升 `"2"`，新增 `apps[]` 与 `backend`：

   ```json
   { "schemaVersion": "2", "templateId": "admin",
     "apps": [
       { "id": "admin",   "name": "院内管理后台", "kind": "admin-web",
         "dir": "apps/admin",   "codeDir": "src",
         "sharedDirs": ["src/components", "src/utils", "vendor"] },
       { "id": "patient", "name": "患者端",       "kind": "mp-native",
         "dir": "apps/patient", "codeDir": "src",
         "sharedDirs": ["src/components", "src/utils"] } ],
     "backend": { "dir": "backend",
       "sharedDirs": ["src/main/java/com/nutri/config", "src/main/java/com/nutri/security"] } }
   ```

   - `sharedDirs` 一律**相对各自 `dir`**（换目录不失效）；create 写入时 `{{projectPkg}}`
     等变量已渲染为具体路径。
   - **布局规则（用户裁定）**：N=1 前端落项目根（`dir: "."`，存量零迁移）；N≥2 创建即
     `apps/<id>/`；后补端（`vima app add`）到根布局项目允许混合布局——目录是**数据**
     （`dir` 字段），消费方无感。
   - v1 manifest（无 `apps` 键）由 `resolveApps` 合成默认单端端册（admin：`dir "."`、
     `codeDir "src"`、现行 sharedDirs 字面量），`vima update` 迁移为 v2。
   - template.json 以 `apps[] + backend` 取代顶层 `scaffold`/`sharedDirs`/`codeDirs` 三键
     （loader 兼容旧形态）；`planning.kinds` 声明每个 kind 的
     `{ layoutVocab, regions, shell, status }`，是词表/分栏能力/原型外壳/kind 成熟度的
     **唯一真源**（V-SPEC-04/12 与渲染器同源于此，词表从 validate 代码常量迁出）。
     kind `status: preview` = PLANNING 全流程可用、create/app add 跳过骨架拷贝并显式警告
     （A5 能力诚实分级下推到 kind——设计先行，骨架后到，不两张皮）。

2. **规格层**（契约 §7）。单一 `docs/spec.md` 不拆分——实体、规则、契约、跨端流程是
   系统级真源，拆文件即拆掉「患者端下单 → 医师后台确认」跨端叙事的完整性。端归属靠块内键：
   - `vima:page` 新增 `app` 键（多端必填 ∈ 端册；单端可省 = 唯一端）；PAGE/MENU 等
     **ID 全局唯一不变**（正则、锚点、href 全不动）。
   - `vima:menus` 每条新增 `app` 键；mobile 端的「菜单」= tabbar（3–5 项），同一模型
     两种外壳投影。`menu.page` 必须与 `menu.app` 同端。roles 结构不动（role.menus 可跨端
     ——医师可同时有后台与医师端；V-SPEC-06 逐菜单检查天然按端成立）。
   - **`action: nav` 必须同端**（小程序页面无法「导航」到桌面后台页）；跨端交接只能表达在
     `vima:flow`（step 的端由其 page 推导，flow 不加新键）。
   - `regions`（A14）按 kind 门控：`admin-web` 允许；mobile 端声明即 error（手机单列，
     多栏带是规格谎言）。
   - 端覆盖闭环：端册每个 app 在 spec 中 ≥1 个页面（防「入册未设计」）。

3. **契约层**（契约 §7 vima:contract）。api 新增 `consumers` 键：

   ```yaml
   apis:
     - { method: POST, path: /api/app/appointment,        consumers: [patient] }
     - { method: GET,  path: /api/admin/appointment/list, consumers: [admin] }
   ```

   - **多端项目每个 api 必填非空 `consumers` ⊆ 端册**（用户裁定：安全缺省关闭——
     患者端能不能调 `/api/admin/**` 正是一后端多前端的核心安全接缝）；单端可省 = 唯一端。
   - **两级机检**：spec 级——app=X 的页面 `apis` ⊆ consumers 含 X 的接口集（V-CON-07，
     越权引用设计期拦截）；代码级——V-CODE-01 扩展（越权调用，见 6）。与 V-SPEC-07 +
     V-CODE-01 既有「规格/代码双保险」同构。
   - 新增契约纪律一条（落设计 §9.5）：**不同端需要不同数据形状 ⇒ 必须是不同端点**。
     不建模 per-consumer response 变体（复杂度爆炸，且后端按端出 DTO 本就是防字段
     误泄的安全实践）。契约文件组织不变：仍按 module 一文件，一个 module 可同时服务多端，
     端点单一真源不拆。
   - V-CON-03 升级为「谁消费谁承接」：每 module ≥1 backend 任务；且对每个消费该 module
     ≥1 个 api 的端，须有 ≥1 个该端的 frontend|fullstack 任务经 `contract` 字段引用它。

4. **任务与调度**（契约 §6.1/§9）。frontmatter 新增 `app` 字段：多端项目
   side=frontend|fullstack 必填 ∈ 端册；side=backend **禁止携带**（出现即 error）；
   带 `page` 的任务 `task.app` 必须 == 该页归属端。**plan 批次引擎零改动**——
   不同端任务目录天然不相交，依赖分层 + conflictsWith + 批内 ≤5 并行直接成立；
   共享层每端各一任务、批 0 照旧串行；联调流水线任务改为每端一个（planning-guide
   指示，非引擎改动）。sync 的 tasks/README 批次视图加「端」列；/check 完成度按端分行。

5. **人审产物**（契约 §6.7/§11）。
   - **原型按端各渲染一份** `docs/review/prototype.<appId>.html`（单端保留旧名
     `prototype.html`）：admin-web 沿用桌面侧栏外壳；mp-native 渲染 375px 手机框 +
     底部 tabbar（取该端 vima:menus，链至 `#page-PAGE-xx`）。语义占位线框体系复用，
     词表换 kind 词表。manifest 单文件不变，顶层改 `apps: { <appId>: { pages } }`
     （统一新形态，N=1 亦然；verifier/approve/post-write 对账同步）。
   - **审计视图仍单文件**：五视图内按端分组（角色×菜单矩阵按端分段、页面详情按端分章、

## A17 /go 批间连续性：预算按任务计数 + 检查点提交授权口径 + 合法停点白名单

> 创建日期：2026-08-13
> 来源：真实项目开发期用户反馈「每个批次执行完即阻塞，需再次输入 /go 才续跑，
> 无法自动化推进」；排查定位三个停顿源（见「问题」），经用户裁定按排查建议落地。

### 问题（三个停顿源）

1. **会话预算的批次计数在串行批下过早触发**。go.md 规定「单次 /go 最多推进
   3 个批次或 8 个任务（先到为准）」，而批次计划里 shared 与 pipeline 任务
   **每任务单独一个串行批**（§9 批次算法 / §10.7 写令牌）——共享层阶段
   3 个批次 = 只推进 3 个任务即停；业务批 ≤5 任务，2 批即触 8 任务上限。
   预算防的是编排者上下文过载（§10.2），其成本与**任务数**成正比（每任务一份
   Builder 摘要 + 一份 Verifier 报告，重试翻倍），与批次数无关：
   批次数是上下文成本的坏代理指标，且专门惩罚串行批。
2. **批次检查点提交与环境级提交禁令正面冲突**。go.md 要求每批完成后
   `git commit -m "vima: batch <N> completed"` 形成回滚点，而 Claude Code 的缺省
   纪律与常见的用户全局规则都是「未经用户明确要求不得提交」。主 Agent 每批结束
   都撞一次矛盾指令，典型行为是停轮征询——这正是「每个批次执行后阻塞」的直接
   原因。缺的不是机制而是**授权口径**：没有任何文字说清「用户输入 /go」是否
   构成对检查点提交的明确要求。
3. **只有正向停点、没有反向纪律**。go.md 只定义了「预算达标后停」，没写
   「预算未达标不得停」——主 Agent 派发完一批、输出阶段总结后自然结束回合，
   没有文字资产拦截这种停顿（§10.2 自己也只提供「用户中断后再 /go」的兜底）。

### 规格（全部为工作区文字资产与设计文案语义，零文件格式/模块接口变更）

1. **会话预算改为单一任务计数**：单次 /go 最多推进 8 个任务，批次数不设上限；
   达标后落盘全部状态、提示用户再次输入 /go 续跑。预算本身保留——编排者上下文
   过载的风险真实存在，§10.2 对策表照旧。重试不另计（属同一任务的处理成本，
   8 任务上限本就是按含重试摘要的保守余量取的）。
2. **检查点提交授权口径**：用户输入 /go 即构成对本次运行**全部批次检查点提交**的
   明确授权，主 Agent 不逐批征询。若环境规则/权限仍拒绝提交：跳过本次 commit、
   在批次报告中注明「未形成回滚点」，**继续调度下一批**——提交受阻不是停点
   （回滚点是增强件，不是推进的前置条件）。宪法（CLAUDE.project.md 工作协议）
   同步声明一行，口径不依赖主 Agent 是否完整读过 go.md。
3. **合法停点白名单（反停顿纪律）**：批次之间不得结束回合等待用户。/go 唯一
   允许的停点：① 会话预算耗尽；② 全部任务达终态（无 pending/running）；
   ③ 确定性前置失败或闸门阻断需用户处置（lifecycle 缺失、vima plan 依赖环、
   三道闸门未过、断点续跑中 failed 任务裁定）；④ 用户主动中断。
   批次完成、检查点提交受阻、sharedChangeRequest 补偿批插入均不是停点——
   同一回复内继续派发下一批。

### 验收判据（可 grep 条件，d2 防漂移断言镜像）


## A18 批次调度效率：任务负责接口集 + 同层流水线 + 并行度可配 + /go 续跑器

> 创建日期：2026-08-13
> 来源：sustain-v3 实测评估（`docs/design/batching-efficiency-assessment.md`），
> 用户反馈「每批几十个接口、单批半小时以上、每批都要重输 /go」。
> 该评估触发了 A17「不做」清单第 2 条自留的重开条件（「待真实项目验证 8 任务/次的
> 手动续跑节奏仍不可接受时另行立项」）。两项口径由用户 2026-08-13 拍板：
> 检查点提交走 `/go --commit` 显式授权；续跑走 Stop hook 确定性续跑器。

### 问题（实测，非推断）

1. **瓶颈是不均衡造成的空转，不是工作量也不是构建**。实测 `npm run build:check`
   2.82s、`./mvnw -o -q compile` 1.34s——工具开销可忽略。而按 `@vima <taskId>` 标注
   归属统计的 25 个已完成任务共 38 629 行（≈502k token、≈120 分钟单线程生成量），
   单任务最大 `followup-api-be` 4527 行 / 81 文件 / ≈14 分钟，是同批最小任务的 7 倍。
   子代理内部严格串行，批次时长取批内最大值 ⇒ 实测三个业务批的并行槽空转率
   **52% / 54% / 53%**。四个批的时长之和 50.6 分钟，而 120÷5 的均衡理想值是 24 分钟。
2. **任务粒度 = 契约文件粒度，且无规模上限**。`_template-be.md` 只写「建议
   `<模块>-api-be`」，全仓无任何一条文字资产给任务规模设界。
3. **前端任务默认依赖对应后端**（planning-guide 第 5.4 步默认值），而前端验收清单
   只有「字段与契约一致 + `npm run build:check`」，无任何后端运行时依赖——
   契约先行体系里的假依赖，把 18 个批次锁成「4 批后端 → 10 批前端」两段式。
4. **`MAX_PARALLEL = 5` 硬编码**（`lib/commands/plan.mjs`），无 CLI/配置入口；
   设计 §10.2 给的理由「避免资源争抢与输出混乱」无实测依据。
5. **同层子批白走一倍轮次**。因并行度上限切出的同层子批之间没有任何依赖
   （§9 切批算法只在同一 level 内贪心装桶），却仍按「本批 Builder 全回 → 本批
   Verifier 全回 → 下批」串成 2N 轮。
6. **会话预算的保护假设不成立**。§10.2 对策表写「续跑即新会话」，但实际用户是在
   **同一会话**里重输 `/go`——上下文根本没重置，预算只制造了摩擦，没起到保护作用。
   且每任务的上下文成本本身无界（实测磁盘 Builder 报告 7–13KB/份）。
7. **批次检查点提交与用户全局禁令正面冲突**。A17 判定「/go 即授权」，但用户全局
   `CLAUDE.md` 的「禁止自动提交（必读·不可绕过）」优先级更高，实测 sustain-v3
   至今 **0 个提交**——20 个任务、251 个接口没有任何回滚点，且每批刷一行
   「未形成回滚点」噪声。

### 决策：七条规格

**1）任务负责接口集 `apis`（新增可选 frontmatter 字段）+ 规模上限机检**

拆分大任务会引入一个原本不存在的失败模式：同一契约的多个子任务之间**漏实现 /
重复实现**。因此拆分能力与其完整性机检必须同批落地（「立项即做透」）。

- `apis`：可选字符串数组，条目形如 `GET /api/foods`；缺省语义 = 本任务负责该契约
  **全部**接口（向后兼容，存量任务零改动）。
- **V-TASK-11**（warn）：`layer=business` 且 `side ∈ {backend, fullstack}` 的任务，
  负责接口数 > **10** → 提示按子域拆分。判据取 `apis` 长度（声明时）或契约条目数。
- **V-TASK-12**（error）：`apis` 每条归一后须 ∈ 该契约 apis；同一契约下 side=backend
  的任务，声明了 `apis` 的两两不得相交（防重复实现）；若该契约下全部 backend 任务
  都声明了 `apis`，其并集须等于契约全集（防漏实现）。
- **`vima context` 按 `apis` 切片契约**：声明时上下文包只保留本任务负责接口的人读
  小节（`## <METHOD> <path>`）与机读块条目，其余章节原样保留——直接压缩 Builder 上下文。
- **拆分判据是「均衡」不是「小」**：批次时长取批内最大值，一个 14 分钟任务配四个
  3 分钟任务等于浪费 54% 并行槽。拆分应按**子域（实体组）**切，使每个子任务独占
  自己的 Entity/Repository/Service/Controller；确有共享文件时用 `conflictsWith` 登记。

**2）前端任务默认只依赖 `shared-base`**

planning-guide 第 5.4 步默认值对调：默认前端仅依赖 `shared-base`（契约先行的必然
推论——前端的事实来源是已过三道闸门的契约，不是后端产物）；确需依赖后端产物的
（如需要真实种子数据的联调页）逐个显式说明理由。`_template-fe.md` 注释同步。

**3）同层子批流水线化**

- `batch-plan.json` 每个批次增 `level` 字段（shared/pipeline 批的 level 取其拓扑序号，
  business 批取其依赖层号）——让主 Agent 能**确定性判断**两个批是否同层，不靠推断。
- go.md 允许：同一 `level` 内相邻子批之间，「上一子批的 Verifier」与「下一子批的
  Builder」在同一轮回复内派发。跨 level、跨 layer 的批次边界仍是硬屏障。
- 校验强度不变——每个任务仍走完整的 Builder → 独立 Verifier，只是无依赖子批的轮次重叠。

**4）并行度可配**

`vima plan --max-parallel <N>`（整数 1–10，默认 **8**），写入 `batch-plan.json` 的
`maxParallel` 字段供追溯。默认值 5→8 与原值 5 一样是取值判断而非实测结论，
故同时提供配置入口，允许按项目实测调整。

**5）回传摘要上限 + 会话预算放大**

- `vima-builder.md` / `vima-verifier.md` 硬性规定：返回主 Agent 的摘要 **≤ 15 行**
  结构化结论，明细一律落 `.vima/reports/<taskId>-*.json`（本就要求落盘，此处只是
  把「回传」与「落盘」的职责切开）。
- 在此前提下会话预算 8 → **24** 个任务/次。顺序纪律：**先有摘要上限，才能放大预算**
  ——A17 对编排者上下文过载的担忧真实存在，放大阈值的前提是把每任务的上下文成本
  从不受控变成有界。
- 预算耗尽的续跑提示改为「**先 `/clear` 再 `/go`**」，让「续跑即新会话」的设计假设
  真正成立（问题 6）。

**6）`/go --commit` 显式提交授权**（用户裁定）

- 不带 `--commit`：主 Agent **完全不碰 git**，批次报告不再输出「未形成回滚点」噪声。
- 带 `--commit`：即构成对本次运行全部批次检查点提交的明确授权，逐批
  `git commit -m "vima: batch <N> completed (<k> tasks)"`，不逐批征询；
  被环境规则拒绝时跳过并在报告注明，**继续调度**（保留 A17「提交受阻不是停点」）。
- A17 的「/go 即授权」口径由本项取代——授权点必须显式可见，才不与用户全局禁令冲突。

**7）Stop hook 确定性续跑器**（用户裁定；显式推翻 A17「不用 Stop hook」）

A17 否决 Stop hook 的理由是「hook 无法区分合法停点与非法停顿，一刀切会击穿合法停点」。
该理由成立的前提是 hook 只能猜。**让主 Agent 把停因写成机读文件，hook 就不必猜**：

- 主 Agent 在每次结束回合前写 `.vima/go-state.json`（§6.12）：
  `{ schemaVersion, phase, stopReason, consecutiveResumes, updatedAt }`，
  `stopReason ∈ {budget, terminal, gate, user, in-progress}`。
- `.claude/hooks/go-continue.mjs`（Stop hook）读该文件：
  - `stopReason ∈ {budget, terminal, gate, user}` → 放行停轮（合法停点白名单，A17 原表）；
  - `stopReason = in-progress` → **阻止停轮并注入**「继续派发下一批（合法停点见 go.md）」；
  - 文件缺失 / 解析失败 / `phase ≠ DEVELOPING` / 修改时间早于本次会话 → **一律放行**
    （「防误不防恶意」，与既有两个 hook 同口径，绝不误伤非 /go 场景）；
  - `consecutiveResumes` ≥ **5** → 放行并提示（防死循环兜底；每次成功推进任务后由
    主 Agent 归零）。

**8）新增受管文件的交付路径修复**（本项落地时暴露，同批修复）

A18 是 update 机制存在以来第一次新增受管文件（`hooks/go-continue.mjs`），暴露出三处缺陷：

- `vima update` 覆盖 `settings.json`（已引用新 hook）却**拒绝安装新增文件**，产出一个
  「配置指向不存在文件」的破损状态；其提示的补救办法 `vima init --force` 又会**重写
  lifecycle**，把 DEVELOPING 打回 PLANNING 并丢掉 taskStats/phaseHistory/tasksApproved。
- 顺带查出 `vima init` **整体覆盖 manifest**，把 create 写入的端册（`apps`/`backend`）连同
  schemaVersion 2 一起清掉——A16 多端项目在 create → init 的正常路径上就会失去端册
  （实测 doctor ⑪ 因此误报「代码目录不在位」）。

修复：① manifest 增 `install: {minimal, skipScan}`（init 写入；旧 manifest 按已记录文件
确定性反推——无 `docs/` 条目 = minimal，有 `docs/` 无 `docs/ui-framework/` = skip-scan——
并由 update 固化写回）；② update 对模板新增文件走同一套三方比较：磁盘无 → 安装并登记，
磁盘有且等于模板源 → 采信登记，磁盘有且不同 → 写 `.vima-new` 人工合并；
③ init 改为**合并写 manifest**，保留既有 `apps`/`backend`/`schemaVersion`；
④ init **不重写已存在的 lifecycle**，保留并提示「保留既有状态（未重置）」——
`--force` 的语义是重建生成物，不是清空进度。

### 不做

- **不拆契约文件来实现任务拆分**——契约是模块级唯一事实来源，拆成子契约会让

  代价大于收益。任务侧用 `apis` 表达归属即可，契约文件维持模块粒度。
- **不做跨会话自动续跑驱动**（自动开新会话再 `/go`）——仍需以 Claude Code 会话为
  操作对象的外部驱动器，超出工作区文字资产层与 `lib/` 平台中立边界。
  本项的 Stop hook 只在**同一会话内**阻止非法停顿，不制造新会话。
- **不删会话预算**——编排者上下文过载的风险真实存在，本项只在「摘要有界」的前提下
  放大阈值，并把续跑提示改成 `/clear`，让预算真正发挥保护作用。
- **不合并 Builder 与 Verifier 角色**——省一轮的代价是失去独立视角，而 sustain-v3 的
  `cross-task-debt.json` 表明校验强度本就偏弱，不是偏强。
- **不把 `apis` 做成必填**——绝大多数模块 ≤10 个接口，无需拆分；必填会给全部存量与
  新建任务凭空加一份需要与契约同步维护的清单。
- **不把 Java/Spring 结构规则写进 `lib/`**——分层边界（CLAUDE.md 硬约束）。
  `cross-task-debt.json` 记录的「带 `@vima` 的 Controller 不得 import repository 包」
  属 admin 模板专属机检，与本项正交，另行立项。

## A19 存量项目的升级可达性：端册迁移 + 产物形态体检 + 骨架基线三方比较

> 创建日期：2026-08-13
> 来源：用户提问「已有的 vima 创建的项目能否通过 `vima update` 更新到最新功能而不影响
> 原有程序」。核实结论：**主体已实现**——update 的受管清单里代码文件命中数为 0
> （实测：一个改过 210 个代码文件的项目跑 update 后代码树指纹完全一致），
> `docs/spec.md`／`docs/contracts/*`／真实任务文件／`src`／`backend`／`vendor` 全在 managed 之外；
> CLI 能力（validate/plan/context/trace/render）随 `vima upgrade` 换 CLI 即生效，项目侧零改动。
> 剩三处缺口，本项逐条补齐（骨架自动更新**不做**，理由见「不做」）。

### 问题（实测，非推断）

1. **契约宣称的 manifest v1→v2 端册迁移根本没实现**。`docs/internal-contracts.md` §6.4 白纸黑字
   写「v1 manifest（无 apps 键）……`vima update` 迁移为 v2」，而 `lib/commands/update.mjs`
   里没有任何迁移代码——sustain-v3 跑了两次 update 仍是 `schemaVersion: 1`、无 `apps` 键。
   典型的「宣称与实现两张皮」。
2. **产物格式类增补项的缺口要到 `/go` 闸门才暴露**。A4 决策表、A13 `vima:rules`／
   `vima:non-goals`、A2 前端任务 `page` 字段都落在 userOwned 产物里，update 按设计永不触碰。
   实测：把一个项目的 spec 删掉那两个块再跑新 CLI 的 validate，得到 **V-SPEC-09/V-SPEC-11
   两条 error**——老项目升级 CLI 后会直接卡在 `/go` 第一道闸门，而在此之前没有任何环节
   告诉它「你缺的这些是哪个版本引入的、该补在哪、块长什么样」。
3. **骨架改进对存量项目完全不可见，且无从安全判断**。骨架（`src/`／`backend/`／`vendor/`）
   只在 `create` 时落一次。想告诉用户「模板骨架后来改了什么」，前提是能区分
   「用户自己改的」与「模板变的」——而 manifest 只记 managed 的校验和，骨架没有任何基线，
   于是连**报告**都做不出来（任何 diff 都混着用户的业务改动）。

### 决策：三条规格

**1）`vima update` 兑现 manifest v1→v2 端册迁移**

- manifest 缺 `apps` 键或 `schemaVersion ≠ "2"` 时，把 `resolveApps` 合成的端册
  （`apps[]` + `backend`）写入 manifest 并置 `schemaVersion: "2"`。
- 已有 `apps` 的项目不动（多端项目由 create 写入，迁移只补 v1）。
- **行为等价性**：写入的正是消费方（validate/context/trace/doctor/render）每次运行时
  由 `resolveApps` 合成的同一份端册——迁移只是把「每次现算」固化成「记录在案」，
  不改变任何既有行为。这是本条零风险的依据。

**2）`vima doctor` 增第 ⑫ 项：产物形态与当前 CLI 规则的差距**

一张显式的「增补项 → 产物结构判据 → 补写指引」表（**只列后加增补项引入的结构要求**，
新项目的 spec 骨架天然满足，故本项只会命中老项目）：

| 判据 | 出处 | 级别 | 缺失时的指引 |
|---|---|---|---|
| spec 第八章含决策表且表头有「已否决方案」列 | A4 | error（同 V-DEC-01） | 在第八章补 markdown 表：决策/理由/已否决方案/否决理由 |
| spec 第五章含 `vima:rules` 块 | A13 | error（同 V-SPEC-09） | 在第五章补 `yaml vima:rules` 块，每条 id/type/entity/desc 四要素 |
| spec 第九章含 `vima:non-goals` 块 | A13 | error（同 V-SPEC-11） | 在第九章补 `yaml vima:non-goals` 块；空清单也须显式 `non-goals: []` |
| 前端业务任务带 `page: PAGE-xx` | A2 | warn | 给 side=frontend 的 business 任务补 `page` 字段，正文删掉手写页面结构 |

- **与 validate 的分工**：validate 说「缺什么」（并据此阻断 `/go`），⑫ 说
  「这是哪个增补项引入的、补在哪一章、块长什么样」。级别与对应 validate 规则对齐，
  口径不打架。
- **门控**：`docs/spec.md` 不存在 → 本项跳过（warn「spec 未生成」），不误伤 BOOTSTRAP 期项目。

**3）骨架基线 + `vima update --scaffold-diff`（只报告，绝不写盘）**

- `create` 在 manifest 增 `files.scaffold: [{path, checksum}]`——记录**落盘后的实际内容**
  哈希（变量已渲染），`--force` 重跑时重建。骨架文件约 219 个（admin 模板），
  manifest 增约 18KB。
- `vima update --scaffold-diff`：只读子模式，按三方比较（基线／磁盘现状／当前模板源
  用同一组变量重渲染）输出：

  | 磁盘 vs 基线 | 模板源 vs 基线 | 结论 |
  |---|---|---|
  | 相同 | 不同 | **可安全更新**（你没改过，模板变了）——列出文件，附新版本内容位置 |
  | 不同 | 不同 | **需人工**（你改过且模板也变了） |
  | 不同 | 相同 | 不列（只是你的业务改动） |
  | 相同 | 相同 | 不列 |

- **无基线的存量项目**：输出一行说明「本项目 create 时未记录骨架基线，无法区分你的改动
  与模板变更」并正常退出（exit 0）——诚实报告能力边界，不猜。
- **本子模式不写任何文件、不改 manifest**。变量取 manifest 的 `createdAt` 与目录名，
  保证重渲染确定性（实测骨架文件中 `{{createdAt}}` 命中数为 0，无时间戳污染）。

### 验收判据（可跑命令）

```bash
# 1 端册迁移
node -e "const m=require('./.vima/manifest.json');delete m.apps;m.schemaVersion='1';require('fs').writeFileSync('.vima/manifest.json',JSON.stringify(m,null,2))"
vima update >/dev/null && node -e "const m=require('./.vima/manifest.json');console.log(m.schemaVersion, m.apps.length)"   # 2 1
# 2 产物形态体检
vima doctor --json | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).checks.find(c=>c.id==='artifact-shape').status))"  # ok
node -e "const fs=require('fs');fs.writeFileSync('docs/spec.md',fs.readFileSync('docs/spec.md','utf8').replace(/\`\`\`yaml vima:rules[\s\S]*?\`\`\`\n/,''))"
vima doctor 2>&1 | grep -c 'A13'                                        # ≥1（指出出处）
# 3 骨架基线与只读 diff
node -e "console.log(require('./.vima/manifest.json').files.scaffold.length)"   # >0（新建项目）
vima update --scaffold-diff | grep -cE '可安全更新|需人工|未记录骨架基线'        # ≥1
git status --porcelain | wc -l                                                  # 与运行前一致（只读证明）
```

### 落点

| 类型 | 路径 |
|---|---|
| 文件格式 | `docs/internal-contracts.md` §6.4（`files.scaffold` 基线 + 迁移口径落实） |
| 端册迁移 | `lib/commands/update.mjs` |
| 骨架基线 | `lib/commands/create.mjs`（copyDir 记录落盘内容哈希 → manifest `files.scaffold`） |
| 只读 diff | `lib/commands/update.mjs`（`--scaffold-diff` 子模式）、`lib/cli.mjs` 帮助面 |
| 体检项 | `lib/commands/doctor.mjs`（第 ⑫ 项 + `--json` 的 `artifact-shape`） |
| 契约登记 | `docs/internal-contracts.md` §12 +A19 |
| 单测 | `tests/unit/c1.update.test.mjs`、`c1.create.test.mjs`、`c2.doctor.test.mjs` |
| 文档 | `CHANGELOG.md`、设计 §21 版本历史 |

### 不做

- **不做骨架自动更新**（哪怕「用户未改过的文件」也不自动写）。骨架一旦生成就是用户的
  业务代码，自动改它与本项的出发点「不影响原有程序」直接冲突；`--scaffold-diff` 只报告，
  合不合、怎么合由用户决定。**也不提供 `--scaffold-apply`**——需求没要求，属镀金。
- **不为存量项目补造骨架基线**（如拿当前模板当基线）。那会把「模板后来的改动」误记成
  「用户的原始状态」，产出比没有更坏的结论。能力边界如实说明。
- **不把 A16 多端键（`app`/`consumers`）列进 ⑫ 的判据表**：多端项目只能由
  `create --apps` 建立，天生带这些键，老项目升级不会命中——列进去是凑数。
- **不在 ⑫ 里重跑全量 validate**：那是重复实现且拖慢体检；⑫ 只做结构存在性判据，
  「缺什么」仍归 validate。
