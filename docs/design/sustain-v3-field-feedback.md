## 一等发现：四类机检盲区

### F1. 弹窗必填字段 ⊄ 提交端点入参（双向）

**现象**：spec 的 `vima:page` 弹窗声明 `required: true` 的字段，提交端点的 `request` 里没有；
反方向亦然——契约必填的入参，弹窗里没有任何字段能填。

**证据（本次实证 4 条，全部为功能级阻断，非体验瑕疵）**

| 弹窗 | 缺失 | 后果 |
|---|---|---|
| MODAL-85 量表 | `scaleType`（契约必填、spec 无字段） | **提交必被 40001 拒绝，根本创建不了量表** |
| MODAL-76 库存盘点 | `itemId`（同上） | **盘点提交必被拒** |
| MODAL-90 质控指标 | `code`（spec 必填、契约与实体与真源建表均无） | 用户被迫填一个填了即丢的值 |
| MODAL-59 宣教内容 | `contentType`（同上） | 同上 |

前两条由 Builder 写代码时撞出（`page-34-fe` / `page-29-fe`），后两条由静态扫描发现后经
三源核对（契约 + 实体 + 真源建表）确认。**现有规则查了「页面 apis ⊆ 契约」，但没查字段。**

**这条缺口的连带价值**：补 MODAL-64「退款决定」时连带查出
`MallOrderService#refund()` **原先没有 `decision` 参数、一律按同意处理**——
退款审批形同虚设。教训是：**缺的那个字段往往正是某个业务判断的输入，字段缺失
意味着那个判断根本没发生**。这不只是 UI 问题。

**建议规则**：`V-SPEC-1x`（warn 起步，稳定后升 error）
- 正向：`modal.fields[].required==true` 的 `field` ∈ `submit.api` 对应契约 api 的 `request[].name`
- 反向：契约 api 的 `request[].required==true` 的 `name` ∈ 该 modal 的 `fields[].field`

**误报边界（这条规则不好写，务必先看这段）**

本次我自己的脚本给出过 **54 → 32 → 13** 三个数字，**前两个都是错的**：

1. 第一版正则 `\{\s*api:\s*([^}\n]+?)\s*\}` 在 `{id}` 的花括号处截断路径，
   造出 ~35 条假的「端点未找到」。**`submit: { api: POST /api/x/{id}/y }` 的闭合花括号是行末那个。**
2. 第二版没考虑**聚合 json 入参**：`items` 嵌在 `content` 里、`questions` 嵌在 `structure` 里
   并不算缺失。本项目大量采用这种做法（7 个聚合字段）。
3. 还需排除三类结构性假阳性：
   - `submit` 指向 `GET` 的选择/参考类弹窗（字段本就不提交）
   - 字段名即路径参数（`{id}` 对应 `patientId`/`orderId`）
   - 由页面上下文或表格勾选提供的值（`ids`、`txnType` 这类由弹窗身份决定的常量）

**结论：规则必须支持「聚合 json 分层判定」，否则误报率高到没人看。**
建议实现为「候选清单 + 分级置信度」而非直接判 error——本次最终定性靠的是实现者实地验证，
不是静态判据。

### F2. 一个字段有四个面，缺一面就是「只进不出」

**现象**：给端点补字段时只加 `POST` 请求，漏了 `GET` 列表响应 / `GET` 详情响应 / `PUT` 请求，
字段变成「建完再也看不见、改不了」。前端表现为「新建时能填，编辑时那一栏是灰的」，**且不报错**。

**证据**：本次**同一个错犯了三次**——设备编码 `code`、质控指标 `code`、宣教 `contentType`，
三次都是我（编排者）补契约时只写了 POST。第一次由 `page-40-fe` 撞出并登记为「补齐不完整」，
但我只当成一次疏忽记下、没提炼成检查项，于是补后两个时**原样又犯两遍**。

**建议规则**：`V-CON-0x`（warn）
对每个业务实体的字段做四面对账：`POST.request` / `GET(list).response` / `GET(detail).response` /
`PUT.request`。只出现在其中一面且非只读/非只写语义的，提示「疑似只进不出」。

**误报边界**：确有单向字段（如 `password` 只写、`createdAt` 只读、计算字段只出现在响应）。
建议提供 `writeOnly` / `readOnly` 标记让契约显式豁免，而非靠猜。

### F3. 跨页导航 key 一致性

**现象**：多个页面跳转到同一目标页时，各用各的 key 约定，目标页匹配不上，
**静默落到兜底分支且不报错**。

**证据**：本次三个跳转入口全是坏的——
- `page-05`（AI 辅助）推 `step: '5'` / `'8'`（数字串）
- `page-01`（工作台）推 `step: 'rxReview'`（**真源九步里根本没有这个 key**）
- 而壳页 `page-04` 按真源 `StepKey`（`screening`/`assessment`/…/`followup`）匹配

壳页对未知 step 的兜底是「纠正到首个可用步骤并改写 URL」——不报错，
用户只觉得「点了没去到该去的地方」。

**关键点：每个页面单看都自洽**（各自文件内 step 值用得一致），
**只有跨页对照真源才暴露**。单任务 Verifier 结构上看不见此类问题，
它归编排者（主 Agent）负责，但编排者也需要工具支撑。

**建议规则**：`V-CODE-0x`
从 spec 的 `nav`/`action: nav` 与代码中的 `router.push({ query: { step: … } })` 类字面量
提取跨页跳转参数，与目标页声明的取值域比对。

### F4. 聚合 JSON 入参无子协议

**现象**：契约对聚合入参只声明到 `type: json`，**内部结构没有任何约束**，
于是写入方 / 读取方 / 后端计算方各写各的。

**证据**：`structure` / `scoringRule` 的子结构在三处互不一致——
PAGE-34（量表管理，写入）、PAGE-42（评估，读取评分）、后端 `ScoringEngine.java`（计算）。
编译期与机检都看不见，运行时表现为「**存进去了但算不对**」。

本项目共 7 个聚合字段：`structure`、`scoringRule`、`content`、`basis`、`surveyDays`、
`fieldConfig`、`formula`。逐个补子协议时又发现两类新情况：

- **`content` 不是一个字段**：它在 6 个模块里是 6 种不同的领域对象（处方组分模板 /
  查房记录 / 长嘱组分 / 随访方案 / 病历七节 / HIS 医嘱明细），仅仅重名。
  `inpatient-order` 内部还有三种形状。**统一成一套结构是过度抽象**，正确做法是各自补。
- **有些字段确实没有权威结构**：`NutrientSummaryCalculator.summarize(Object surveyDays)`
  接收裸 `Object`、按键名递归求和；`PrintTemplateService` 对 `fieldConfig` 整体透传不解析。
  这两处的「子协议」只能是**建议性**的。

**建议**：
1. `type: json` 的字段要么带子结构声明，要么**显式标注 `enforced: false`**——
   「无强制结构」应当能被如实表达，而不是留白让人以为漏写了。
2. 增加一条 warn：同名聚合字段在不同契约里若给出**不同子结构**，提示「同名不同义，确认是否有意」。
   本次 `content` 正是这种情况，且确实是有意的。

## 二、溯源规则只到端点级，不到值级

`V-SRC-01` 查「契约端点在真源锚点有无实据」，但**值级漂移无人管**。本次两例：

| 漂移 | 后果 |
|---|---|
| 真源种子 `scoringRule.levels[].label` vs 引擎 `ScoringEngine.resolveLevel()` 读 `level` | 照真源入库会「**总分算得对、风险分级恒为空**」 |
| spec 字面值 `PG-SGA` vs 真实种子编码 `PG_SGA`（下划线） | 硬编码原型文案会让提交时 `scaleCode` 查无此项 |

两条都是 Builder 写代码时撞出来的，静态规则一条没抓到。

**建议**：`V-SRC-02`（warn）——spec 中以字面值列举的 `options` / 枚举，
与真源种子或后端枚举类的实际取值集比对。这类漂移「编译期与机检都发现不了，只在运行时炸」。

## 三、「每环都对 ≠ 链条通」：缺少冷启动可用性检查

**证据**：病区链路最典型——

1. 补 `GET /api/wards` 契约 ✓（`validate` 0 错误）
2. 建 `Ward` 实体 + 端点 ✓（324 测试全绿）
3. 种 6 条病区 ✓（336 测试全绿）

**三环各自验收全过，但全新启动时 6 条病区全部跳过**——底座 `DataInitializer` 只种
「总公司 / 技术部」两个脚手架部门，而病区需要「消化内科 / 普外科 / …」。
跨环的前置依赖（科室数据从哪来）没有任何一环负责。

后果：全新部署时 MODAL-01 的**科室下拉是对医院毫无意义的选项、病区下拉全空，患者建档走不通**——
正是 D-22 本要解决的问题，只是断点比预想更靠前。

**建议**：`pipeline` 阶段增加一类检查——**空库启动后，spec 中标为必选的字段，
其数据源是否真的有数据**。本次是我在验收报告里读到「跳过 6 条」才追下去的，属侥幸。

补救时我给修复轮定的核心验收点值得固化为惯例：
**不要只测「种了几行」，要断言「A 跑完后 B 能解析出全部 N 条」**——
即链条的端到端证明，而非各环自证。

## 四、编排层的三处摩擦

### F5. 增量修复轮没有一等公民地位

**证据**：临时开的修复轮没有对应任务文件，Builder 就按我给的报告文件名造了个
`@vima aggregate-subschema-fix` 打进 5 个文件，被 `vima trace` 抓出野生标注。

追溯体系的价值就在「每处代码能反查到哪条需求要的」，**造一个假 taskId 等于在链条上打洞**。
但编排期确实会产生大量跨任务的增量修复（本次约 10 轮），它们天然无处挂靠。

**建议**：提供轻量的修复轮登记（如 `vima fix-round <名称> --owns <既有 taskId 列表>`），
或明确约定「修复轮产出物一律沿用被修文件的既有 taskId」——本次我事后正是这么修的
（重新挂回 `page-34-fe` / `page-41-fe` / `page-42-fe`）。

### F6. 跨 layer 屏障与反停顿 hook 打架

**证据**：`pipeline-test` 依赖 `menu-seed`（pipeline 层，位于下一批次）时，
批次 14 尚未收敛，**跨 layer 屏障未开、确实无事可派**；但 `go-continue` hook 仍反复
要求「继续派发下一批」，我被迫在多个回合重复解释同一件事。

**建议**：`go-state.json` 的 `stopReason` 增加 `blocked-by-barrier`，
hook 见此值放行（与 `budget` / `terminal` 同级）。

### F7. 预算 24 与批次 5 不整除

**证据**：批次固定 5 个任务，预算 24——推进到 20 就只剩 4 个额度、不够下一批，
只能停在批次边界。**预算的实际生效值是 20，不是 24。**

**建议**：预算按批次对齐（如取 `floor(budget / maxParallel) * maxParallel`），
或允许在预算内拆分批次。

## 五、`vima context` 缺两条检索线（本次最大的系统性返工源）

**现象**：Builder 把 `docs/contracts/` 当成唯一事实来源，于是
**「契约里没写」= 「系统里没有」**，做出降级实现。

**证据（两次，性质递进）**

1. `page-02-fe` 把**系统底座**已有的 `getDeptList` / `getUserList` 判为不存在
   → 科室下拉空着、「分配营养师」退化成自分配（而契约明确支持指派任意人与取消分配）
2. `page-04-fe` 把 spec **自己指名的真源** `docs/raw/03-代码补位/FlowSteps.vue` 里
   现成的九步 `roles` 判为「未给出」→ RULE-28「无权限步骤置灰」半实现

第二次比第一次更严重：**spec 正文写着「真源为 `docs/raw/…:行号`」，Builder 仍然没去看**，
因为上下文包里没有它。

**止血办法**（本次采用）：把「判断某能力是否存在要查三条线」写进 `docs/coding-standards.md`——
它会随 `vima context` 分发到每个任务。此后批次未再出现同类降级。

**建议根治**：`vima context` 的上下文包除契约外，应纳入
① 系统底座接口索引（`src/api/system.ts` 等既有封装 + 后端无 `@vima` 标注的 controller）
② spec 正文引用到的 `docs/raw/` 真源片段。

## 六、并发热文件缺官方口径

**现象**：多个任务共用同一契约时会抢同一个 API 封装文件。本次最密集处
`page-17~24` 共 8 个任务同用 `followup-api.md`、`page-27~32` 共 6 个同用 `basedata-api.md`。

**风险形态**：后写者用 `Write` 整体覆盖会**静默抹掉其他人的导出，且 TypeScript 编译不报错**，
要等别的页面运行时才炸。

**本次绕法**：让各页把请求封装放进自己视图目录的 `api.ts`。
**但这违反编码规范「API 封装集中在 `src/api/<module>.ts`」**——属有意偏离，已记账，最终仍需人工合并。

**建议**：给任务 frontmatter 增加 `conflictsWith` 声明，或在 `vima plan` 分批时
避免同契约任务进同一批次；至少在编码规范里给出官方的并发写策略，
而不是让每个编排者各自发明一套。

## 七、三处人机工程

### F8. `npx vima *` 在子目录静默给错结果

**证据**：我在 `backend/` 下跑 `vima validate` 得到「**2 错误**」（假的，项目根实为 0 错误）；
在同一目录跑 `render-review` 得到 `NO_SPEC: 未找到 docs/spec.md`。
**同一个错我栽了两次**，第二次才反应过来是目录问题。

**建议**：CLI 向上查找项目根（识别 `.vima/` 或 `docs/lifecycle.json`），
或明确报错「当前不在 vima 项目根」，而非按当前目录静默工作。

### F9. `coding-standards.md` 是 managed 文件，但项目必须往里加内容

**证据**：本次往里加了三节（系统底座接口索引 / 检索纪律 / 补字段纪律），
因为它是**唯一会随 `vima context` 分发到每个任务的规范文件**——这是止血最有效的落点。
代价是 `doctor` ⑧ 从此长期报「受管文件被手改」。

**建议**：提供 project-local 追加区（如 `docs/coding-standards.local.md`，
由 `context` 一并打包但不纳入 manifest 校验和），让项目定制不污染受管基线。

### F10. `V-TASK-11` 的规则时机不对

**证据**：CLI 升级后新增「单任务负责接口数 >10 建议拆分」，本次命中 9 个任务——
但它们**早已全部完成**，此时拆分毫无意义，只能长期停在 warn 列表里。

**建议**：这类「任务粒度」规则应在 PLANNING 期（任务尚可调整时）起作用；
对已 `done` 的任务应自动豁免或降级为 info。

## 八、反过来：三处设计这次真的兑现了

写反馈也要写对的部分，否则下次不知道该保留什么。

1. **A16 端册化**：把前端从仓库根搬到 `apps/admin/` 时，**只改了 `.vima/manifest.json` 的
   `apps[0].dir` 一个字段**，`guard-shared`（按各端 dir 解析 sharedDirs）、
   `post-write`（从 `apps[].dir + codeDir` 推导 appDir 再定位 vendor）、
   `validate`、`trace`（扫描目录自动变为 `apps/admin/src, backend/src`）全部自动跟上。
   这个抽象在真实的结构变更中经受住了检验。

2. **`guard-shared` 写令牌**：并行批次里挡住了 Builder 单方面改契约，
   逼出「契约由主 Agent 单写者维护」的正确模式。多次拦截都是对的，没有一次误伤。

3. **`vima trace`**：抓出了**编排者自己**造的假 taskId。
   一个能抓编排者错误、而不只是抓 Builder 错误的机制，价值很高。

> F6 的语义已被 A17 白名单③覆盖（只补举例，不新增 stopReason 取值）。
