# Sustain 经 vima 重建后的视觉与交互退化：根因及解决方案

> 日期：2026-08-14
> 对象：`/home/renmk/projects/Sustain` 旧版与 vima 重建版
> 对照提交：`8c54687`（旧版最终形态）→ `d6f4382`（整仓替换为 vima 重建版本）
> 结论性质：基于 Git 历史、原始 Claude Design 文档、vima 规划产物、Agent 指令与最终代码的实证分析

## 1. 执行摘要

Sustain 经 vima 2.0.2 重建后出现的“页面变死板”，不是单纯的配色、圆角或组件库问题，也不是
生成模型能力下降。根因是 vima 2.0.2 在规划阶段把一个高维的视觉与交互设计问题，转换成了一个
低维、可枚举、可机检的规格实现问题：

```text
旧路径：需求 → Claude Design 高保真交互原型 → 以整页体验为目标直接开发 → 浏览器迭代

vima 2.0.2：需求 + 原型 → cards/table/form 等低维规格 → 灰盒线框审批
           → 分页并行实现 → 字段/接口/区块机械验收
```

在第二条路径中，空间关系、视觉层级、领域隐喻、动态状态、页面主角和微交互等信息，在进入
Builder 之前已经被丢失。Builder 又被要求不得自行发明组件树，Verifier 会对缺失、额外区块和
越界行为作失败判定。因此，Agent 最理性的行为就是使用最通用的 `VCard + VTable + VForm` 组合，
而不是恢复原型中已经被规格丢弃的设计。

本次对比也证明：vima-ui 不是主要瓶颈。当 PAGE-03 患者档案得到足够细的 1:1 版面说明时，
vima 仍能生成复杂、领域化的三列工作台。真正的瓶颈是：

1. 视觉信息是否进入实现上下文；
2. 实现者是否被授权进行表现层设计；
3. 验收是否评价实际体验，而不仅是结构与契约。

正确方向不是用 Claude Design 替代 vima，也不是让 vima 放弃确定性，而是建立职责分离的双真源：

- `spec / contracts` 负责业务事实、接口、权限和范围；
- 高保真设计稿或交互原型负责视觉、构图和交互表达；
- vima 负责组织两者进入任务、实现与验收，而不是把后者压缩掉。

## 2. 分析范围与方法

### 2.1 提交边界

Sustain 的 Git 历史存在一个明确的替换边界：

- `8c54687 feat: UI 企业蓝 v5.0 与密度收口 v5.1、患者工作站/诊疗流程重构……`
- `d6f4382 refactor!: 整仓替换为 vima 重建版本……`

本文主要比较这两个提交，避免将当前工作区中尚未提交的局部样式补救误算为 vima 的原始产物。

### 2.2 证据来源

本文使用以下一手材料：

### 2.3 量化概况

这些数字说明 vima 在吞吐量、完整性和一致性方面确实成功；视觉退化并不是“项目没有完成”，
而是“系统完成了它实际优化的目标，却没有优化用户关心的视觉与体验目标”。

## 3. 关键实证对比

### 3.1 工作台：角色化驾驶舱变成固定容器序列

旧版 `sustain-web/src/views/dashboard/Dashboard.vue` 共 931 行，其核心不是一组静态卡片，而是按角色
动态编排的工作台：

- 角色专属快捷动作；
- 角色专属焦点指标；
- 完成率环；
- 我的待办主区；
- 筛查提醒副区；
- 7 日筛查趋势图与风险分级图；
- 对每个跳转做角色、功能开关和患者上下文可达性校验；
- 药师、护士、医师等角色获得不同的页面主次和内容组合。

vima spec 将其归一化为：

```yaml
layout: [cards, toolbar, tabs, table]
```

对应的 `apps/admin/src/views/workbench/index.vue` 严格实现为：

- 六张固定导航卡；
- 一张提醒分类统计卡；
- 两个管理员工具按钮；
- 三个页签；
- 页签下的若干表格。

尤其值得注意的是，`screeningTrend` 和 `levelDist` 在新版中被放进 `VTable`，而旧版使用图表。
数据没有丢，信息表达方式却发生了退化。用户看到的不再是“今天最需要处理什么”，而是
“系统里有哪些字段和记录”。

这是视觉退化，也是产品语义退化：工作台从任务决策界面变成了数据容器集合。

### 3.2 随访模板设计器：“配置即所见”变成字段 CRUD

原 Claude Design 文档把随访模板设计器定义为核心创新：

> 三块结构 · 左侧配置，右侧实时预览“配置即所见”。

旧版 `FuTemplateDesigner.vue` 包含：

- 视频、表单、提醒、量表等内容块；
- 折叠式块配置与块顺序调整；
- 单选、多选、文本、数值、日期、图片、文件等字段构建器；
- 选项和单位的就地配置；
- sticky 手机外壳；
- 患者端真实形态的实时预览；
- `LIVE PREVIEW` / `SYNCED` 等即时反馈。

vima spec 自己记录了降级事实：

> 旧系统为“控件面板 / 画布 / 属性面板”三栏拖拽设计器。区块词表无对应词，下方以
> cards + form + table 降级表达。

最终实现中：

- “控件面板”成为按钮集合；
- “画布”成为字段 `VTable`；
- “属性面板”成为普通 `VForm`；
- 实时手机预览变成弹窗中的只读 `VTextarea`。

所有声明的按钮、字段和 API 都可以通过验收，但“直接操纵 + 即时可视反馈”的产品核心已经消失。
这是本项目最典型的“需求覆盖成功，产品体验失败”。

### 3.3 咨询处理：会话工作台被翻译成表格加表单

旧版是 `280px / 1fr` 两栏会话工作台：左侧会话列表，右侧消息流和回复区。

vima spec 同样明确记录：

> 区块词表无“两栏工作台”对应词，下方以 tabs + table + form 降级表达。

这使“正在与某位患者持续对话”的交互模型，被转换成“从表格选中记录并提交表单”的后台 CRUD
模型。接口和字段可能完全正确，但人的任务心智已经不同。

### 3.4 患者档案：反证组件库不是根因

PAGE-03 患者档案在 spec 中得到了一段高精度的 1:1 保留说明，包括：

- `264px / minmax(0,1fr) / 224px` 三列外壳；
- 固定患者身份栏、档案内容区和九步诊疗流程栏；
- sticky 锚点；
- 多级响应式断点；
- 档案/作业模式切换时左右栏不重挂载、不重取数；
- 异常检验数量、流程状态和动作区的细节。

该页面在 vima 重建版中达到 1085 行，超过旧版对应工作台的 931 行，保留了明显的领域结构。

这说明：

- vima-ui 组件足以承载复杂页面；
- Builder 也有能力实现复杂结构；
- 当视觉和交互意图没有在规划阶段丢失时，vima 并不会天然生成简单页面。

因此，主要矛盾是信息和权限，不是组件能力。

## 4. 根因分析

### 4.1 根因一：中间表示发生有损压缩

Claude Design 原型包含的不是单纯 CSS，而是一整套高维信息：

- 空间关系与比例；
- 信息主次；
- 内容密度与首屏重心；
- 角色变化和状态变化；
- 工作台、画布、会话、时间线等领域隐喻；
- 动作附着位置；
- 空态、加载态和异常态；
- 页面壳层与页面内容之间的节奏；
- 微交互和反馈方式。

vima 2.0.2 的 admin-web 页面词表主要是：

```text
toolbar / search / table / form / cards / tabs / pagination
```

这些词描述的是实现组件类别，不是用户任务结构。它们能够回答“这里有什么控件”，却无法完整回答：

- 哪一块是页面主角；
- 用户视线从哪里开始；
- 哪些内容应并列、嵌套、持续可见；
- 用户是在浏览、判断、设计、对话，还是执行流程；
- 数据最适合用图、时间轴、画布、卡片流还是表格表达。

一旦高维设计被压成低维组件序列，下游再强的 Agent 也无法判断丢失部分应该如何恢复。

### 4.2 根因二：灰盒线框承担了不该承担的审批职责

`docs/review/prototype.html` 明确声明：

> 语义占位线框：只表达功能与布局，不表达视觉。

但这份线框又是 `vima approve` 前的主要页面评审载体。于是评审可以验证：

- 页面和菜单是否存在；
- 角色是否可见；
- 按钮、弹窗和接口是否齐全；
- spec 与渲染产物是否漂移。

却无法验证：

- 页面是否形成完整构图；
- 信息是否拥挤或稀薄；
- 页面有没有明确主角；
- 交互模型是否符合领域任务；
- 实际视觉是否达到用户可接受的产品水准。

这会产生“全部闸门通过，但每页都不能用”的假成功。

### 4.3 根因三：Builder 与 Verifier 的激励共同抑制创新

当前 Builder 指令要求：

- spec 数据块和原型是页面结构唯一真源；
- 页面区块结构与组件清单必须一致；
- 每个区块必须有完全对应的 `data-block`；
- 共享层不可修改；
- 重试只允许修报告指出的问题，不得重写。

Verifier 又会：

- 逐个组件、行操作、弹窗字段和链接核对；
- 对多出来的按钮、接口、字段和页面作越界检查；
- 找不到明确代码证据即失败；
- 不评价构图完整性、视觉层级和使用体验。

由此形成不对称激励：

- 标准组件组合：收益明确、风险低；
- 页面级独特构图：无验收加分、存在越界或结构不符风险；
- 新领域组件：需要跨越共享层写保护；
- 改善交互模型：可能被判为超出 spec。

Agent 选择保守实现不是偶然，而是当前规则下的理性最优解。

### 4.4 根因四：页面并行切片消除了持续的设计作者

vima 的并行策略适合接口和独立业务任务，却天然削弱跨页面视觉一致性：

- 每个 Builder 只读取自己的 context 切片；
- 不持续观察其他页面的构图和交互；
- 页面之间很难共同生长新的领域组件；
- `src/components/` 整体被标为共享层只读；
- 共享修改需要额外补偿任务和串行流程。

旧版包含 `FlowSteps.vue`、`PatientContextBar.vue`、`PatientPicker.vue`、`StatusTag.vue` 等项目领域组件。
vima 重建版公共组件主要剩壳层与 `DictTag`，大量领域结构直接堆进千行级页面。

也就是说，新版既没有获得旧版的设计自由，也没有充分获得领域组件化收益。

### 4.5 根因五：确定性被扩展到了不适合确定化的领域

vima 的“确定性优先”对以下内容非常有效：

- 接口路径与字段；
- 任务依赖；
- 权限集合；
- 覆盖矩阵；
- 文件结构；
- 构建和测试；
- 追溯标记。

但视觉设计需要在约束内做判断，不能在设计发生之前被完全枚举。把页面视觉也试图压进有限词表，
会将“一致性”误写成“同构”，将“可验证”误写成“只实现容易验证的部分”。

### 4.6 根因六：吞吐速度压缩了真实反馈轮次

旧 Sustain 从 7 月中旬持续迭代到 8 月中旬，页面、设计令牌、壳层和领域组件经历了多轮互相校准。

vima 版从进入规划到 73 个任务开发完成约为一个工作日。这种速度是工程优势，但如果没有高保真
视觉目标和浏览器校准，节省掉的同时也是：

- 观察真实页面的机会；
- 发现构图空洞的机会；
- 比较跨页节奏的机会；
- 把一次性页面模式提炼成领域语言的机会。

时间差是放大器，不是根本原因；根本原因仍是流水线没有把这些反馈设为完成条件。

## 5. 两种开发范式的本质差异

### 5.1 Claude Design 直接开发：目标驱动、整体收敛

Claude Design 路径先给出一个完整的可感知目标：页面应该长什么样、什么信息最重要、用户如何操作。
开发阶段的任务是把代码逐步收敛到这个目标。

它允许实现者进行创造，因为创造并非无边界：前方有一张可比较、可人审、可修改的目标稿。

其主要优势是：

- 页面有明确主角；
- 领域任务容易形成独特交互；
- 跨页视觉语言更容易被整体感知；
- 设计讨论发生在成本较低的代码之前。

其主要风险是：

- 规格和代码可能脱节；
- 页面文件容易过大；
- 局部样式和重复组件较多；
- 后端契约、权限和异常路径容易被视觉主线遮蔽；
- 原型到代码的偏差缺少机械约束。

### 5.2 vima 2.0.2：证明驱动、局部完备

vima 路径先把需求拆成可验证事实，再证明每项事实被实现。它擅长让一个大项目在高并发下仍然：

- 不漏接口；
- 不漏字段；
- 不漏权限；
- 不产生任务依赖冲突；
- 可以机械回溯需求来源；
- 可以稳定重试和审计。

其主要风险是：

- 没进入规格的体验信息等同于不存在；
- 页面被组件词表塑形；
- 每页局部正确，全站仍可能视觉失败；
- “超范围”约束与“表现层创造”缺少清晰边界；
- 通过验收不能证明页面好用或好看。

### 5.3 本质结论

两种范式优化的是不同目标函数：

```text
Claude Design：优化体验上限、整体一致性、领域表达和视觉辨识度
vima 2.0.2：优化工程下限、需求覆盖、并行吞吐和可审计性
```

问题不在于二选一，而在于 vima 2.0.2 用“守工程下限”的机制替代了“创造视觉上限”的机制。

## 6. 解决方案总纲：双真源、分级设计、双层验收

建议把 vima 定位为 Claude Design 的工程编排器，而不是替代者。

### 6.1 双真源按关注点分权

| 真源 | 负责内容 | 不负责内容 |
|---|---|---|
| `docs/spec.md` / contracts | 页面能力、字段、接口、权限、业务规则、范围 | 像素构图、视觉节奏、具体表现形式 |
| 高保真设计稿 / 交互原型 | 视觉层级、空间关系、领域隐喻、动作主次、状态表达 | 发明新接口、新字段、新权限和新业务规则 |

发生冲突时按关注点裁定：

- 业务事实冲突，以 spec / contract 为准并回修设计稿；
- 视觉表达冲突，以已批准设计稿为准并回修代码；
- 设计稿需要新增业务能力时，先回 PLANNING 修改 spec，不能在开发阶段静默扩范围。

这不是制造“双重真源”，而是拒绝让同一份低维文件承担两个不同专业领域的全部事实。

### 6.2 页面分级，避免对 50 页一刀切

建议在 PLANNING 阶段给每页声明设计保真级别：

| 级别 | 页面类型 | 必需设计输入 | 示例 |
|---|---|---|---|
| D0 | 标准 CRUD | PDL + 项目模式库 | 字典、部门、普通主数据列表 |
| D1 | 领域信息页 | 一张高保真静态稿，含正常态和空态 | 工作台、患者概览、报表 |
| D2 | 标志性交互页 | 可交互高保真原型 + 关键任务场景 | 模板设计器、咨询台、诊疗流程、复杂处方 |

规则应是：

- D0 可以降级为模式库实现；
- D1 没有高保真稿不得进入前端开发，除非用户明确豁免；
- D2 没有交互原型不得 approve，不能用灰盒线框替代。

这样既避免为每个简单列表页付出高昂设计成本，也保护真正决定产品辨识度的页面。

### 6.3 高保真产物必须进入仓库

仅登记外部设计链接不够。建议至少冻结：

```text
docs/review/design/
  shell.png
  PAGE-01.default.png
  PAGE-01.empty.png
  PAGE-20.prototype.html
  PAGE-20.preview.png
```

外部 Claude Design 链接可以作为编辑入口，但仓库中的导出物才是：

- Builder 可稳定读取的视觉上下文；
- Code Review 可引用的证据；
- 末轮截图校准的基线；
- 数月后仍可复核的设计留档。

### 6.4 修改 Builder 的授权口径

当前的“页面组件树必须与 spec 一致”应改为：

> spec 声明的业务区块、字段、动作和接口不得缺失或改变；表现层可以增加子结构、页面级构图、
> 状态表达和领域组件，只要不引入新的业务能力，并与已批准设计稿一致。

建议明确区分：

- **业务扩展**：新增按钮、接口、字段、权限、状态流转——必须回 spec；
- **表现层设计**：网格、层级、图表、时间线、预览外壳、视觉分组、hover、空态——页面任务可自主实现；
- **领域交互组件**：患者上下文、流程步骤、消息流、设计画布——可在 feature 范围内提取，不应一律视为共享层越权。

### 6.5 调整共享层边界

建议拆为三层：

```text
src/components/framework/       # vima 框架层，业务任务只读
src/components/project/         # 项目级设计系统，由 Stage A / shared task 维护
src/features/<domain>/components/ # 领域组件，由领域任务拥有
```

不要把整个 `src/components/` 标记为业务只读。否则项目永远只能消费模板组件，无法长出
`PatientContextBar`、`FlowSteps`、`ConversationPane`、`LiveFormPreview` 这类真正构成产品辨识度的组件。

### 6.6 Stage A 管视觉语言，不垄断页面构图

A30 的两段式方向正确：

- Stage A：壳层、令牌、字体、密度刻度、圆角、投影、基础模式；
- Stage B：逐页内容构图和交互表达。

但需要修正“业务页不再自写整页 grid”的绝对约束。建议改为：

- 壳层和重复出现的版面模式必须进入 `layout.css`；
- 单页独有且由任务语义决定的构图，可以保留 page-local CSS；
- 同一种构图出现第二次时，再评估上收为项目模式；
- 页面不得绕过令牌自行创造新的视觉刻度，但可以自由组合已有刻度。

Stage A 应提供语言和边界，不应预先穷举每一页允许出现的句子。

### 6.7 PDL 表达任务拓扑，不只表达组件类别

A27 的 `pattern / density / data.shape / fold` 能提高结构下限，但仍需为高复杂页面保留逃生口。

不建议继续无限扩充 `toolbar/table/form` 枚举，而应允许声明：

```yaml
design:
  fidelity: D2
  pattern: custom
  designRef: docs/review/design/PAGE-20.prototype.html
  interactionModel: direct-manipulation
  primaryTask: 配置随访模板并即时确认患者端效果
  persistentRegions: [control-palette, canvas, live-preview]
```

这里的关键不是再造一个更大的组件词表，而是保留：

- 页面为何存在；
- 用户最重要的任务；
- 哪些区域必须持续可见；
- 使用的是浏览、编辑、设计、对话还是流程执行模型；
- 对应的视觉真源在哪里。

### 6.8 将视觉评审放进真正的闸门

建议形成双层 approve：

1. **结构审批**：现有 validate、review、prototype、coverage；
2. **视觉审批**：D1/D2 页设计稿齐备，用户在真实高保真稿上确认；
3. 两层均通过后才进入 DEVELOPING。

开发完成后再增加双层收口：

1. 七探针和构建测试保证页面“不坏”；
2. 真浏览器截图与冻结设计稿对照保证页面“达稿”；
3. D2 页面执行关键任务场景，保证交互模型没有被 CRUD 化。

视觉比较不必追求全站像素级硬失败，但必须至少检查：

- 主区域数量与方向；
- 首屏主角位置；
- 关键动作主次；
- 空态形态；
- 持久区域是否存在；
- 图表、时间线、对话流、画布等表达是否被表格替代。

## 7. 对 A27–A30 的具体评价与修订建议

### 7.1 应保留的部分

- 保留 A27 PDL、语义线框和七探针，继续负责结构下限；
- 保留 A29 “Claude Design 高保真稿 → 1:1 开发 → 末轮校准”；
- 保留 A30 Stage A / Stage B 分离；
- 保留设计语言、令牌和 layout 资产必须固化进仓库的原则；
- 保留“设计稿不得发明业务事实”的边界。

### 7.2 必须修订的部分

#### 修订一：设计稿不能只是非机检台账

A29 当前将 `design-links.md` 定义为不进 schema、不进机检的文档约定。对 D1/D2 页面，这会使设计
流程很容易被长期跳过。

建议：

- D0：`designRef` 可选；
- D1/D2：`designRef` 必填且本地文件必须存在；
- `vima approve` 只检查覆盖和文件存在，不尝试判断“好看”；
- 视觉质量仍由用户和最终截图校准负责。

这不是对审美做假机检，而是对“承诺的评审载体是否真的存在”做确定性检查。

#### 修订二：Stage B 必须保留原创构图权

A30 D-A30-04 不应禁止 Stage B 改变所有版面和卡片形态。应改为：

- 不得修改项目壳层和全局刻度；
- 可以为当前页面创造独有构图；
- 可使用 page-local grid/flex；
- 形成复用证据后再上收 Stage A；
- 需要新全局模式时才走 `sharedChangeRequest`。

否则两段式会再次退化为“所有页面从六种模式里选一个”，只是把七词表换成六模式表。

#### 修订三：分级而非逐页一刀切

A29 的“每张业务页一张稿”对 50 页项目成本过高，也容易使团队启用合法降级路径。

应改为：

- D0 模式参考页覆盖即可；
- D1 每页静态稿；
- D2 每页交互原型；
- 用户可以提升任意页面等级；
- 不允许系统自动降低等级。

#### 修订四：冻结视觉产物

云端稿不能在 Stage A 后直接“作废”到只剩 CSS。至少保留审批截图；D2 页面还应保留交互 HTML
或录屏。否则 5.2.6 校准轮缺少稳定比较基线。

#### 修订五：增加领域组件所有权

在 manifest 和任务模型中增加 feature-owned 目录，使一个领域任务组可以创建和复用自己的组件，
而不需要把所有项目组件都提升为全局共享层。

## 8. 推荐落地路线

### 8.1 第一阶段：先修工序，不扩 CLI 内核

目标：最小代价阻止下一次 Sustain 式退化。

1. 修改 planning-guide，加入 D0/D1/D2 分级；
2. 修改前端任务模板，登记本地 `designRef`、页面等级、primaryTask；
3. 修改 Builder 指令，区分业务越界和表现层设计；
4. 修改 Verifier 指令，D1/D2 增加设计稿对照证据；
5. 修改 `/go`，D2 页面收口时执行关键任务场景；
6. 将设计导出物保存在 `docs/review/design/`。

这一阶段即使没有新增 schema，也可以先通过任务卡和 managed 指令形成有效闭环。

### 8.2 第二阶段：补确定性覆盖检查

目标：保证承诺过的视觉工序不会静默缺席。

1. PDL 增加 `fidelity`、`designRef`、`primaryTask`；
2. validate 检查 D1/D2 的设计文件存在；
3. prototype manifest 携带 fidelity 与 designRef；
4. `vima context` 将本页设计文件、项目壳层截图和模式库切片打进 Builder 上下文；
5. approve 输出“结构已审 / 视觉已审”的双状态，不混为一个布尔值。

机器只检查覆盖与引用闭环，不尝试给审美打分。

### 8.3 第三阶段：建立浏览器视觉收口

目标：让“实现与设计稿一致”产生可审计证据。

1. 为每个 D1/D2 页面定义可复现的 mock 数据档位；
2. 真浏览器按固定 viewport 截图；
3. 报告中并列设计基线图和实现截图；
4. 自动探测溢出、空洞、首屏缺块、方向错误；
5. 人审判断视觉质量和可接受偏差；
6. D2 运行一条核心任务场景并记录结果。

### 8.4 第四阶段：用 Sustain 做回归样本

建议选以下四页作为 vima 设计能力黄金样本：

| 页面 | 类型 | 要守住的能力 |
|---|---|---|
| PAGE-01 工作台 | D1 | 角色化主次、指标、待办、趋势与提醒共存 |
| PAGE-03 患者档案 | D2 | 三列持久上下文、锚点、九步状态、模式切换 |
| PAGE-20 随访模板设计器 | D2 | 直接操纵、内容块、字段构建、手机实时预览 |
| PAGE-23 咨询处理 | D2 | 会话列表、消息流、回复区持续上下文 |

如果未来版本能同时满足：

- spec / contract / permission 全部通过；
- 四页没有被翻译成标准 CRUD；
- 设计稿与浏览器实现达稿；
- 领域组件可以合理复用；

才能说明 vima 已经从“工程正确的脚手架”进化为“兼顾产品上限的开发系统”。

## 9. 验收标准

解决方案落地后，至少应满足以下判据：

### 9.1 规划期

- 每个前端页面声明 D0/D1/D2；
- D1/D2 有本地视觉真源；
- 高保真稿使用真实字段、真实数量级数据并含空态；
- D2 原型可以完成页面的 primaryTask；
- 用户分别确认结构与视觉；
- 灰盒线框不再被表述为视觉稿。

### 9.2 开发期

- Builder 同时读取语义真源与视觉真源；
- 业务字段、接口、权限不因设计自由而漂移；
- 页面可以创建表现层子结构和 feature-owned 领域组件；
- D1/D2 不允许以通用 table/form 替代设计稿中的图表、消息流、画布、时间线或实时预览；
- 并行页面任务共享同一 Stage A 壳层和令牌。

### 9.3 收口期

- 现有构建、测试、trace、权限和接口对账保持不降级；
- 七探针无结构问题；
- D1/D2 具有设计基线与实现截图；
- 版面级偏差回 Stage A，页面级偏差回本页；
- D2 的关键任务场景可完成；
- 完成报告区分“结构通过”“视觉达稿”“交互达标”。

## 10. 不应采取的方案

### 10.1 只增加更多页面词表

继续添加 `timeline/chart/canvas/chat/...` 可以修复个别降级，但最终会形成一个不断膨胀、仍无法表达
完整构图的枚举系统。结构词应覆盖高频稳定模式，特殊页面应使用 `pattern: custom + designRef`。

### 10.2 只重做组件库皮肤

更漂亮的按钮、卡片和表格无法恢复已经丢失的角色编排、实时预览和会话心智。组件库决定零件质量，
页面设计决定产品结构；当前主要缺口在后者。

### 10.3 取消 spec 和机械验收

旧版的表达力不意味着应该放弃 vima 的契约、权限、追溯和批次优势。正确做法是给视觉设计增加独立
真源和验收通道，而不是退回完全依赖 Agent 记忆的开发方式。

### 10.4 让所有页面自由发挥

完全自由会重新引入旧版的重复、漂移和维护问题。设计自由应集中在：

- 项目级视觉语言；
- 页面级构图；
- 领域交互组件；

业务事实、接口、权限、令牌刻度和壳层边界仍应保持严格。

## 11. 最终结论

旧 Sustain 的灵活和创新，不是因为它“没有规范”，而是因为它的规范仍然保留了页面应该如何被
感知和使用。vima 2.0.2 重建后，这些内容在进入开发前被当成无法机检的信息压缩掉，只留下适合
枚举、并行和验收的业务事实。随后所有 Agent 都非常正确地实现了那份已经失去产品表达力的规格。

因此，vima 的下一步不应是让 PDL 变成更庞大的 UI 描述语言，而应承认两个事实：

1. 工程下限可以由结构化规格和确定性工具守住；
2. 视觉上限必须由完整设计目标、页面级判断和真实浏览器反馈创造。

最合适的产品定位是：

> **vima 负责把 Claude Design 的视觉目标，与契约、权限、任务、并行和验收可靠地连接起来；
> 它不替 Claude Design 做设计，也不允许设计绕过工程事实。**

这条边界既能保留旧 Sustain 的灵活与创新，也能保留 vima 已经证明有效的确定性和规模化能力。
