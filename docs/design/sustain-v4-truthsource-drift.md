# sustain-v4 重建实证：规格真源漂移与 vima-cli 的缺口

创建日期：2026-08-15
来源：用 vima-cli 3.0.6 全流程重建 Sustain（`/home/renmk/projects/sustain-v4`），
完成 BOOTSTRAP → PLANNING → DESIGNING → DEVELOPING 的后端全部 20 个模块（295 接口、198 测试全绿）
后中止；本文记录**过程中暴露的 vima-cli 缺口**，作为增补项的立项依据。

> 该次重建**未走 `/go` 编排**，是逐任务手工推进的。这一点本身也是一条发现：
> 手工推进能跑通，说明模板与契约体系是自洽的；但下面这 8 类缺陷全靠人工发现，
> 而它们本该由确定性内核在规划期拦住。

---

## 0. 结论先行

vima-cli 目前把「规格是否自洽」交给了人，而规格自身的三份真源
（`docs/raw/` 原始物料 → `vima:entities` → `docs/contracts/`）**没有任何机检把它们对起来**。

本次重建里，这三者两两之间都出现了大面积不一致，且**全部是静默的**：
不报错、不影响 `vima validate`（当时 0 错误），只在写到第 N 个模块时才被撞见。

| 真源对 | 实测不一致 | 后果 |
|---|---|---|
| DDL ↔ `vima:entities` | 72 个实体只有 **2 个**逐列吻合；缺 296 列、多 136 个 DDL 里不存在的字段 | 照实体块实现的后端无法服务契约 |
| DDL ↔ `enums` | 20 处可比对的枚举绑定中 **14 处**取值不符 | 状态显示空白、筛选永远筛不出东西 |
| 契约 ↔ 骨架 | 响应信封两套写法（`{code,msg,data}` vs 骨架的 `{code,message,data}`），88 处 | 前端要按两套形状解析 |
| 契约 ↔ 契约 | `_error-codes.md` 被 19 份契约引用却**不存在**；`SenderType` 取值在三处契约里两种写法 | 无统一错误码真源 |

## 1. 逐条缺陷与它本该被谁拦住

### D1 `vima:entities` 与 DDL 大面积不符（最严重）

spec 原文写「实体与枚举的机器真源是下方 `vima:entities` 块，**推导自** `03-代码补位/db-migration/`
的 85 张建表语句」——但实测 72 个实体只有 2 个与 DDL 一致。

例：`Patient` 缺 `attendingId` / `heightCm` / `admissionNo` 等 10 列，
而 `GET /api/patients` 的契约明确要求返回这三个字段。

**这不是某次疏忽**：它是「生成期用 LLM 归纳、之后无人复核」的必然结果。
LLM 归纳 85 张表时会自然地「取核心字段」，而「核心」的判据在归纳那一刻就丢失了。

> **缺口**：vima-cli 没有「结构化真源 → spec 块」的确定性通道，也没有反向机检。

### D2 枚举取值与 DDL 的 CHECK 约束不符

`RxType` 写 `en/pn/diet`，DDL 是 `nutrition/diet`；
`ChargeStatus` 写 `unpaid/paid/refunded/voided`，DDL 是 `pending/paying/paid/refund_pending/refunded/closed`。

枚举取值错了**不会编译报错**——它表现为「保存后状态显示空白」或「筛选条件永远筛不出东西」，
是最难归因的一类缺陷。

> **缺口**：同 D1。且枚举的证据强度需要分档（见第 2 节）。

### D3 契约引用了不存在的文件

19 份契约的表头都写「错误码取值见 `docs/contracts/_error-codes.md`（全局统一表），不得自行新造」，
而该文件**从未生成**。

> **缺口**：`vima validate` 不检查契约里的**文件引用**是否可达。
> 这是一条零成本、零误报的检查——路径写在文本里，存在与否是确定的。

### D4 响应信封与骨架实际不符

契约写 `ApiResponse<T> { code, msg, data }` / `PageResult<T> { total, list }`，
骨架实际是 `{ code, message, data }` / `PageResponse<T> { records, total, pageNum, pageSize }`。
88 处引用。

**这一处最能说明问题**：骨架是 vima-cli 自己发的模板，其 DTO 形状是**已知常量**；
契约由 LLM 起草时却写成了另一套。两边都在仓库里，没有任何东西把它们对起来。

> **缺口**：骨架的既有类型（`ApiResponse` / `PageResponse` / 系统底座实体）
> 应作为**契约生成期的约束**，而不是事后靠人对。

### D5 SQL 保留字撞列名 → 建表静默失败

`monitoring_point.value`、`prescription_item.usage` 都是 SQL 保留字。
Hibernate 建表报 syntax error 后**只在日志里记一行然后继续启动**——
上下文冒烟测试照样通过，直到运行时查询报「表不存在」才暴露。

修复是一行配置（`hibernate.auto_quote_keyword=true`），
但发现它靠的是我恰好翻了测试日志。

> **缺口**：骨架的 `application.yml` 未预置这条；也没有「每个实体都真建出表」的断言。
> 这类「框架静默降级」的坑，模板应当预先堵上——它对每个项目都一样。

### D6 DDL 解析的三处语法陷阱

本次为做比对写了解析器，踩到三个都会**静默少解析**的坑：

1. **迁移文件排序**：`readdirSync().sort()` 把 `V9` 排到 `V11` 之后，
   于是被 V11 扩展过的 CHECK 约束又被 V9 的旧定义覆盖回去。必须按数字序。
2. **一条 ALTER 加多列**：`ALTER TABLE t ADD COLUMN a …, ADD COLUMN b …;`
   只解析第一列会让 `Charge` 少掉 4 个结算字段。且**不能按逗号切**——列注释里带中文逗号。
3. **列定义跨行**：`status varchar(16) DEFAULT 'draft'` 换行后才是 `CHECK (...)`，
   逐行解析会整条漏掉。

> **缺口**：若 vima-cli 要提供「从 DDL 导入」的能力，这三条必须内建，否则导入器本身就是新的失真源。

### D7 权限点：代码自造 spec 未声明的码

给 AI 接口写了 `ai:advice:view`，而 spec 只声明了 `generate` 与 `confirm`。
自造的权限点**永远配不上**——角色配置页的可选项来自 spec 的菜单表，
管理员在那里找不到这一项，于是该接口对所有角色都是 403，且没有任何报错指向原因。

反向也踩到：spec 里有 14 个**不带引号**的 `perms: x:y:z` 声明
（settlement / order / followup / exercise），我最初的检查正则只认带引号的，
于是误以为这些模块没有权限点可用，差点又去编一个。

> **缺口**：`vima validate` 应校验「代码里用到的权限点 ⊆ spec 菜单声明」。
> 这是 A22「字段级机检」的自然延伸——权限点也是一种字段。

### D8 实体排除清单的误判

`clinical.menu_template` 是**食谱模板**（配餐业务），我因表名前缀像系统菜单而误排除，
导致 4 个 `/api/meal/menu-templates` 接口没有实体可用。

> **缺口**：任何「按名字模式排除」的规则都需要人工复核清单，
> 且清单本身应该是 spec 的一部分（可审阅），而不是脚本里的常量。

## 2. 一条方法论：证据强度分档

处理「DDL 说 A、契约说 B」时，需要可复现的判据，否则每次都靠个案裁量。
本次收敛出的分档（已写进 sustain-v4 的 D-13）：

| 档 | 证据 | 效力 |
|---|---|---|
| 1 | DDL 的 `CHECK` 约束 | **最硬**——数据库真的会拒绝越界值。取最后一次 `ADD CONSTRAINT` 的定义 |
| 2 | DDL 的行内注释 `-- a/b/c` | 仅提示，不覆盖。注释极易与实际脱节 |
| 3 | 契约明确要求而 DDL 未声明 | 单列登记并注明**是哪个接口需要它** |
| 4 | 无任何证据 | 保留原值 |

反例（都试过、都不行）：
- 「一律以注释为准」→ 会把过时注释当真源；
- 「一律以 CHECK 为准」→ 会丢掉契约明确需要但 DDL 漏声明的状态（如 `RecordStatus.voided`
  由 `POST /api/assessments/{id}/void` 要求）。

## 3. 对 vima-cli 的候选改动（按证据强度排序）

以下按「有实测证据 → 改动面可控 → 与既有架构相容」排序，**未立项**，供裁定：

### 候选 1：契约的文件引用可达性检查（V-CON 新规则）

- **证据**：D3，19 份契约引用了不存在的 `_error-codes.md`。
- **实现**：扫契约正文里的 `docs/**.md` 形式路径，逐条 `existsSync`。
- **代价**：约 20 行，零误报（路径是确定的），无新依赖。

### 候选 2：权限点闭包检查（V-SPEC 新规则）

- **证据**：D7，自造权限点会让接口对所有角色 403 且无任何提示。
- **实现**：代码里 `@perm.has('x')` / `v-auth="x"` 的集合 ⊆ spec 菜单声明的 `perms:` 集合。
- **注意**：spec 的 `perms:` 有带引号与不带引号两种写法，正则必须都认（我踩过）。
- **代价**：约 40 行。属 A22 字段级机检的同类扩展。

### 候选 3：骨架既有类型作为契约生成期约束

- **证据**：D4，88 处信封不一致。骨架的 DTO 形状是 vima-cli 自己发的**已知常量**。
- **实现**：模板侧提供一份「骨架已提供的类型与形状」清单（`CAPABILITY.md` 的后端版），
  规划期的契约起草必须引用它而非自拟。
- **代价**：中。需要新增一份后端 CAPABILITY，并让 planning 阶段的提示词消费它。

### 候选 4：模板预置「框架静默降级」的防护

- **证据**：D5，`auto_quote_keyword` 缺失导致建表静默失败。
- **实现**：骨架 `application.yml` 预置该项；模板测试里加「每个 `@Entity` 都能查通」的断言。
- **代价**：小，且**对每个项目都一样**——这正是模板该承担的。

### 候选 5：结构化真源导入器（最大的一块，需慎重）

- **证据**：D1/D2，实体与枚举的失真率分别是 97% 与 70%。
- **形态**：`vima import-schema --from <ddl-dir>` 把 DDL 确定性地转成 `vima:entities`，
  并提供 `--check` 做持续比对（我在 sustain-v4 里手写了这三个脚本，可作为原型）。
- **风险**：这是**新增一类能力**而非补一个规则。要防止它变成「支持 MySQL/Oracle/…」的无底洞。
  建议若立项，**只支持一种输入形态**（PostgreSQL DDL），且明确写进非目标：不做通用方言解析。
- **前置**：D6 的三条解析陷阱必须内建，否则导入器自己就是新失真源。

## 4. 一条元观察

本次 20 个后端模块全部手工完成（未走 `/go`），最终 198 测试全绿、
契约 292 接口 100% 覆盖、0 校验错误。这说明：

- **模板与契约体系本身是自洽可用的**——手工按契约实现能跑通；
- **失效点不在执行期，在规划期**：上述 8 类缺陷全部诞生于「LLM 起草规格」那一步，
  而 vima-cli 当前的确定性内核**只校验规格内部的引用完整性**
  （V-SPEC/V-CON 检查的是「块里的字段齐不齐、引用对不对」），
  **不校验规格与外部真源的一致性**。

换句话说：`vima validate` 能保证规格「自洽」，不能保证规格「属实」。
本次八条里有六条属于后者。

> 这与 A21 经验反哺回路的方向一致，但 A21 采集的是**执行期**轨迹；
> 规划期的失真需要另一类机制——不是采集，是**对账**。
