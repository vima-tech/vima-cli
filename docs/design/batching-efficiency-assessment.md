## 0. 一页结论

先答问题本身：**会重犯，而且重犯点不在「分批」，在「拆任务」和「填依赖」。**

三个体感症状对应三个不同根因，其中只有半个被 A17 修过：

| 症状 | 真实根因 | A17 是否覆盖 |
|---|---|---|
| 每批几十个接口、单批 > 30min | **任务粒度没有上限**——一个契约文件 = 一个任务，`basedata-api-be` 单任务 62 个接口 | ❌ 未覆盖，模板默认值仍会复发 |
| 每批都要重输 `/go` | 一半是批次计数（A17 已修，但该项目 `go.md` 还停在 2.0.2 没吃到）；一半是 **8 任务/次的阈值**对 73 任务量级不够用 | ◐ 修了计数口径，没动阈值 |
| 开发周期长 | 另有一条纯结构性浪费：**50 个前端任务被假依赖锁在 19 个后端任务之后**，而前端验收清单里没有任何一条需要后端跑起来 | ❌ 未覆盖，且是 planning-guide 写明的**默认值** |

杠杆排序（对 wall-clock 的影响）：
**任务粒度上限 ＞ 前后端解依赖 ＞ 同层子批流水线化 ＞ 并行度可配 ＞ 会话预算阈值。**

关键认知（§1.5 实测支撑）：**瓶颈既不是构建也不是工作量，是不均衡造成的空转**。
构建实测只要 1.34s / 2.82s；总生成量 120 分钟是硬成本，省不掉。
但批次时长取的是**批内最慢任务**，而 `followup`（14.0 min）比同批最小任务大 7 倍——
实测三个业务批的并行槽空转率都在 **52–54%**。所以「拆细」的目的不是让任务变小，
而是让**同批任务体量均衡**，把批次时长从「最大值」拉回「均值」。
其余四条都是把拆细带来的任务数增长吸收掉，不让它变成更多次 `/go`。

## 1.5 时间到底花在哪（实测，2026-08-13 追加）

初稿把「每批半小时」归因于工作量，用户质疑「平常写几十个接口用不了那么久，
是不是每个子代理都要跑测试」。两个假设都实测证伪了，真因是第三个。

**证伪一：构建/测试不是瓶颈。**

```bash
cd ~/projects/sustain-v3        && /usr/bin/time npm run build:check   # → 2.82 秒
cd ~/projects/sustain-v3/backend && /usr/bin/time ./mvnw -o -q compile  # → 1.34 秒
```

全量 `mvn test` 规模从 54 用例长到 296 用例（各 builder 报告的 `checks.fullTest`），
含 Spring 上下文 + 真实 Postgres/Redis，量级是**分钟**不是半小时。工具开销占比很小。

**证伪二：也不是「工作量大」这么笼统。** 真正的量在这里——每个业务文件头部都带
`@vima <taskId>` 标注（builder 角色模板的「代码级追溯（必做）」），所以产出可以精确归属：

```bash
cd ~/projects/sustain-v3
grep -rl '@vima followup-api-be' backend/src src | xargs wc -l | tail -1
```

| 任务 | 文件数 | 行数 | ≈输出 token | ≈纯生成分钟 |
|---|---|---|---|---|
| `followup-api-be` | 81 | 4527 | 58.9k | **14.0** |
| `basedata-api-be` | 58 | 3878 | 50.4k | **12.0** |
| `settlement-api-be` | 64 | 3856 | 50.1k | **11.9** |
| `inpatient-order-api-be` | 42 | 2551 | 33.2k | 7.9 |
| …（中位数附近） | 11–22 | 600–1300 | 8–17k | 1.9–4.2 |
| **25 个已完成任务合计** | **608** | **38 629** | **502k** | **120（单线程）** |

> 换算口径（估算，非实测）：Java/Vue 约 13 token/行；子代理输出速率按 70 token/s。
> 这两个系数只影响绝对值，不影响下面的结论——`followup` 比同批最小任务大 **7 倍**
> 这件事与速率取值无关。

**真因：子代理内部是严格串行的，而大任务把本可并行的工作串行化了。**

- 人写「几十个接口」快，是因为复制粘贴改；子代理是**逐 token 生成**，
  4527 行就是 4527 行的物理时间，跟难不难无关，跟多少字符有关。
- 一个接口不是一个文件：`followup` 35 个接口摊到 **81 个文件**
  （Entity/Repository/Service/Impl/Controller/DTO/单测 六七层），平均 **~130 行/接口**。
- **批次时长 = 批内最慢任务，不是平均值**。实测三个业务批的构成：

  | 批次 | 批内任务纯生成分钟 | 批内合计 | 批次时长（=最大值） | 空转率 |
  |---|---|---|---|---|
  | 批 1 | ai 2.0 / assessment 4.2 / **basedata 12.0** / consultation 3.2 / dashboard 3.8 | 25.2 | 12.0 | **52%** |
  | 批 2 | diagnosis 3.5 / exercise 1.9 / **followup 14.0** / his 3.1 / inpatient 7.9 | 30.4 | 14.0 | **54%** |
  | 批 4 | prescription 6.1 / report 3.6 / **settlement 11.9** / ward-round 3.5 | 25.1 | 11.9 | **53%** |

  每批约**一半的并行槽在空转**等最慢那一个。纯生成 12–14 分钟，加上读契约、查表结构、
  跑测试、按 Verifier 报告返工的往返，「单批半小时以上」完全对得上。

**结论修正**：B1 仍是最大杠杆，但理由不是「上下文压力」而是 **Amdahl 瓶颈**——
拆细的目的不是「让每个任务变小」，而是**让同批任务的体量均衡**，因为批次时长取的是最大值。
理想情况下 120 分钟的总生成量除以 5 路并行 = 24 分钟；实测这四个批的时长之和是
50.6 分钟，**多出来的 26 分钟纯粹是不均衡造成的空转**。

## 2. 六个瓶颈

### B1 任务粒度 = 契约文件粒度，且无任何规模上限 ★最大杠杆

- 证据：`templates/admin/planning/_template-be.md:18`「后端模块任务建议 `<模块>-api-be`」，
  全仓 grep「任务规模 / 接口数 / 拆分粒度 / 单任务」在设计文档、增补项、planning-guide 中
  **零命中**——没有任何一条文字资产给任务规模设界。
- 后果（按 §1.5 实测重述）：`followup` 35 个接口 = 81 个文件 = 4527 行塞进**一个**
  子代理的单次委派，而子代理内部严格串行——它一个人的纯生成时间（14.0 min）就是
  整批 5 个任务（合计 30.4 min）的批次时长，另外 4 个任务干等，**空转率 54%**。
  同时是质量问题：单会话临近上下文上限时后半段接口的对齐质量必然下滑，
  Verifier 也要一口气核对 81 个文件。
- **判据应是「均衡」而非「小」**：批次时长取最大值，所以同批任务体量接近才是目标。
  实测 60–180 行/接口（`basedata` 63、`followup` 129、`patient` 176），
  接口数是可用但有 3 倍方差的代理指标。
- 判定：**未修复**。任何新项目按现模板拆解都会复现。

### B2 前后端假依赖（契约先行体系里最贵的一处自相矛盾）

- 证据：`templates/admin/planning/planning-guide.md:149-150`——任务拆解确认环节
  「与用户确认前端任务依赖策略（**默认前端依赖对应后端**；也可仅依赖 shared 并行开发）」。
- 反证：`docs/tasks/page-05-fe.md` 的验收清单只有「区块标记齐全 / 字段与**契约**一致 /
  `npm run build:check` 通过」——**没有一条需要后端进程跑起来**。
  前端任务的事实来源自始至终是契约文件（PLANNING 期就已落盘并通过三道闸门）。
- 后果：拓扑分层把 50 个前端任务整体压到 level ≥1，18 个批次被锁成
  「4 批后端 → 10 批前端」的两段式；本可与后端同层混排的前端任务全部空等。
- 判定：**未修复**，而且错的是**默认值**——单一真源（契约）已经在位，默认却不信它。

### B3 会话预算阈值 8 任务/次

- 证据：`templates/admin/workspace/commands/go.md:86`「单次 /go 最多推进 8 个任务」。
- 后果：73 任务 ≥ 10 次人工 `/go`；B1 的修复会把任务数推到 ~85，若阈值不动则变 11 次，
  「拆细任务」的收益会被「更多次手工续跑」抵消掉。
- A17 的原始论证是对的：成本与任务数成正比，每任务一份 Builder 摘要 + 一份 Verifier 报告。
  但**这两份的体量本身没有被约束**——实测磁盘上的 Builder 报告 7–13KB/份
  （`wc -c .vima/reports/*-builder.json`）。阈值 8 是在「回传摘要可能很长」的假设下取的保守值；
  真正该管的是回传摘要的**长度上限**，管住了长度，阈值才能安全放大。
- 判定：**未修复**（A17 明确「不放宽 8 任务上限」，并把重开条件留给了本次反馈）。

### B4 `MAX_PARALLEL = 5` 硬编码

- 证据：`lib/commands/plan.mjs:9`，无 CLI 选项、无配置文件入口；
  设计 §10.2 要点 4 给的理由是「避免资源争抢与输出混乱」，**无实测依据**。
- 后果：50 个互不依赖的前端页面任务被切成 10 个子批，纯粹由这个常数决定。
- 判定：**未修复**。

### B5 同层子批之间白白多走一倍轮次

- 证据：`go.md:66`「等待本批全部 Builder 返回结果摘要，逐任务派发 vima-verifier 校验」——
  每批固定 2 轮（Builder 轮 + Verifier 轮），18 批 ≈ 36 轮。
- 关键观察：因**并行度上限**切出的同层子批之间**没有任何依赖**
  （`plan.mjs:126-138` 的贪心切批只在同一 level 内进行）。
  既然无依赖，「子批 N 的 Verifier」与「子批 N+1 的 Builder」完全可以在同一轮内派发。
  前端 10 个子批可由 20 轮压到 11 轮。
- 附带发现（质量侧）：`.vima/reports/cross-task-debt.json` 自己记了教训——
  「Verifier 逐任务验收看不见跨任务的同款违规；被引用的『先例』本身就是未被发现的缺陷」
  （Controller 直连 Repository 在 ward-round 被判 fail，同款违规在 consultation 存活）。
  这类**结构性规则该由机检覆盖**（零 token、零轮次、天然全量），不该指望每个 Verifier 各自发现。
- 判定：**未修复**。

### B6 批次检查点从未形成（零回滚点）

- 证据：sustain-v3 `git log` → 「尚无任何提交」；20 个任务、251 个接口的产出没有任何批粒度回滚能力。
- 成因：A17 规定「用户输入 /go 即构成明确授权」，但用户全局 `CLAUDE.md`
  的「禁止自动提交（必读 · 不可绕过）」优先级更高，主 Agent 的实际行为是跳过提交。
  A17 已把「提交受阻」判为非停点（不再阻塞调度，这一半是对的），
  但**回滚点缺失这件事本身没有兜底**——报告里注明一句「未形成回滚点」，然后就没有然后了。
- 判定：口径冲突仍在，**需用户裁定**（见 §4 第 6 条），这一条不是效率问题而是风险问题。

## 3. 方案 A：sustain-v3 剩余 53 个任务，现在就能做

不依赖 vima-cli 任何改动：

1. **`vima update`**——把 `.claude/commands/go.md` 从 2.0.2 拉到 3.0.1，A17 三项修复即刻生效
   （批次计数退役 / 提交授权口径 / 合法停点白名单）。已 `--dry-run` 验证：
   go.md、check.md、三个 agent、两个 hook 均判为「未修改，随模板更新」，
   唯一需人工合并的是 `docs/coding-standards.md`（用户改过，新版写到 `.vima-new` 旁路）。
   预期效果：剩余 53 任务的 `/go` 次数从 ≈10 次降到 ≈7 次。
2. **建立 git 基线提交**（需用户明确授权）——当前 20 个任务的产出零回滚点，
   这是本次评估里唯一的**风险**项而非效率项。
3. **不做**：批量摘掉 50 个前端任务的后端依赖。后端已全部 done，此刻解依赖不改变分批结果
   （层级仍是同一层、仍是 10 个子批），属于无收益改动。B2 的价值在**下一个项目**。

## 4. 方案 B：vima-cli 增补项 A18 候选规格（六条）

按杠杆排序。每条注明落点层与「为什么它不是过度设计」（可反查到的需求出处）。

**1）任务规模上限 + 机检**（对应 B1）
- 规格：单个 `business` 任务引用契约中的接口数 ≤ **10**（实测 ~130 行/接口，
  对应 ≈1300 行、≈4 分钟纯生成，与当前中位任务持平）；超出者必须按子域拆分为
  `<模块>-api-be-<子域>`，并在 `conflictsWith` 中互相登记（同模块任务共享实体/仓储层，
  A8 冲突声明已有此机制，不排同批）。
- **目标是均衡不是变小**（§1.5）：批次时长取批内最大值，一个 14 分钟的任务配四个
  3 分钟的任务，等于浪费掉 54% 的并行槽。上限 10 的作用是压掉长尾，
  让同批任务落进同一量级。
- 落点：`planning-guide.md` 任务拆解节拍 +1 步；`_template-be.md` frontmatter 注释；
  `validate.checklist.md` 新增 V-TASK-xx（warn 级，可由用户裁定放行）；`lib/commands/validate.mjs`。
- 需求出处：本评估 B1（用户实测反馈「每批几十个接口、半小时以上」）。

**2）前端任务默认只依赖 `shared-base`**（对应 B2）
- 规格：planning-guide 第 5.4 步默认值对调为「**默认前端仅依赖 shared-base**（契约先行的必然推论）；
  确需依赖后端产物的（如需要真实种子数据的联调页）逐个显式说明理由」。
  `_template-fe.md` 注释同步。
- 落点：`planning-guide.md:149-150`、`templates/admin/planning/_template-fe.md`。
- 需求出处：设计 §9.5「契约是前后端唯一对齐真源」——本条是把既有真源口径贯彻到调度层，
  不是新需求。

**3）同层子批流水线化**（对应 B5 速度侧）
- 规格：`go.md` 批次调度增加一条——同一 level 内因并行度上限切出的子批之间无依赖，
  主 Agent **可在同一轮内派发「上一子批的 Verifier」+「下一子批的 Builder」**；
  跨 level、跨 layer 的批次边界仍是硬屏障。
- 落点：`go.md` 步骤 3；设计 §10.2 时序图；`batch-plan.json` 增 `level` 字段
  （让主 Agent 能确定性判断两个批是否同层，不靠推断）。
- 需求出处：本评估 B5；机制依据是 `plan.mjs:126-138` 的切批算法本身保证同层无依赖。

**4）并行度可配**（对应 B4）
- 规格：`vima plan --max-parallel N`（1–10，默认值从 5 提到 **8**），
  写入 `batch-plan.json` 的 `maxParallel` 字段供追溯。
- 落点：`lib/commands/plan.mjs`、`docs/internal-contracts.md` §9 与 §6.5。
- 诚实标注：默认值 5→8 **无实测依据**，与原值 5 一样是取值判断；
  建议先做成可配置并在 sustain-v3 剩余前端批上实测一次再定默认。

**5）回传摘要长度上限 + 会话预算放大**（对应 B3）
- 规格：`vima-builder.md` / `vima-verifier.md` 角色模板硬性规定
  「返回主 Agent 的摘要 ≤ 15 行结构化结论，明细一律落 `.vima/reports/<taskId>-*.json`」；
  在此前提下会话预算从 8 提到 **24 任务/次**。
- 顺序纪律：**先有摘要上限，才能放大预算**——A17 对「编排者上下文过载」的担忧真实存在，
  放大阈值的前提是把每任务的上下文成本从「不受控」变成「有界」。
- 落点：`.claude/agents/vima-builder.md`、`vima-verifier.md`、`go.md` 步骤 3、设计 §10.2 对策表。
- 需求出处：A17「不做」清单第 2 条自留的重开条件，本次已被真实项目触发。

**6）批次检查点的口径冲突（需用户裁定，不预设结论）**（对应 B6）
- 三个候选，请用户选一：
  a. 维持现状（A17 口径），接受「全局禁令环境下无回滚点」；
  b. 降级为**非 git 快照**：批后把改动文件清单 + 内容哈希写入 `.vima/reports/batch-<N>-snapshot.json`，
     不碰 git，回滚由用户手动执行——绕开禁令但保留追溯；
  c. 把授权显式化：`/go --commit` 才提交，不带该 flag 时连尝试都不做，报告不再刷「未形成回滚点」噪声。
- 落点视裁定结果而定。

**（不进 A18，另议）结构性规则机检下沉**——把 `cross-task-debt.json` 记录的
「带 `@vima` 标注的 Controller 不得 import repository 包」这类规则做进
`templates/admin/workspace/hooks/post-write.mjs`（admin 模板专属，符合分层边界：
Java 语义不得进平台中立的 `lib/`）。这条**提质量不提速度**，与本评估主题正交，
需求出处是 sustain-v3 的实际缺陷记录，建议单独立项。

## 5. 量化预期（估算，非实测）

以 sustain-v3 规模（251 接口 / 50 页面）为样本，粗估一次完整开发：

口径：用 §1.5 实测的**纯生成分钟**做单位（可归属、可复算），不用会随环境波动的
wall-clock。真实 wall-clock ≈ 纯生成 × (读契约/查表/跑测试/返工的往返系数)，
该系数对新旧方案同量级，故比值可比。

已完成的 20 个后端任务（含 shared）实测：**总生成量 120 分钟**（38 629 行 / ≈502k token）。

| | 现状（实测） | A18 落地后（推算） |
|---|---|---|
| 批次时长构成 | 各批取最大值：6.2 + 12.0 + 14.0 + 6.5 + 11.9 = **50.6 分钟** | 均衡切分后各批 ≈ 均值：**≈ 24 分钟**（并行度 5）／**≈ 15 分钟**（并行度 8） |
| 并行槽空转率 | **52% / 54% / 53%**（批 1/2/4 实测） | < 15%（同批体量落进同一量级） |
| 任务数 | 73 | ≈ 85（后端长尾按 ≤10 接口拆细） |
| 批次数 | 18 | ≈ 14（并行度 8 + 前后端同层混排） |
| 调度轮次 | ≈ 36（每批 Builder + Verifier 各一轮） | ≈ 20（同层子批流水线化） |
| 人工 `/go` 次数 | ≥ 10 | ≈ 4 |

最大的一块收益来自 B1，且它的性质是**消除空转而非压缩工作量**：总生成量 120 分钟一分不少，
但从「50.6 分钟的批次时长」压到「24 分钟」——省下的 26 分钟是四个任务干等第五个的时间。
并行度从 5 提到 8 再省 9 分钟。其余四条合起来把「拆细导致任务数 +16%」变成净收益而非新负担。

## 6. 为什么这套「更快」不等于「更糙」

每条提速都必须有对应的质量论证，否则不该采纳：

| 提速项 | 质量影响 | 论证 |
|---|---|---|
| 任务拆细（B1） | **提升** | 单 Builder 上下文从 62 接口降到 ≤10，远离上下文上限；Verifier 的核对面同步收窄 |
| 前后端解依赖（B2） | **中性** | 前端事实来源本就是契约（已过三道闸门），验收清单不含任何后端运行时依赖；契约不一致由 `vima validate` 的引用闭环规则机检 |
| 同层子批流水线（B3/B5） | **中性** | 每个任务仍走完整的 Builder → 独立 Verifier；只是两个**无依赖**子批的轮次重叠，不减少任何一次校验 |
| 并行度 5→8（B4） | 待实测 | 唯一有未知数的一条，故先做成可配置项而非直接改默认 |
| 预算 8→24（B3） | **中性（有前提）** | 前提是回传摘要 ≤15 行且明细落盘；A17 的担忧针对的是「不受控的长摘要」，不是任务数本身 |
| 结构规则机检（另议） | **提升** | 逐任务 Verifier 存在跨任务盲区，机检天然全量——这是 sustain-v3 已发生的真实缺陷 |

**没有一条是通过减少校验换速度的。** 被砍掉的全是等待、空转与超大任务的上下文税。

## 7. 不做

- **不做跨会话自动续跑驱动**——与 A17 结论一致：需要以 Claude Code 会话为操作对象的
  外部驱动器，超出工作区文字资产层与 `lib/` 平台中立边界。会话预算放大到 24 之后，
  一个 sustain-v3 规模项目 4 次 `/go` 已属可接受节奏。
- **不合并 Builder 与 Verifier 角色**——省一轮的代价是失去独立视角，
  而 `cross-task-debt.json` 的教训恰恰说明校验强度本就偏弱，不是偏强。
- **不删会话预算**——编排者上下文过载的风险真实存在，本评估只改阈值与其前提，不撤保护。
- **不把 Java/Spring 语义规则写进 `lib/`**——分层边界（CLAUDE.md 硬约束），
  这类规则只能落在 `templates/admin/workspace/hooks/`。
- **不对 sustain-v3 已完成的 20 个任务做回溯拆分**——已 done 的产出重拆无收益，
  拆分规则只对未来项目与未来模块生效。
