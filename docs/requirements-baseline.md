# vima 需求基线

创建日期：2026-08-16 · 出处：与用户对齐产出的需求基线（原件为 claude.ai artifact
`3e876414-0659-4393-ad6f-e650f3a2e2ef`，本文是它落进仓库的可 diff 正本）

八条需求、四条约束、两项排除。**每条附判据——怎么算满足，而不只是想要什么。**
此后所有设计必须能反查到这里的某一条；反查不到的即未授权复杂度。

编号稳定不重排，被合并的行保留并标注去向。

## 需求

### R1 从零散物料产出能跑的系统

起点大概率什么都没有——只有截图、旧代码、SQL、零散文档，且它们互相矛盾、互相取代。
要能整理成结构化需求，再一路做成系统。

- **判据**：**冷读通过**——新起一个 agent，只给它规格，看它能否开工、有无追问。
- **裁定**：物料形式不限（PRD / SDD / PACT 皆可）· 不要求完整继承 PACT ·
  **冷读作度量不作闸门**（跑、记分、展示，不拦）。
- **边界**：「这条需求对不对」**不做程序化确认**——它由人与 AI 讨论得出，默认人已审核。
  系统只**记录出处**（供 R6 回溯），不质疑内容。
- **实证**：上轮物料 112 文件 3.6MB，其中 76 张 PNG；SDD 只含 40/85 张表、
  API 覆盖 206/335 端点、原型覆盖 43/61 页且视觉与结构双失效。
- **v4 落地**：✅ 出处进 claim（顶层 `intent` 必填 `source`，其余层必填 `from`）；
  `vima-intake` skill 承接物料整理。
  ⚠️ **冷读度量未做**——「作度量不作闸门」这条裁定目前没有任何采集口。

### R2 观测平台（最高优先）

一个统一的观测面，回答五类问题。**五类必须共用一个数据底座**——分开做必然重演
「事实散在五处、join 靠人脑」。

| 问的是 | 要看到 |
|---|---|
| 这条做对了吗、凭什么 | 每条需求的证据与强度（分级——每条自己声明需要多强） |
| 整体做到哪、能交付吗 | 真实进度（不把「自称做完」计入）与可交付性判定 |
| 过程怎么走的、谁做的 | 历史回放 + Agent 行为（跑多久、读什么、产出什么） |
| 花了多少 | token 与时长，分摊到环节 / 代理 / 任务 |
| 哪些是 AI 替我定的 | 裁定台账，含置信度与影响面，**可二次裁决** |

- **判据**：五类问题**在同一个界面上**都能回答，且数据同源可对账。
- **裁定**：形态 web trace UI · 受众为自己看 + 对外展示交接 ·
  **「每条需求必须有可执行的验收方式」归入本条**（没有验收方式就产生不了证据，
  这一格永远是空）· 裁定须带置信度与影响面。
- **范围**：**本轮证据阶梯止于「跑了命令且绿」**——「真跑一遍界面」这一档不建采集设施
  （见 AR-1）。视觉正确性改由实现阶段的设计稿事前约束，见 R7。
- **实证**：上轮走验收链路的 21 个任务通过率 100%，没走的 87 个是 18%，
  而唯一信号是 doctor 一条 warn。
- **v4 落地**：✅ 五视图同源（总览 / 命题与证据 / 裁定台账 / 过程回放 / 成本），
  底座是同一条 `events.jsonl`；成本从 transcript 的 `usage` 求和并**诚实标为 derived**。

### R3 中途改需求，影响面是算出来的

改一处，能拿到「还有哪些地方跟着失效」的清单，不靠人估。二次裁决走同一条链路。

- **判据**：改完的标志是**失效清单清空**，不是人觉得改完了。
- **v4 落地**：✅ 命题定义变化 → 清证据 + 传播失效；`audit` 的 `summary.stale` 即失效清单；
  二次裁决（`ruling.overrides`）走同一条链路，不另设回滚。

### R5 并行加速

- **判据**：实际并发数**可观测**，且与计划并发数**可对账**。
- **实证**：上轮 20 个验收代理把 337 分钟压进 78 分钟（4.3×），
  但分波派发浪费约 3.5 倍——理论上限是 20×。
- **v4 落地**：📝 **判据后半句已改判**。v4 不是批次调度模型（没有「计划并发」这个对象），
  它靠租约排除做到「同一条命题同一时刻只派给一个执行者」。
  于是「与计划并发数对账」在 v4 里无对应物——**改判为：实际并发可观测即满足本条**，
  计划侧留待真出现调度器时再立。
  ✅ 前半句已做：`vima status`（人读面与 `--json` 两处）显示当前活跃并发、持有者
  与已过期租约数。
  ⚠️ **已知边界**：租约落在 `vima` 解析到的那个根，各 worktree 里的租约互相看不见，
  因此这个数字只在「所有执行者指向同一个根」时是真的。这一点在呈现处当场写明，
  不靠读文档。
  ⚠️ **Web 观测面暂不显示并发**：判活租约要读系统时钟，而 `front/web.mjs` 立着
  「不读系统时钟，同一输入必须同一输出」的渲染纪律。两者冲突未裁，本轮不硬塞——
  要接的话得先决定 Web 是否为「此刻态」开一个显式的时钟入口。

### R6 出问题能定位到是哪一步错的

- **判据**：任意症状能回溯到**第一条证据不足或与上游矛盾**的地方。
- **注意**：R1 修正后，回溯链要一路通到「当初从物料里就理解错了」与
  「熔合门当时怎么裁的」。
- **v4 落地**：✅ 事件流 append-only 可回放，命题带 `from` / `source` 链，
  裁定单列台账；Web「过程回放」按 actor 与时刻走。

### R7 产出企业风格化产品，风格统一可控

**骨相统一**（结构与交互范式写死）、**皮相可变**（颜色字体圆角项目级可换）。四层全管：

| 层 | 骨/皮 | 约束形态 |
|---|---|---|
| 信息架构 | 骨 | 导航结构 · 页面间跳转必须显式声明 · 权限点↔菜单成对 |
| 交互 | 骨 | **范式词表**：校验 / 错误反馈 / 空态 / 加载失败 / 行操作显隐，各若干种选一，不许自由发挥 |
| 版面 | 骨 | 版面词表 + 区块词 + 骨架组件 |
| 令牌 | **皮** | 阶梯定义 + 禁裸值；**阶梯本身可整体替换** |

- **判据**：四层各有**封闭**词表或阶梯 · **骨架自身也满足**，不得豁免自己。
- **裁定**：词表**宁宽勿窄**，尽量留足灵活性——风险不是词表大而是不封闭。
  **支持持续扩展**：缺词不阻塞，AI 可先用，但须记录进观测平台由人二次裁决收编。
  初值由既有项目实际写法归一化统计得出，不拍脑袋。
- **视觉落地**：实现阶段由 **Claude Design** 产出设计稿作为事前约束——把「做完再验」
  换成「照着稿做」，从验形挪到定形，成本低得多。两个档位：**高保真稿**（贵，视觉完整）
  与**框线图**（省，只管结构与信息层次）。框线图恰好对应骨相，皮相由令牌阶梯自动管，
  是默认档。
- **实证**：有词表的层可机检（区块对账成立），没词表的层不可机检：89.8% 页面错误提示静默、
  12/45 页校验形同虚设、同一契约缺口四种处置；反向代价也实测过——48 页里 19%
  因词表不够被迫降级。
- **v4 落地**：✅ 四层齐备且封闭（`tokens/*.json` 皮 + `layout` / `interaction` / `ia`
  三份 vocab 骨），规则层明写「不许加 other / custom / misc」逃生口。
  ⚠️ **「骨架自身也满足」未做**：vima 自己的 Web UI 不消费这三份词表，
  即工具豁免了自己。这条判据成立且尚未兑现——不假装满足。
  ⚠️ **Claude Design 两档设计稿未接线**：v4 没有对应工序。
  ⚠️ 词表初值目前是人工拟定，不是「由既有项目实际写法归一化统计得出」。

### R9 存量项目接管

两种都要：接管**从未用过 vima 的陌生代码库** + 升级旧 vima 项目。

- **判据**：陌生库接管后能产出完整命题图，且反推的命题
  **来源可标最高档、验证强度不得自动继承**。
- **理由**：这个区分不做，接管等于**把既有缺陷追认成规格**——「读得到空数据」
  「规则零执行点」「契约字段恒空」全会被反推成「需求本来就这样」。
- **v4 落地**：✅ 双轴分离正是这条的兑现：来源 S 轴（`fact` 可标最高）与
  验证 E 轴（必须重新挣）正交，反推命题拿不到白送的 E 轴强度。
  `vima-adopt` skill 承接陌生库接管。

### ~~R10 成本可观测~~ —— 已并入 **R2**

### R11 可复用业务块库

成套的业务功能块，按端分集，**持续扩展**。起点三类只是起点不是全集：
后台管理（配置 / 角色 / 菜单 / 人员 / 部门 / 字典 / 日志）· 微信生态
（登录 / 支付 / 分享 / 订阅消息）· 通用能力。

**它的价值不是省 token，是把这些问题从命题空间里整个移除**——已经被验过的东西
不需要再命题、再取证、再验收。

- **分层**：**L1 契约 · L2 后端 · L3 前端行为**（纯逻辑无视觉）跨项目稳定；
  **L4 视觉默认不提供**——带了会与 UI 设计代理冲突。
- **判据**：加一个块**不需要改内核** · 块不含 L4 也能被完整消费 · **拿错端的块是机检项**。
- **收录**：同时满足「语义跨项目稳定」+「实现有标准解」。反过来说更清楚：
  *两个不同行业的项目都会用到它、且用法基本一致*。业务特有的不进。
- **裁定**：L1–L3 是骨、L4 是皮——**这是 R7 原则往上提了一层**，不是新规则。
- **v4 落地**：✅ 加块不改内核（`assets/blocks/<set>/<name>/` 目录即注册）；
  ✅ 不含 L4 也能被完整消费（`next` 按层裁剪下发 L1/L2/L3）；
  ✅ 拿错端的块是机检项（`checkAssets` 判 `block.sides` ∩ `config.apps[].kind`，
  `audit` 报 `block-side-mismatch`）。
  ⚠️ **内容侧几乎为空**：资产仓当前只有 1 个块（`admin/role-management`），
  `common/` 与 `wechat/` 是空目录。机制齐了，料没有——「供料」这条支柱目前供不出东西。

## 约束

不是需求，但约束所有设计。

### C1 执行者会偷懒、会自称完成

机制必须假定这一点。

- **实证**：43 个任务都写了「Service 层单元测试」验收项，实际覆盖 0/58，而 `mvn test` 恒绿。
- **v4 落地**：✅ 官方接口不采信自述——`submit` 只收 claimId，证据内容由系统生成；
  E 轴最弱档 `claimed` 恒可分辨。证据策略强制 `expects` 非空
  （只看退出码等于没有策略：退出 0 的命令太容易造）。
  **边界**：这挡 T1（自述通道），不挡 T2（拥有 Write 的 agent 直接改事件流）——
  见 ARCHITECTURE 纪律 0。

### C2 防过度设计

每处设计能反查到 R1–R11 的某一条。反查不到 = 未授权复杂度。
约束别扩面 · 抽象别提前 · 字段表别镀金。

### C3 文档可读、可 diff、可 code review

现有形态最值得保的性质。任何索引/图都必须是可随时重建的派生物，不能反过来当真源。

### C4 设计与开发阶段不阻塞

需要人裁定的一律先由 AI 定夺并记录，人事后推翻。

- 前提是记录够硬：**显式落盘**（不能写在代码注释里）· **可见**（观测平台）·
  **可推翻**（触发失效传播）。
- **实证（反面）**：builder 自行裁定设备状态枚举，理由写在 `types.ts` 注释里，
  导致三条写路径 100% 被拒——问题不在自行裁定，在**斩了没奏**。
- **v4 落地**：✅ `ruling` 事件强制 `confidence` 与 `blastRadius`，
  `overrides` 走同一条失效传播链路。

## 明确排除

排除是决定，不是遗漏。

| 项 | 理由 |
|---|---|
| 多人多会话协作 | 当前范围是「一个人 + 一个会话内的多个子代理」。纳入会把并发控制升级成真正的分布式问题 |
| 业务块的版本与兼容 | 「支持不断扩展」指的是注册表开放性；版本管理是另一件事，未提出即不做 |

## 裁定台账

对齐过程中做出的决定与理由。

| 涉及 | 决定 | 理由 |
|---|---|---|
| R1 | 不要求完整继承 PACT | 判据是「产出的物料能让 AI 稳定工作」，形式不限 |
| R1 | 熔合门自行定夺 | 多来源矛盾由 AI 裁定并记录，不停下来问人。配 C4 的三条硬要求 |
| R1 | 冷读门降为度量 | 与 C4 不阻塞冲突。跑、记分、展示，不拦 |
| R2 | 吸收原 R4 / R8 / R10 | 四者是同一件事的四个面，共用一个底座是需求而非优化 |
| R2 | 「需求必须有可执行验收」归入 | 它不是独立门禁，是观测平台的前置条件——没有验收方式就产生不了证据 |
| R2 | 裁定须带置信度与影响面 | 展示的必要精度。200 条流水账人不会看；同理于「永远消不掉的告警会训练人忽略整张表」 |
| R7 | 词表宁宽勿窄 | 风险不是词表大而是不封闭；10 个词和 40 个词可机检性相同，而窄词表会逼出逃生口 |
| R11 | 视觉层默认不提供 | 真实前端会与 UI 设计代理冲突。分层后设计代理消费 L3 行为契约、自产 L4 |
| R2 · R7 | 不做「真跑界面」这一档 | 本轮成本不划算。视觉转由 Claude Design 事前约束；行为仍靠跑测试覆盖。风险记为 AR-1 |
| R1 | 需求正确性不做程序确认 | 由人与 AI 讨论得出，默认已审核。系统只记录出处供回溯，不质疑内容 |
| 全局 | 两条生长通道：扩词 · 沉淀 | 形状相同——缺什么不拦路，但缺这件事必须留痕；累积的留痕就是该往哪长的证据 |

| 涉及 | 决定 | 理由 | 日期 |

| R5 | 判据后半句「与计划并发数可对账」不适用 | v4 不是批次调度模型，没有「计划并发」这个对象。前半句「实际并发可观测」照做；计划侧留待真出现调度器时再立 | 2026-08-16 |

## 已接受的风险

裁定为不做，不等于问题消失。

### AR-1 运行期行为正确性缺一档证据

「真跑一遍界面」这一档本轮不建采集设施。视觉正确性改由 Claude Design 的设计稿
**事前约束**覆盖——从验形挪到定形，成本低得多。

- **代价**：设计稿约束的是「**长得对不对**」，管不了「**行为对不对**」。上轮那批缺陷
  设计稿一个都看不出来：12/45 页 `:rules` 写了不调 `validate()`（类型正确、语法正确、
  构建全绿、*行为*错误）· 89.8% 页面错误提示对用户静默 · 主入口因解包路径写错而打不开。
- **缓解**：**E3 保留且必须加强**——R7 交互层判据仍是「跑测试证明校验真的拦住提交」。
  放弃的是最上面那一档，不是所有运行时验证。若 E3 也不做，R7 交互层就落空了。
- **复议**：当出现「测试全绿但用户说用不了」的实例时，重新评估。
- **v4 落地**：✅ E 轴最高档 `observed` 接口留着，调用时**如实返回未实现**，
  绝不降级用 `executed` 冒充。E3（跑测试）由 `executed` + policy `expects` 承接。
