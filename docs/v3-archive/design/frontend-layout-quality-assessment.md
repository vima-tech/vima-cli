# 前端版面质量评估：页面「不精致 / 凌乱 / 撑不满 / 溢出」的根因与改造建议

> 创建日期：2026-08-14
> 问题（用户提出）：Sustain 开发下来，很多页面排版不精致、不紧凑、有凌乱感、内容撑不满
> 或直接溢出。这是 UI 框架的限制导致的吗？是否应当**放弃 UI 框架、全部走 Claude Design
> MCP**，让页面更灵活、更有「设计感」？同时想给 vima-cli 增加前端开发约束，并在 `/go`
> 末端加一轮页面冒烟测试。
> 方法：对 **Sustain 重建后的 68 个页面**逐文件静态量测 + 模板/vendored 框架源码逐层核对；
> 数字全部来自最终版检测命令，不用探索期粗筛。本文只评估与建议，**不改任何代码**。
> 结论一句话：**不是 UI 框架限制导致的。凌乱恰恰发生在框架「没管」的那一半——
> 版面层是空的，于是 59 个页面各写各的 8572 行布局 CSS。**

---

## 一、实测证据

### 1.1 页面根契约执行得不错，但页面**自己写版面**的量极大

| 指标 | 实测值 | 说明 |
|---|---|---|
| 业务页面总数 | **68** | `apps/admin/src/views/**/*.vue` |
| 页面根挂 `vui-page` | 65 / 68 | 框架页面骨架契约执行率 96% |
| 带 `data-page` | 50 | 其余为壳层/子组件页 |
| **带 `<style>` 的页面** | **59** | 87% 的页面有私有样式 |
| **页面私有样式总行数** | **8572 行** | 均 **145 行/页**，最大单页 **970 行** |
| 自己写 `display:flex` | 48 页 | |
| 自己写 `display:grid` | 20 页 | |
| 自己写 `height:` | 27 页 | |
| 自己写 `overflow` | 22 页 | |

> 复现：`find apps/admin/src/views -name '*.vue' | wc -l`；
> 各项为对 `<style>` 块的正则统计（脚本见本文 §5.3 的同款探针思路）。

### 1.2 令牌纪律不差，但**版面刻度是散的**

| 指标 | 实测值 | 理想 |
|---|---|---|
| 页面样式里引用 `var(--v-*)` | **832 次** | —— |
| 页面样式里写死 px 数值 | **173 次** | 0 |
| **不同的间距取值种数** | **36 种** | 5 种（`--v-gap-xs/sm/md/lg/xl` = 4/8/12/16/24） |
| **不同的字号取值种数** | **14 种** | 6 种（令牌只定义 6 档） |

间距高频值：`14px×10 · 4px×9 · 12px×8 · 10px×7 · 2px×7 · 8px×6 · 6px×6 · 3px×5 · 26px×5 · 20px×5 …`

**这一行数据就是「不紧凑 / 凌乱」的量化定义**：83% 的取值走了令牌，可剩下的 17% 把
刻度从 5 档撑成了 36 档。人眼看到的「凌乱」，本质是**同一屏里出现了 6 种不同的间距**。

### 1.3 「撑不满 / 溢出」那批缺陷的**修法早已在框架里**

`vendor/vima-ui-admin/dist/styles/components.css` 现有契约：

```css
.vui-page > *                                  { flex-shrink: 0 }        /* 内容超屏不压扁上方模块 */
.vui-page > .vui-card                          { margin-bottom: 0 }      /* 间距只由页面根 gap 给 */
.vui-page > .vui-card:last-child > .vui-card-body { flex: 1 1 auto; min-height: 0; overflow: auto }
.vui-page > .vui-card:last-child > … > .vui-table { flex: 1 1 auto; min-height: 0 }
```

外加 `src/styles/base.css` 与框架 `ui.css` 各有一处全局 `box-sizing: border-box`。

这四条正是历史上那批「顶部模块被压扁 / 页底 150–354px 空洞 / 内容 content-box 溢出」
缺陷的修法，**已经回流进 vendored 框架**。也就是说：

> 这一类缺陷的根因是**框架的页面骨架契约当年不完整**，修法是**加强契约**，不是拆掉框架。
> 而且修完之后**没有任何守卫**——新写的页面照样可以在自己的 `<style>` 里
> 写 `height: 100%` / `overflow: hidden` 把它推翻，没有一条机检拦得住。

### 1.4 「捆着手脚」的真实来源：**规格词表**，不是组件库

`admin-web` 的区块词表只有 7 词：`toolbar search table form cards tabs pagination`。

sustain-v3 规划期实测（`~/projects/Sustain/docs/vima-cli-评估_规划期实测.md` §三）：

> **48 个页面中有 9 个（19%）必须降级表达，且恰好是本系统最有价值的页面。**
> 无对应词的版面：三栏外壳 / sticky 侧栏 / 步骤条 / 折叠面板 / 锚点条 / 时间轴 / 图表 / 拖拽画布。
> 无法声明的交互：抽屉（4 处全部降级成弹窗）、页内页签切换（19 处）、滚动锚点、
> 打印导出、全屏、行内编辑、级联联动。

**注意这一条的性质**：被卡住的是 `docs/spec.md` 能不能**说出**这个版面，
与 `vima-ui-admin` 有没有这个组件**无关**。用户感到的「捆着手脚」，
绝大部分发生在**规划期表达**，而不是编码期渲染。

## 二、根因三层（互不重叠，需要分别解）

| 层 | 缺什么 | 表现 | 证据 |
|---|---|---|---|
| **L-A 版面层空缺** | 框架管到「页面外壳 + 组件」就停了，**没有版面原语**（两栏 / 主从 / 看板 / 表单页），也没有密度规范 | 59 页各写 8572 行布局、36 种间距刻度 | §1.1 §1.2 |
| **L-B 规划期无版面意图** | `vima:page` 只声明「这一页有哪些区块」，不声明「怎么排」——几栏、谁主谁次、谁撑满、密度、视线动线；原型渲染出的是**线框**，人审只看得见「有没有」，看不见「排得对不对」 | 「页面没有灵魂 / 缺少整体设计」 | `vima:page` 块字段；`render-prototype` 产物形态 |
| **L-C 词表表达力不足** | 7 词说不出真实版面与交互 | 19% 页面被迫降级，且是核心页 | §1.4 |

**三层都不是「UI 框架限制太死」。** L-A 与 L-B 恰恰是**约束太少**，L-C 是**规格词汇太少**。

## 三、逐条评估用户的四点思考

### ① 「排版不精致 / 不紧凑 / 凌乱 —— 是 UI 框架的限制导致的吗？」

**不是。判据在 §1.2：** 页面已经在自由发挥（17% 的取值绕开令牌，把 5 档刻度撑成 36 档）。
凌乱发生在**自由的那一部分**，不在框架约束的那一部分。

框架该背的责任是另一条：**它只提供了 5 档间距令牌与 6 档字号，没有提供「版面密度」这一层
语义**（紧凑表格 / 标准表单 / 宽松详情各该用什么刻度）。开发者找不到语义档，
就只好自己写 `10px`、`14px`、`26px`。**缺的是刻度的语义，不是刻度的自由。**

### ② 「内容撑不满 / 直接溢出」

**不是框架限制，是框架契约曾经不完整——现已修复，但缺守卫。** 见 §1.3。
现状是：修法在框架里，页面却可以在自己的 `<style>` 里推翻它，**且没有任何机检**。
这一条是**当前最容易见效**的缺口。

### ③ 「想给 vima-cli 增加前端开发约束」

**方向正确，但落法决定成败。** vima-cli 已经有一份 `coding-standards.md`
（A6「规范执行者阶梯」要求每条规范标注「谁保证它」）。当前前端约束里
**大量条目挂在 L5·verifier（人/子代理判定）**——而版面问题恰恰是子代理最判不准的一类
（它看不见渲染结果）。

> **建议的硬判据：凡是加进来的版面约束，必须能落到 L1（框架吸收）或 L3（机检），
> 落不到就先别加。** 一条只能靠 verifier 目测的「页面要紧凑」，等于没加。

### ④ 「在 /go 末端加一轮前端页面冒烟测试（排除脚手架自带页面）」

**这是四点里价值最高的一条，且完全可行。** 详见 §5。三个关键判断：

1. **「排除脚手架自带页面」不需要新配置**——业务页天然带 `data-page`，壳层页天然不带，
   现成的判据直接用。
2. **不要截图给模型看**（token 贵且判不准）。用**量化探针**（溢出量、页底空洞、间隙、
   刻度合规）产出 JSON 报告，`bad = 0` 时 Agent 一个字都不用读。
3. 它是 A20 收口闸门的天然一环：`converge`（跨任务集成对账）之后、进 MAINTAINING 之前。

## 四、关于「放弃 UI 框架，全部走 Claude Design MCP」

### 4.1 结论：**不成立**，但直觉指向的缺口是真的

四条否决理由，按强度排序：

1. **反证据最直接**：Sustain 的页面**已经**有一半是自由发挥（8572 行私有布局），
   而凌乱就长在这一半上。放弃框架 = 把自由度从 ~50% 提到 100%，
   36 种间距会变成 60 种。**「缺少整体设计」的解药是更强的共同约束，不是更少的约束。**
2. **确定性硬约束**：`CLAUDE.md` 第一条——「凡能用文件系统 + 确定性代码解决的，
   不留给 Agent 概率性行为；渲染器禁止嵌入时间戳/随机数，同一输入必须字节一致」。
   Design MCP 是**联网 + 登录 + 云端项目**的托管服务（实测其接口形态：
   `create_project` 返回 project UUID、`render_preview` 返回短时效
   `*.claudeusercontent.com` 链接）。它无法在离线 / CI / 批次并行里保证同输入同字节。
3. **修法没有落点**：§1.3 那四条契约是「一处改、68 页全好」。没有框架层，
   同样的修法要在 68 个页面里各打一遍，且下一批新页面继续犯——
   这正是 sustain-v3 时代发生过的事。
4. **一致性无从保证**：MCP 逐页产出的是**一次性 HTML**，跨页的间距刻度、控件尺寸、
   状态色没有任何机制强制统一——而「整体设计感」的技术定义**就是跨页一致**。

### 4.2 但 Design MCP 应该进来——进**规划期**，不进运行时

正确的位置是 **L-B 层**（§2）：让它产出**版面设计意图与参考页**，人审后**固化成本地的、
确定性的资产**（版面词表 + 密度令牌 + 版面原语类），再由现有渲染器与框架落地。

| | ❌ 放弃框架，运行时逐页走 MCP | ✅ 规划期用 MCP 产出设计真源 |
|---|---|---|
| 确定性 | 每次结果不同 | 一次产出，固化成文件后字节稳定 |
| 离线 / CI | 不可用 | 只在规划期需要网络 |
| 跨页一致 | 无保证 | 由固化的令牌与版面类保证 |
| token | 40+ 页每次改需求重设计 | 一次性，之后零消耗 |
| 产物归属 | 云端项目 | 仓库内文件，可 diff、可机检、可 `vima update` |

**一句话**：Design MCP 是**设计真源的生产工具**，不是**运行时的渲染器替代品**。

### 4.3 与在途 A26（`custom-web`）的关系

并行工作中的 A26 草案（`docs/design/a26-custom-frontend-draft.md`）已经在把
「框架不提供 UI、也不规定 UI」立项为**第四种模式** `custom-web`——**并列**，不是取代前三种。
用户的诉求有一半已经在那里被承接。

**但必须提醒一条**：`custom-web` 把 UI 自由度开到 100%，
在没有 §2 的 L-A / L-B 配套时，它会**放大**本文诊断的凌乱问题，而不是缓解。
建议：`custom-web` 尤其**必须**接入 §5 的页面冒烟——它是四种模式里最需要机检兜底的一种。

## 五、建议清单

> 每条标注**执行者层级**（A6 阶梯）：L1 框架吸收 / L3 机检 / L5 人审。
> **落不到 L1 或 L3 的条目一律不建议加**（见 §3 ③）。

### 5.1 A 组 · 版面层（框架侧，见效最快）

| 编号 | 建议 | 层级 | 判据 |
|---|---|---|---|
| **P1** | **间距与字号刻度语义化**：在 `--v-gap-*` 之上补「版面密度」三档（`compact` / `default` / `loose`），并给出「表格用哪档、表单用哪档、详情用哪档」的对照表 | L1 | 页面样式里不同间距取值种数 ≤ 8（现 36） |
| **P2** | **页面私有样式里禁止裸尺寸**：`gap/padding/margin/font-size` 只允许 `var(--v-*)` 或 `0`；现有 173 处裸 px 逐条收编 | L3·hook | post-write 扩一条（与既有裸色值机检同构） |
| **P3** | **版面原语进框架**：把 20 个页面自写的 grid 收编成 3–4 个版面类（两栏 `vui-layout-split`、主从 `vui-layout-master`、看板 `vui-layout-board`、表单页 `vui-layout-form`），各自带响应式断点与密度 | L1 | 页面自写 `display:grid` 的数量下降 |
| **P4** | **页面骨架契约补齐 + 反向机检**：现有 §1.3 四条之外，补「页面根不许被页面私有样式覆写 `height/overflow`」 | L3·hook | 带 `data-page` 的页面 `<style>` 里出现 `height`/`overflow` 作用于根类 → 拦 |

### 5.2 B 组 · 规划期版面意图（解「没有灵魂」）

| 编号 | 建议 | 层级 | 判据 |
|---|---|---|---|
| **P5** | **`vima:page` 增版面意图**：`layout` 从「区块序列」升级为带意图的声明——栅格（几栏/列宽）、主次（哪个区块是主体）、撑满（谁 `flex:1`）、密度档。A14 的 `regions` 已经开了这个口子，本条是把它从「可选分栏」扩成「必填版面意图」 | L3·validate | 每个业务页必须声明主体区块与密度档，缺 → error |
| **P6** | **原型渲染器从线框升级为版面草图**：按 P5 的意图渲染真实栅格与撑满关系，让人审看得见「排得对不对」而不只是「有没有」 | L1·渲染器 | 原型 `--check` 字节确定性不变 |
| **P7** | **人审清单增「版面评审」一栏**：主体区块是否撑满、密度档是否与页面类型匹配、是否有三栏以上（手机/窄屏必然崩） | L5 | `approve` 前置项 |

### 5.3 C 组 · 词表扩容（解「捆着手脚」，直接引用 19% 降级清单）

| 编号 | 建议 | 层级 |
|---|---|---|
| **P8** | 区块词补：`steps`（步骤条）、`collapse`（折叠面板）、`anchor`（锚点条）、`timeline`（时间轴）、`chart`（图表占位）、`aside`（sticky 侧栏） | L3·validate 词表 |
| **P9** | 交互补：`drawer`（抽屉，现被迫降级成弹窗 4 处）、`print`（打印导出）；页内页签的「切换后加载什么」需要能声明（19 处失真） | L3·validate |
| **P10** | 每加一个词，必须同时给：kind 词表配置 + `componentMap` 映射 + 组件文档 + 原型渲染器画法 + checklist 镜像（A16 已定的三处同步纪律） | L3·单测闭包 |

### 5.4 D 组 · 机检与冒烟（守住成果）

| 编号 | 建议 | 层级 |
|---|---|---|
| **P11** | **`/go` 末端页面冒烟**（详见 §6） | L3 |
| **P12** | **页面私有样式预算**：单页 `<style>` 超过 N 行（建议 80）→ warn。145 行/页是「版面层缺失」的信号，不是罪证；预算的作用是**把压力顶回 P3** | L3·validate |

## 六、`/go` 末端页面冒烟测试的设计

### 6.1 位置与触发

`/go` 步骤 5 的收口闸门内：`vima converge`（A20 跨任务集成对账）**之后**、
进入 MAINTAINING **之前**。与 A20 的修复循环同一个回合——冒烟发现的问题按 `byTask` 归组
派回对应任务修，最多 N 轮。

### 6.2 测哪些页面（用户要求：排除脚手架自带页面）

**判据现成，零新增配置**：只测**带 `data-page="PAGE-xx"` 的页面**。
业务页由任务按 spec 生成，天然带；脚手架自带的壳层页（登录、404、个人设置、
mp 的 home/mine、h5 的 Home/Mine）天然不带。

路由发现：从 `router/index.ts`（h5/admin）或 `app.json` 的 `pages`（mp）取，
与页面文件的 `data-page` 求交集。

### 6.3 探针（**不截图、零 LLM**）

对每个页面在 375 / 1280 / 1920 三个视口各跑一遍，逐条量化：

| # | 探针 | 判据 | 对应的用户抱怨 |
|---|---|---|---|
| 1 | **横向溢出** | `scrollWidth - clientWidth > 1` 且祖先链无 `overflow-x: auto` | 「直接溢出了页面」 |
| 2 | **页底空洞** | 页面无纵向滚动，且末子元素底边到容器底 > 120px | 「没有撑满页面」 |
| 3 | **元素被裁** | `scrollHeight > clientHeight` 且 `overflow: hidden` | 「内容被裁掉半截」 |
| 4 | **间隙异常** | 相邻兄弟间距 > 40px 或同层间距种数 > 3 | 「凌乱感」 |
| 5 | **刻度合规** | 计算样式的 `gap/padding` 不在令牌取值集合内 | 「不紧凑」 |
| 6 | **控件重叠** | 相邻兄弟 bounding box 相交 | 明显 bug |

> 这套探针在真实项目里跑过：51 条路由两轮，定位速度远快于截图，
> 截图只用于最后确认观感。

### 6.4 数据与依赖边界（两条硬约束都不破）

- **零运行时依赖不破**：Playwright 属**骨架的 devDependency + 一个 npm script**
  （模板资产），**不进 `lib/`**。vima-cli 只负责「调用 + 读 JSON 报告」，
  与 A7 运行时证据的分工完全同构。
- **造数零成本**：stub `fetch`/`wx.request` 直接返回**契约里的 response 示例**——
  契约本来就是真源，不需要额外造 mock。
- **诚实降级**（照抄 mp 采集器纪律）：浏览器/依赖不在场时**不写报告文件**，
  `/check` 如实报「本端无版面冒烟通道」。**空报告会被读成「跑过且零问题」，比没有更糟。**

### 6.5 产物

`.vima/reports/layout-smoke[.<appId>].json`：

```json
{ "schemaVersion": "1", "viewport": [375, 1280, 1920],
  "pages": [ { "page": "PAGE-07", "route": "/patient/list", "task": "page-07-fe",
               "findings": [ { "probe": "overflow-x", "value": 30, "selector": ".opt-card" } ] } ],
  "bad": 0 }
```

`bad = 0` 时 Agent 不读正文；`bad > 0` 时按 `task` 归组派修（与 A20 `byTask` 同款）。

## 七、不做（防止本文被当成「什么都加」的许可）

- **不放弃 UI 框架**（§4.1 四条理由）。
- **不把 Design MCP 接进 `/go` 运行时**——它进规划期，产物必须固化成仓库内文件。
- **不做截图 diff 进 `/go`**：像素级 diff 在多端 × 多视口下噪声极大，且每次都要人看。
  量化探针 + `bad>0` 才升级到截图，才是可持续的。
- **不给版面意图做「自动布局算法」**：让 AI 自己决定几栏、谁撑满，等于把 L-B 的
  设计决定权又交回概率性行为——那正是「没有灵魂」的成因。**版面意图由人在规划期定，
  机器只负责渲染与守卫。**
- **不为本文的任何一条加「只能靠人目测」的规范**（§3 ③ 的硬判据）。

## 九、补评：「UI 框架只约束风格，不约束表达形式」

> 追加日期：2026-08-14
> 用户第二轮表述：admin 脚手架带的业务必需功能与整体 layout、默认页面**应当保留**；
> 但其他 UI 组件**限制太死**，让 AI 只能用组件实现页面。期望 **UI 框架只做样式与风格的
> 约束**——保证不同业务页面风格一致，相同组件在不同场景下可以有细节差别而不是千篇一律；
> **约束的目的是统一风格，不能因此丢掉功能最佳实践与表达形式的灵活性**。

### 9.1 判定

**这一版表述成立**，而且比第一轮（「放弃 UI 框架」）精确得多——它把刀口从
「要不要框架」挪到了「框架该约束哪一层」，这正是对的问题。

**但有一个前提认知需要校正**，校正之后改造点会落在完全不同的地方。

### 9.2 校正：「只能用组件」不是机检强制的——一条这样的规则都没有

| 核查项 | 实测结果 |
|---|---|
| `validate` 里与「必须使用组件」相关的规则 | **0 条** |
| `post-write` 实际拦截的内容 | 导入方式（深路径/幻包名）、原生 `confirm/alert`、页面根类、裸色值、图标名、操作列 width——**全是风格与契约，无一条关于「用不用组件」** |
| Sustain 实测：手写 `<table>` 的页面 | **1 个**（说明手写既被允许、也确实发生过） |
| Sustain 实测：`VCard` vs 手写 `.card` 类 | 63 页 vs **23 页**（近三分之一的页面已经在手写容器） |

**结论：你要的「只约束风格、不约束表达」在机检层面其实已经成立了。**

那被捆住的感觉从哪来？三处**供给侧**，不是机检侧：

1. **`vima context` 只喂组件文档。** 任务上下文包里的「组件文档切片」是按 `componentMap`
   映射出来的——AI 拿到的可用材料**只有组件**，它当然只会用组件。
2. **区块词表只有 7 词**（§1.4），spec 说不出别的版面，任务描述里自然也只有这些。
3. **规范语气**：`coding-standards.md` 写的是「组件已全局注册，模板直接用」，
   读起来像「只能用它」。

**而更要命的是第四处，也是本节的核心发现：**

> **admin 端没有类契约层。** 于是现状是一个**二选一**：
> **用组件 → 风格统一；不用组件 → 完全裸奔**（→ 59 页 8572 行私有样式、36 种间距刻度）。
> AI 面对这个二选一，选组件是理性的。
> **「只约束风格不约束表达」在技术上要成立，前提是先有一个与组件平行的类契约层**——
> 让「不用组件」也有一条合规的路可走。

### 9.3 现成的对照：两端形态不对称

| 端 | 组件 | 类契约 | 令牌 | 形态 |
|---|---|---|---|---|
| `admin-web` | **63 个** | **0** | 83 | 纯组件——不用组件即裸奔 |
| `mp-native` / `h5-mobile`（A23/A25） | 0（h5 有 4 个行为组件） | **112 个类** | 75 | 纯类契约——风格由类与令牌保证，结构完全自由 |

移动端两个 kind 已经是你想要的形态：**框架只给样式与结构约定，页面自己组合**。
admin 端缺的正是这一层。**你的诉求 = 把 admin 端补成「组件 + 类契约」双供给**，
而不是把组件拿掉。

### 9.4 但组件不能整体降级——40/63 承载的正是你说的「功能最佳实践」

| 组件交互面 | 数量 | 说明 |
|---|---|---|
| **≥4 个 props 或带 events** | **40 / 63** | 承载交互状态机、无障碍、数据契约 |
| props < 4 且无 events（近似纯视觉） | 23 / 63 | 主要在 `layout`(9) / `feedback`(4) / `basic`(4) 三类 |

举例：`VTable` 的 props 有 16 个（列设置、分页、树形、拖拽、导出、行选中…），
其中「操作列按行内按钮文案自动算宽」是 L1 已吸收的最佳实践——手写 `<table>` 会全部丢掉。
**所以正确做法是分级，不是一刀切：**

- **contract 级**（约 40 个）：涉及交互状态机 / 无障碍 / 数据契约 → **仍应优先用**，
  手写等于重造并丢掉最佳实践；
- **style 级**（约 23 个）：纯视觉容器（`VCard` `VDivider` `VBadge` `VAlert` `VEmpty`
  `VRow/VCol` 等）→ **明确允许用类契约替代**，页面自由组合结构。

### 9.5 「相同组件风格类似、场景不同可有细节差别」怎么落地

这是本节最微妙的一条。现状是**变体轴极窄**：

```
VCard   → 只有 shadow=always|hover|never
VButton → type / size
VTable  → size
VForm   → layout=horizontal|vertical|inline
```

**没有任何一个组件有「密度」轴。** 于是「场景不同要有细节差别」在现状下只有两条路：
要么全都一样（千篇一律），要么在页面里自己改样式（风格漂移）——**这正是 36 种间距的来源。**

**正确的机制是「受控变体」而不是「自由发挥」**：

- 给关键组件补**变体轴**：`density`（compact / default / loose）、`tone`、`emphasis`；
- 在组件文档里写清**何时用哪个变体**（密集数据表用 compact、录入表单用 default、
  只读详情用 loose）——让 AI 有依据做差别；
- **判据**：差别来自**声明的变体**（可机检、可复现、跨页一致），
  而不是来自页面私有样式（不可检、不可复现）。

> 一句话：**「不千篇一律」的反面不是「随便长」，而是「有限且有依据的变体」。**

### 9.6 建议清单（续 §5 编号）

| 编号 | 建议 | 层级 | 判据 |
|---|---|---|---|
| **P13** | **admin 端补类契约层**（对位移动端的 112 类）：版面类、容器类、字段行类、工具条类、状态块类。让「不用组件」有一条合规的路 | L1 | 页面私有样式行数下降；间距取值种数 ≤ 8 |
| **P14** | **组件分级进 `ai-manifest`**：每个组件加 `tier: contract \| style`；`style` 级在文档中明确写「可用 `.vui-*` 类替代，二者风格等价」 | L3·单测 | 63 个组件 100% 有 tier；tier 与文档措辞一致 |
| **P15** | **`vima context` 供给侧改造（本节最关键的一条）**：任务上下文包里除组件文档外，追加「类契约与令牌速查」+「本页可用的表达形式菜单（组件 / 类 / 何时各用哪个）」。**现在只喂组件，就只会得到组件** | L1·打包器 | 上下文包新增一节；字节预算内 |
| **P16** | **关键组件补密度轴与场景预设**，文档写明「何时用哪个变体」 | L1 + L5 | 每个 contract 级组件至少有一条「场景 → 变体」对照 |
| **P17** | **把机检口径写死为「风格合规」**：拦裸色值 / 裸刻度 / 裸字号 / 自写结构未挂原语类；并在 `coding-standards.md` 与 hook 注释里**显式写明「不检查是否使用了组件」**——消除语气造成的误解 | L3·hook | 现有 173 处裸 px 收敛；规范文本无「只能用组件」歧义 |

### 9.7 边界（防过度设计）

- **不新增 kind。** 本节是 `admin-web` 的**演进**（补一层供给），不是第五种模式。
  与在途 A26 `custom-web` 的区别要写清：`custom-web` 是**框架什么都不给**（项目自带 UI）；
  本节是**框架给风格、不给表达形式**。两者不可合并——前者连令牌都没有。
- **不删任何 style 级组件。** 分级只改变「文档怎么说、context 怎么喂」，
  不删代码——存量 63 页在用 `VCard`，删了就是破坏性变更。
- **不做「组件用量」指标。** 用得多用得少都不说明质量；要量的是**风格一致性**
  （间距种数、裸值数、跨页刻度偏差），不是组件覆盖率。
- **不把变体轴做成开放式**（如任意 `style` 透传）。开放式变体 = 自由发挥换个写法，
  §9.5 的判据立刻失效。

### 9.8 对第一轮结论的修正

第一轮（§三/§四）的结论不变——**根因仍是「版面层空缺」而非「框架限制」**。
本节补上了它的另一半，两条合起来才是完整因果：

> **框架只在「用组件」这条路上提供了风格保证；一旦离开这条路就完全没有保证。
> 于是要么被捆住（只能用组件），要么放飞（8572 行私有样式）。
> 两个症状同源——缺的是同一层东西：与组件平行的类契约层。**

这也解释了为什么第一轮那个「放弃框架」的直觉会产生：**它想解决的是真问题，
但把「补一层」误判成了「拆一层」。**

## 十、补评：「千业千面」——不同行业换风格，核心功能与脚手架接口不变

> 追加日期：2026-08-14
> 用户第三轮表述：希望在不同行业做到**千业千面**（包括脚手架自身的风格样式），
> 但**核心功能与脚手架接口不变**。是否可行？vima-cli 是否需要大动？

### 10.1 结论

**可行。vima-cli 不需要大动——卡点不在 vima-cli 里，在 vendored 的组件库。**

判据是一个可以直接量的东西：**「视觉决定有多少已经在令牌里，多少写死在样式里」**。

### 10.2 实测：换肤就绪度逐层体检

| 层 | 归谁管 | `var()` 引用 | **字面色值（换肤死角）** | 令牌数 | 换肤可行性 |
|---|---|---|---|---|---|
| 骨架外壳 `shell.css`（1386 行） | **vima-cli 模板** | 247 | **1 处** | —— | ✅ 已就绪 |
| 骨架 `base.css` / `style.css` | vima-cli 模板 | 34 | 3 处 | —— | ✅ |
| 骨架令牌 `tokens.css` | vima-cli 模板 | —— | 72（**令牌定义本身**） | **83** | ✅ 换肤入口现成 |
| 17 个内置脚手架页面 | vima-cli 模板 | —— | **30 处，全在 `login/index.vue`**（其余 16 页为 0） | —— | ✅ 修一个文件 |
| **vendored `vima-ui-admin`** | **外部库** | 486 | **186 处**（`ui.css` 124 + `components.css` 62），另 `index.js` **11 处**（含主色 `#2f73c5`） | **仅 34** | ❌ **唯一卡点** |
| 移动端 `vima-ui-mp` / `vima-ui-h5`（A23/A25 新做） | vima-cli 模板 | 359 | 9 处（全在渐变/遮罩的 `rgba`） | **75** | ✅ 已有 `themes/` 实证 |

**`shell.css` 1386 行只有 1 处字面色值——这是「换肤就绪」最直接的证据。**
vima-cli 自己管的整个骨架层，视觉取值已经全部收敛进 83 个令牌。

**而 vendored 组件库只有 34 个令牌，却在自己的 CSS 里留了 186 处字面色值。**
今天直接换令牌，换掉的只有约三分之二——剩下三分之一不跟着变，结果是「花的」。

### 10.3 已经跑通的先例

A23/A25 做移动端框架时已经完整验证过这条路径：

- `themes/clinical-blue.wxss`：**只覆盖令牌，不含任何类样式**，换肤 = 在框架样式后多 `@import` 一行；
- 并且有单测锁死这条纪律——`主题文件不得包含类样式`（一旦在主题里写类，换肤就变成了改框架）。

**这套机制原样搬到 admin 端即可，不需要新设计。**

### 10.4 「千业千面」的三级粒度（必须先说清，否则会被理解成无限自由）

| 级 | 换什么 | 现状 | 改动量 |
|---|---|---|---|
| **L1 取值** | 色板 / 字体 / 圆角 / 阴影 / 间距密度 | 骨架侧 **83 令牌里 77 个是取值类**（含 5 个侧栏配色），已就绪；组件库侧需先做 P19 | **零架构改动** |
| **L2 外壳尺度** | 顶栏高 / 侧栏宽 / 页签高 / 密度档 | 已参数化 **4 个 `--v-shell-*` 尺寸令牌**（`header-height` / `bar-height` / `side-width` / `side-width-collapsed`）；**密度档尚缺**（见 P1） | 小 |
| **L2+ 外壳形态** | 侧栏导航 ↔ 顶栏导航、有无页签 | **不是主题**，是 shell 变体，需单独立项 | 中 |
| **L3 组件形态** | 胶囊 ↔ 直角、扁平 ↔ 拟物、表格斑马纹 | 受制于组件库 186 处裸值 | 大，且**在组件库侧不在 vima-cli** |

> **判据**：**主题只换「取值」，不换「结构与行为」。**
> 换色/字/圆角/密度 = 主题；换导航形态、换信息架构、换交互行为 = 功能变更，走正常立项。
> 这条线不划清，「千业千面」会滑成「每个行业一个分叉」。

### 10.5 「核心功能与脚手架接口不变」——这一条在现状下已经成立

两者的分离**已经是结构性的**，不是靠自觉：

| | 内容 | 现状证据 |
|---|---|---|
| **接口面（不变）** | `template.json` 的 `apps`/`kinds` 结构、骨架目录约定、`request` 门面形状（V-CODE-01 依赖它）、`docs/contracts/` 契约、17 个内置页面的功能与路由、后端 RBAC/认证/系统模块 | 这些全部与样式无关，主题文件碰不到它们 |
| **风格面（可变）** | `tokens.css` 的 83 个令牌 + 组件库的 34 个令牌 | `shell.css` 1386 行只有 1 处裸值 = 结构与取值已分层 |

### 10.6 建议清单（续 §9 编号）

| 编号 | 建议 | 归属 | 规模 |
|---|---|---|---|
| **P18** | **主题作为正交维度进 vima-cli**：`template.json` / manifest 增 `theme` 字段（**不是第五种 kind**——kind 是端形态，theme 是取值集，两者正交）；`create --theme <id>`；`init` 装主题文件；`update` 时主题属 **userOwned 永不覆盖**；`doctor` 加一项主题完整性 | vima-cli | **小（百行量级）** |
| **P19** | **vendored 组件库令牌化收敛**：186 处字面色值 → 令牌，34 个令牌扩到与骨架同量级（~80）；`index.js` 里 11 处字面色值（含主色）一并清掉 | **vima-ui-admin 库侧** | **中大——这是真正的工作量所在** |
| **P20** | **主题纪律机检**：主题文件只许定义令牌、不许含类样式；主题覆盖的令牌必须都是已定义的（拼错即静默失效）。**口径与实现直接照抄 A25 的移动端主题单测** | vima-cli | 小 |
| **P21** | **登录页 30 处裸值收编**（唯一有裸值的内置页面）；其余 16 页已达标，不动 | vima-cli 模板 | 很小 |

### 10.7 必须避开的坑

- **不要「每个行业一套 dist」。** vima-ui 的 vendor 已经吃过分叉的亏（vendor 里的 dist 比库仓库源码新，同步只能逐文件 cp，整目录覆盖会回退手改）。
  **N 套框架 = N 份漂移**；正确形态是**一套框架 + N 个只含令牌的主题包**。
- **不要把主题做成 kind。** kind 是端形态（决定词表、外壳、机检面、骨架），theme 是取值集。
  混成一个维度会让 `admin-web × 医疗 / admin-web × 政务` 变成两个 kind，词表与机检面全部重复一遍。
- **不要让主题能改结构。** 见 §10.4 判据。主题里一旦允许写类，`vima update` 换框架版本时
  就会与主题打架——这正是 P20 那条机检存在的理由。
- **行业主题的「设计」不是工程活。** P19 做完之后，每套行业主题的取值该长什么样，
  是设计问题——**这正是 §4.2 的结论落地的地方**：用 Design MCP 在规划期产出行业视觉方案，
  人审后固化成一个只含令牌的主题文件。一次产出，之后零 token、可 diff、可机检。

### 10.8 一句话回答

> **可行；vima-cli 侧是小改（P18/P20/P21，百行量级），因为骨架层早已令牌化
> （`shell.css` 1386 行只有 1 处裸值）。真正的工作量在 vendored 组件库的令牌化收敛（P19），
> 那是 `vima-ui-admin` 的活，不是 vima-cli 内核的活。**
> 移动端两个 kind 已经把整条机制跑通了，admin 端照搬即可。

## 十一、补评：用「真实框架 + 实时预览」替代网页版原型工具

> 追加日期：2026-08-14
> 用户第四轮设想：在当前脚手架下，让 Claude Design 直接产出**真实前端代码与设计**，
> 用前端 dev server 的**实时预览**替代网页版 Claude Design / open design 的原型展示
> （**可接受无后端接口对接**）。理由：这是在真实前端框架上开发，比网页原型更接近落地。

### 11.1 结论

**思路成立，优势是真的，而且它比本文 §4.2 的方案更强**——§4.2 只让 Design MCP 产出
「视觉方案 → 固化成令牌」，本方案直接把设计产出变成**可运行的真实页面**，
少了「设计稿 → 代码」这道最容易失真的翻译。

**但今天直接做不到，有两道硬坎；补齐它们是中等工作量，且其中最核心的一块有双重价值。**

### 11.2 两道硬坎（实测）

| # | 坎 | 实测证据 | 后果 |
|---|---|---|---|
| 1 | **路由守卫强制登录** | `router/index.ts:143` —— `if (!userStore.isLoggedIn) next({ path: '/login' })` | 无后端 → 登不进去 → **一个业务页都看不到**，只能看登录页 |
| 2 | **零 mock 层** | 全骨架 `grep mock` 命中 **0**；只有一个 `VITE_API_BASE_URL` 声明，**连 `.env` 文件都没有** | 页面渲染即请求失败，看到的是空表格与错误吐司，不是设计 |

### 11.3 但底气也是实测出来的：**契约可以确定性驱动 mock**

| 实测 | 数据 |
|---|---|
| Sustain 契约文件 | 21 个 |
| 接口数 | **270** |
| **带 `response` 声明的接口** | **270（100%）** |
| 字段类型全集 | **仅 8 种**：`string / number / boolean / date / datetime / array / object / json` |

**8 种类型 → 8 条生成规则**，零随机数、零时间戳 → **同输入同字节**，
完全符合「确定性优先」硬约束。

> 这是本方案相对一切外部原型工具的**决定性优势**：
> **假数据的字段名与真实接口一字不差**，因为它们来自同一份契约。
> 网页原型里的数据是编的——落地时字段对不上，那正是「原型很好看、做出来不是那回事」的来源。

### 11.4 优势逐条落实（不空谈「更接近落地」）

| 优势 | 具体机制 |
|---|---|
| **零转换损耗** | 网页原型 → 代码 这一步是失真主因；本方案产物**即代码** |
| **数据真实** | mock 由契约生成（§11.3），字段名 100% 对齐 |
| **跨页一致由框架保证** | 这恰好解掉了本文 §4.1 否决 Design MCP 的**第 4 条理由** |
| **能被机检管住** | `post-write`（风格）、页面冒烟（版面）、`trace`（标注）全都作用得上；网页原型是机检盲区 |
| **可 diff / review / update** | 产物在仓库里，走正常评审与 `vima update` |

### 11.5 但它**不替代**线框原型——三者定位不同，顺序不能倒

| 产物 | 回答什么问题 | 成本 | 时机 |
|---|---|---|---|
| `vima render-prototype` 线框 | **有没有、对不对**（区块齐不齐、连线通不通、权限对不对） | 零依赖、秒级、字节确定 | 规划期 `approve` 闸门 |
| **真实框架实时预览**（本方案） | **好不好看、顺不顺手、撑不撑得满** | 需 dev server + mock | 设计期 / 开发期 |
| 网页版 design 工具 | 视觉方案探索（另起一种视觉时） | 云端、一次性产物 | 仅在需要换视觉语言时 |

> **顺序判据：先线框（便宜、可否决），再真实预览（贵、但真实）。**
> 倒过来 = 在可能被否决的版面上先花真实代码。

### 11.6 建议清单（续 §10 编号）

| 编号 | 建议 | 说明 | 规模 |
|---|---|---|---|
| **P22** | **演示态开关**：`.env.demo` + `VITE_DEMO=1`；守卫在 demo 态放行并注入假用户（**`perms: ['*']` 必须给**，否则按钮级权限会让页面点不动，看到的仍不是完整设计）。构建期剔除，**不进生产产物**（与 A7 上报同款纪律） | 解坎 1 | 小 |
| **P23** | ⭐ **契约驱动 mock**：由 `docs/contracts/*.md` 确定性生成 `src/mocks/contract-mock.ts`，`request` 门面在 demo 态短路返回。**8 种类型 8 条规则**；列表接口按「数据量档位」返回（空 / 少 / 多 / 极端长文本） | 解坎 2；**本方案的核心** | 中 |
| **P24** | **页面画廊**：`/__gallery` 路由列出全部带 `data-page` 的业务页，支持视口切换（375/1280/1920）与三态切换（正常 / 空 / 加载 / 错误）。**页面发现复用 §6.2 的同一套判据** | 让「实时预览」真的能一屏看全 | 小 |
| **P25** | **与页面冒烟共用一套 stub 与页面发现**，不做两份 | 见下 | —— |

### 11.7 为什么 P23 不是镀金：一份 mock，两个消费方

> §6.4 已经定了页面冒烟测试的数据来源是「stub 请求返回契约里的 response 示例」。
> **P23 正是那一块**——做一次，同时喂给「实时预览（给人看）」与「版面冒烟（给机器看）」。
> 这也是建议**立项己与立项丙一起做**的原因：分开做必然出现两套 mock、两套页面发现。

### 11.8 风险与边界

- **mock 只反映契约的「结构」，不反映业务的「分布」。** 列表 3 条与 3000 条的版面表现
  完全不同。所以 P23 的**数据量档位**不是可选项——**「极端长文本 / 空列表」恰恰是暴露
  版面缺陷最有效的两档**，比正常数据有用得多。
- **mock 必须由契约生成，不能手写。** 手写 mock = 第二份契约 = 必然漂移。
  生成物应标记为受管文件，契约变更后重新生成。
- **demo 态不得进生产构建**，也不得让 demo 用户态泄漏到真实登录逻辑里。
- **不要用它替代 `approve` 闸门。** 线框原型是确定性产物、能字节比对、能进 CI；
  实时预览需要跑起服务，**不适合做闸门**，适合做设计与评审的现场。
- **不做「设计稿与实现的像素 diff」**（§7 已定），本方案让二者本来就是同一个东西，
  这个需求自动消失。

### 11.9 对前几轮结论的影响

本方案**加强**而非推翻 §4.2：

> Design MCP 仍然进规划期，但它的产出物形态可以升级——
> 从「设计稿 + 令牌方案」升级为**直接在真实骨架里写页面**，
> 再由 P22–P24 提供的演示态把它跑起来给人看。
> **「设计」与「实现」不再是两个产物，而是同一个产物的两次评审。**

## 十二、补评：线框「画不出三列」的真实机制，与 AI 介入的正确位置

> 追加日期：2026-08-14
> 用户提出：线框图布局太古板、不够灵活，**很难设计出三列数据的页面**；并进一步认为
> **框线设计才是最难搞定的，应当由 AI 介入**——充分考虑「内容有什么、什么类型的数据
> （数据格式与行业背景）、什么样的人机交互、什么样的可读性」这些人类需求的附加价值。

### 12.1 先纠正一个可能的误判：分栏能力**已经有了**

`regions`（A14）实现正确。造一个三列页面实测：

```yaml
layout: [cards, cards, cards]
regions:
  - columns:
      - { name: 待办,     width: 264px, blocks: [cards] }
      - { name: 主工作区, width: 1fr,   blocks: [cards] }
      - { name: 实时指标, width: 224px, blocks: [cards] }
```

`validate` **0 错 0 警**；渲染产物里 `wf-cols` 容器 + 三个 `wf-col`，
`flex:0 0 264px` / `flex:1 1 0` / `flex:0 0 224px` 宽度全对，列名与列宽标注都在。
Sustain 实战 spec 里 `regions` 也确实用了 **10 处**。

> 排查提示：渲染器用的是 `wf-col` + flex，**不是** `grid-template-columns`。
> 按后者搜会搜不到，容易误判成「没实现」。

### 12.2 真实机制：**列内内容没有差别**

三列渲染出来是这样——三个一模一样的灰盒：

```html
<div class="wf-block wf-cards"><span class="wf-tag">cards</span>
  <div class="wf-row"><div class="wf-ph-lg"></div></div></div>
```

根因在渲染器：**只有 5 个词有专门的高保真渲染函数**
（`table` 会取契约 response 字段画真实列头、`form`、`list`、`detail`、`pagination`），
其余全部走同一个兜底分支——**`items` 为空就渲染一个灰盒 `wf-ph-lg`**。

| kind | 高保真 | **低保真（无 items 即灰盒）** |
|---|---|---|
| `admin-web`（7 词） | `table` `form` `pagination` | **`toolbar` `search` `cards` `tabs`** |
| `mp-native` / `h5-mobile`（8 词） | `list` `form` `detail` | **`search` `cards` `tabs` `banner` `actionbar`** |

**而「三列数据页」的三列，典型内容恰恰全是 `cards`——正好落在低保真区。**

再往下一层，根子在**数据模型**：`components[]` 条目只支持
`block` / `items` / `api` / `rowActions`。**`cards` 装数据时，spec 里没有地方写
「几张卡、每张卡是什么」**——所以 AI 就算想清楚了也写不下来。

### 12.3 因此「AI 介入」的位置要说准

**问题不是「AI 设计得不够好」，是「AI 没有能写下设计判断的语言」。**
同一个缺口有四个下游表现，它们是同一件事：

```
AI 的设计判断无处落笔  →  渲染器无从提高保真度  →  人审看不见  →  Builder 拿不到
                                                              ↓
                                              编码期重新自由发挥（§1.1 的 8572 行私有样式）
```

更根本的一句定性：

> 实体有 spec 第二章、接口有契约、业务规则有 `vima:rules`、页面有哪些区块有 `layout`
> ——**唯独「怎么排」没有真源**。版面是这套体系里最后一个没有真源的东西，
> 所以它是唯一一个每页都要重新即兴发挥的东西。**这就是「框线设计最难搞定」的结构性原因。**

### 12.4 建议（续 §11 编号）

| 编号 | 建议 | 层级 |
|---|---|---|
| **P26** | **区块补内容语义键**：`components[]` 增 `name`（实例名——三个 `cards` 立刻可区分，**并顺带解掉 `data-block` 对账用 Set 去重、同名区块无法分辨的问题**）、`intent`（这块给谁看、解决什么）、`density`；`cards` 补 `cards: [{title, value, hint}]`，`tabs` 补页签名 | L3·validate + L1·渲染器 |
| **P27** | **把「版面设计」变成规划期显式步骤**，让 AI 逐页回答五问并写进 spec：内容是什么 / 数据形态（列表·单条·指标·时序）/ 读者与场景 / 最高频交互放哪 / 一屏必须看到什么 | L5 + L3 |
| **P28** | **给 AI 判断的依据而不只是要求**（P15 的延伸）：提供**版面模式库**（列表页 / 详情页 / 工作台 / 看板 / 表单页 / 主从页的范式），AI 选模式 + 按行业与数据形态微调。**从零编正是「凌乱」的来源** | L1·context |
| **P29** | 线框渲染器按 P26 的新键提保真：`cards` 画出卡片数与字段位、`tabs` 画出页签名 | L1·渲染器 |

### 12.5 保真度红线（防过度设计）

**不要把线框往高保真无限推。** 判据：**保真度只需提到「能看出三列各自不同、能看出主次与密度」**，
再往上交给 §十一 的真实框架预览。线框的价值是**便宜 + 确定性 + 能否决**；
推成高保真就变成第二个前端框架——维护成本爆炸，且永远追不上真实渲染。

## 十三、补评：细化到按钮——**垂直空间**，不是像素尺寸

> 追加日期：2026-08-14
> 用户表述（经其本人纠正后的准确版本）：页面布局设计需要细化到按钮，
> **不需要精确到按钮的具体宽度，而是需要精确到「某个位置是否能放下这个按钮」**，
> 以此解决**按钮独占一行、挤占页面高度**的问题。

### 13.1 一处必须区分开的先例（否则会误引）

vima-cli 确实否决过一次「把按钮尺寸写进配置」——但那是**表格操作列的水平宽度**：
9 个页面 10 个操作列写死 `width: 220/230/160/150` 全是死配置（VTable 按行内按钮真实文案
逐行算宽取最宽行，**声明 220 实际渲染 286**），已删除并立机检
（`post-write.mjs` + `coding-standards.md`「操作列不写 width」）。

**那条裁决管的是「列内水平尺寸」，与本节的「页面级垂直空间」不是同一件事，不能拿来否决本需求。**

### 13.2 实测：这个问题有多大

| Sustain 50 个业务页面 | 实测 |
|---|---|
| 含 `toolbar` 区块的页面 | **41 页（82%）** |
| 其中按钮只有 1–3 个（完全可并入上一行） | **32 页（78%）** |
| **其中只有 1 个按钮** | **17 页** |
| 平均每页纵向带数 | **4.6 条** |

按框架取值算：一条 toolbar 带 ≈ 控件高 38px + 上下间距 16px×2 ≈ **70px**；
1080p 下工作区可用高约 944px ——**为一个按钮吃掉约 7.4% 的首屏高度**。
**17 个页面为了放一个按钮独占了一整条带。**
这与 §1 量到的「内容撑不满 / 页底空洞」是同一件事的两端。

### 13.3 根因：一维 `layout` 决定了「按钮只能独占一行」

`layout` 是一维词序列，**每个词 = 一条独占横带**；而 button 在模型里只能作为某个 block 的
`items`。于是「新增」按钮唯一的存在方式就是 `toolbar` 这条独立带。

真实设计里按钮有 6 种位置，**现在只能表达 2 种**：

| 位置 | 现状 | 框架落点 |
|---|---|---|
| 独立工具条 | ✅ 唯一常用的 | `toolbar` 带 |
| 表格行内操作 | ✅ | `rowActions` |
| 搜索栏行尾 | ❌ **表达不了** | 搜索栏是 flex 行，尾部有空位 |
| 卡片头右侧 | ❌ **表达不了** | **`.vui-card-extra` 已存在**（`flex: none`） |
| 分区标题右侧 | ❌ | — |
| 页尾固定操作条 | 移动端有 `actionbar` 词，admin 无 | — |

**框架的落点已经有了，规格说不出来。**

### 13.4 建议：声明「附着点」+「优先级」，两个键覆盖两个方向

| 编号 | 建议 | 说明 | 层级 |
|---|---|---|---|
| **P30** | **操作附着点**：宿主块增 `actions: [...]`，表示这些按钮**贴在本块所在行**而不新起一带。<br>选它而不选 `anchor: <块名>` 的理由：天然表达「贴谁」，不需要引用解析，也不会引入「anchor 指向不存在的块」这类新错误 | 解**垂直**方向（省一整条带） | L3·validate + L1·渲染器 |
| **P31** | **操作优先级**：`rowActions[]` / `items[]` 的 button 增 `priority: primary \| secondary \| overflow`；**框架按密度档自动把超出的收进「更多」下拉**（复用已有的 `VDropdownMenu`；compact 2 / default 3 / loose 4） | 解**水平**方向（省一行内宽度） | L1·框架 + L3 |
| **P32** | **「放不放得下」由运行期量测判定，不在规格期估算**：§6.3 的探针补第 7 条——**检测同一行内是否发生了 flex 换行**（同行元素 `offsetTop` 不一致即换行）。发现即报，按规格声明的降级策略处理 | 见下 | L3·冒烟 |

### 13.5 关键分工：规格声明意图，运行期判定「放不放得下」

**「能不能放下」不能在规格期判定**——它取决于文案长度、字号、密度档、视口宽度。
这与操作列宽度是同一个道理（那次实测：声明 220、实际 286）。正确分工：

- **规格期**：声明**意图**（想贴哪、谁重要）+ **降级策略**（放不下怎么办：换行 / 收进「更多」 / 退回独立带）；
- **运行期**：冒烟探针量真实渲染，**换行 = 事实，不是审美**，因此可判定、可机检、可回归。

> 一句话：**AI 判断「哪个按钮重要、该贴在哪」（业务语义，它擅长）；
> 框架计算「多宽、放得下放不下、超了收哪个」（确定性、可复现、随主题自动变）。**
> 最好的佐证是 VTable 自己——它已经在按真实文案算宽了。

### 13.6 顺带发现的一个缺陷（P33）

**P33**：`templates/admin/planning/prototype.mjs` 含 **1 个字面 NUL 字节**
（与早先在 `lib/commands/validate.mjs` 修掉的同类）。它让该文件对 `grep`/`file` 变成
二进制、默认静默不匹配——本次排查第一遍搜 `regions` 返回空，**差点误判成「渲染器没实现分栏」**。
